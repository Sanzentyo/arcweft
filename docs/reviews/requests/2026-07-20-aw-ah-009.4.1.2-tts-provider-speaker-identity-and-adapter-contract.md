# AW-AH-009.4.1.2 — TTS provider-speaker identity and adapter contract

## Sequence and independence

The returned AW-AH-009.4.1 package combined dialogue View character projection
with a proposed `tts_speaker` rename. Current production has no
`arcweft-audio-tts` crate, no accepted provider-speaker catalog, no provider
speaker ID type, and no production TTS adapter dispatch model matching the
proposed wire.

This request therefore owns TTS provider identity as an independent design.
It may run in parallel with
[AW-AH-009.4.1.1](2026-07-20-aw-ah-009.4.1.1-dialogue-view-character-projection-production-contract-correction.md)
and must not block dialogue character projection, display-name localization,
View evaluation, save, Agent observation, accessibility, capture, or the
AW-AH-009.4 runtime sequence.

The only fixed relationship is:

```text
CharacterId != TtsSpeakerId != provider-owned speaker key
```

Any mapping among them is explicit accepted metadata, never identity
equivalence or string fallback.

## Why this split is required

Dialogue View character projection consumes an already accepted
`DialoguePresentationCharacter` and can render, save, observe, and restore it
without synthesizing audio. TTS instead requires provider discovery,
capability policy, external I/O, cancellation, secret handling, and an adapter
protocol. Combining the two would couple a presentation-only migration to a
new external subsystem and would obscure which failures may block dialogue
display.

The split lets AW-AH-009.4.1.1 finish the nested View projection without a TTS
crate, provider, or credential. This request can then select a complete TTS
boundary on its own evidence and implementation schedule.

## Current problem

The original package selects:

```rust
pub struct TtsSpeakerId(PublicId);

pub struct TtsProviderSpeakerBinding {
    pub tts_speaker: TtsSpeakerId,
    pub provider: TtsProviderId,
    pub provider_key: TtsProviderSpeakerKey,
}
```

but it does not reconcile that sketch with an existing runtime subsystem.
There is currently no production owner for:

- `TtsSpeakerId`;
- `TtsProviderId`;
- `TtsProviderSpeakerKey`;
- accepted TTS provider-speaker bindings;
- provider capability/locale inventory;
- TTS request/result protocol;
- adapter dispatch;
- provider-specific key secrecy/publication;
- bundle/save/hot-reload behavior;
- the proposed diagnostics and codec tests.

Calling this a field rename would hide a new subsystem behind an apparently
small migration. The design must either define the minimum complete TTS
boundary or explicitly prove that TTS remains documentation-only and defer all
source/product fields.

## Design objective

Select one typed, Sans-I/O TTS request and provider-speaker identity model that:

- keeps provider identity separate from Character identity and physical audio
  devices;
- can be discovered through the final typed manifest/generated adapter
  metadata path;
- validates all provider mappings before dispatch;
- sends I/O only through an adapter boundary;
- preserves deterministic request identity, replay/debug observability, and
  cancellation behavior;
- exposes no provider secret as semantic public identity;
- does not require or block the dialogue View character projection.

## Required decisions

The returned contract must close every decision below. If any observable
choice remains open, return `STATUS=NOT_READY`.

### 1. Subsystem and crate ownership

Choose whether TTS warrants:

- a new lower Sans-I/O `arcweft-audio-tts` model crate;
- a responsibility module in an existing lower audio crate; or
- no production subsystem yet.

If a new crate or module is selected, provide the exact dependency graph and
explain:

- why the owner is below runtime-driver/host adapters;
- why it does not depend on dialogue, syntax, LSP, filesystem, network,
  platform audio, or provider SDKs;
- which crate owns request/result/error data;
- which crate owns adapter execution and provider SDK integration;
- which facade, if any, re-exports a deliberately small public surface.

Do not create a new crate solely to preserve a name sketched by the original
package.

### 2. Nominal identities

Define exact validated types for:

```text
TtsSpeakerId
TtsProviderId
TtsProviderSpeakerKey
TtsVoiceProfileId, if needed
TtsRequestId or TaskKey relationship, if needed
```

For each type, specify:

- owner and visibility;
- canonical family or grammar;
- maximum bytes/scalars;
- constructor and error type;
- serde/wire form;
- equality, ordering, hashing, and redaction behavior;
- whether it is public semantic identity, accepted artifact identity, or an
  opaque provider-owned value.

If `TtsSpeakerId` uses `PublicId`, select one canonical family such as
`tts_speaker.*` and prove it cannot accept `character.*`, `speaker.*`, device,
or provider-key values.

### 3. Character-to-provider mapping

Define the exact optional relationship among:

- `CharacterId`;
- authored voice profile;
- locale/style/rate/pitch metadata;
- `TtsSpeakerId`;
- `TtsProviderId`;
- `TtsProviderSpeakerKey`.

Select:

- whether one Character can have multiple providers/locales/profiles;
- deterministic selection order;
- duplicate and conflict rules;
- missing-profile behavior;
- whether a non-dialogue TTS request may select a provider speaker directly;
- how a Character-valued API argument is named and typed;
- whether selection is build-time, accepted-runtime, or per-request;
- how hot reload invalidates active or queued requests.

There is no implicit fallback from Character ID text, display name, declaration
name, variable name, or a historical `speaker` field.

### 4. Source and typed-resource surface

Reconcile the design with the top-level declaration reduction and Lang-01.4.
Choose whether authors use:

- a typed `res` value such as a voice profile;
- project/build manifest metadata;
- generated provider metadata;
- an ordinary typed function/API call;
- or a combination with one clear owner for each layer.

Do not restore a dedicated `voice`, `voice profile`, `speaker`, or TTS
top-level keyword if that family is assigned to typed `res` or manifest
metadata.

Define exact source types, callable parameter names, return types, effects,
and diagnostics. If a Character argument is accepted, name it `character`.
Provider identity uses `tts_speaker`; physical output routing uses a separate
device/bus type.

### 5. Manifest and generated adapter metadata

Define one accepted manifest path for:

- provider declaration;
- provider capability and supported locales;
- provider speaker/profile binding;
- provider-specific public configuration;
- adapter artifact identity and ABI;
- secret/credential references without embedding secrets in Sans-I/O data.

Reconcile with Lang-01.5.1's single decoder and
`arcweft-adapter-metadata`. Select the exact typed record, source ranges,
duplicate behavior, canonical ordering, semantic digest, and publication
transaction.

Do not add a second TOML/JSON parser, direct filesystem read, provider-specific
manifest reader, or legacy `speaker` alias.

### 6. Request, result, and adapter protocol

Define complete Sans-I/O records for:

- synthesis request;
- selected provider and speaker evidence;
- text or accepted text reference;
- locale and synthesis options;
- progress;
- audio result or stream;
- cancellation;
- timeout and retry policy;
- structured provider error;
- adapter capability negotiation.

Select whether TTS returns a complete audio asset, a typed stream, a task/Need
result, or another existing runtime abstraction. Reuse the final ordinary
function/suspension/typed Stream contracts rather than inventing a TTS-only
execution model.

Specify which fields participate in deterministic task identity and which
provider outputs are inherently nondeterministic. Define replay/debug behavior
without pretending external synthesis bytes are reproducible when they are
not.

### 7. Wire and version ownership

Define the exact canonical wire owner for:

- provider metadata;
- speaker/profile bindings;
- request/result protocol;
- optional bundle references;
- save or replay records, if any.

For each wire, specify:

- schema/ABI/version;
- deterministic field order and discriminants;
- count and encoded-size budgets;
- malformed, duplicate, unknown, trailing, truncated, noncanonical, and
  oversized rejection;
- semantic digest and artifact binding;
- whether active requests may be saved or must block save;
- hot-reload compatibility.

Current production has no released `speaker` provider wire. Move directly to
the final model; do not add a dual reader or version bump whose only purpose is
to memorialize the design sketch.

### 8. Adapter and capability boundary

Define:

- capability names and policy checks;
- provider availability and locale/style capability validation;
- the adapter trait or request envelope;
- host ownership of network/process/provider SDK I/O;
- cancellation and resource cleanup;
- concurrency and rate-limit ownership;
- provider-key secrecy and logging redaction;
- error mapping that preserves structured provider context without leaking
  secrets;
- test doubles and Sans-I/O simulation.

Lower audio/data crates must not call provider SDKs or read environment
variables, files, credentials, clocks, or network.

### 9. Diagnostics

Specify stable diagnostics, owners, structured fields, and source/runtime
locations for at least:

- malformed or wrong-family TTS identity;
- unknown provider or speaker;
- duplicate provider/speaker/profile binding;
- invalid or duplicate provider key;
- Character/profile mapping mismatch;
- unsupported locale or synthesis option;
- unavailable capability/provider;
- rejected secret-bearing field;
- adapter ABI/artifact mismatch;
- request limit, timeout, cancellation, and provider failure.

Historical `speaker` source/manifest fields receive ordinary unknown-field or
unknown-argument diagnostics. Do not add a dedicated removed-name diagnostic.

### 10. Limits and privacy

Fix exact limits for:

- identity and provider-key bytes;
- provider/profile/binding counts;
- request text bytes/scalars;
- option counts and encoded bytes;
- result bytes or stream buffering;
- in-flight and queued requests;
- diagnostic/provider payload bytes.

Classify every ID, provider key, request text, debug field, and Agent/MCP
projection. Provider keys and credentials must not be published as public
semantic identity or Agent-visible text.

## Required implementation order

The returned contract must specify coherent cuts in this dependency order:

1. land or consume the final single-manifest and generated adapter metadata

2. add the lower nominal identity/request/result model with no I/O;
3. add accepted provider/profile catalog and canonical codec;
4. add host adapter capability and dispatch boundary;
5. integrate typed source/resource/function surfaces;
6. integrate runtime cancellation, save blockers, hot reload, debug, and

7. delete every ambiguous provider `speaker` and Character-valued `speaker`
   argument without aliases;
8. run focused, workspace, adapter simulation, codec tamper, capability,
   structural, and applicable Tier 2 tests.

If no production TTS feature is justified yet, the returned order must instead
remove or defer the documentation-only fields and state the concrete demand
that would authorize a future implementation.

## Projection non-blocking contract

AW-AH-009.4.1.1 and the CharacterDialogue/View runtime must be able to complete
without this TTS subsystem.

The projection contract may carry an already selected optional voice/profile
reference from AW-AH-009.4, but:

- character display-name resolution does not query TTS;
- View evaluation does not require a provider;
- save/restore of dialogue presentation does not serialize provider speaker
  keys;
- Agent/MCP/accessibility/capture does not infer voice identity;
- missing TTS capability cannot invalidate an otherwise valid dialogue View
  projection.

## Constraints

- Do not conflate a narrative Character, provider speaker, physical speaker
