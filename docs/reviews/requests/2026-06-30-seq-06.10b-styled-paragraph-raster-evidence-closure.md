# Request: seq-06.10b styled paragraph raster evidence closure

## Sequence position

This follows seq06.10 cross-backend text raster parity and seq06.10a styled
paragraph layout.

Seq06.10 added native/Web frame evidence, font pinning, and a text-raster
verifier. Seq06.10a replaced dialogue body run-per-block layout with
`RenderStyledParagraph`. Applying both exposes a real remaining gap:
paragraph-level evidence is not yet rich enough for meaningful text-raster
comparison, and the first-cut glyph-area transform route is not wasm-safe.

Do not redesign the viewport scale contract, native/Web player launch paths,
hidden DOM policy, or the root styled paragraph model unless current evidence
shows a concrete flaw.

## Current evidence

- `RenderStyledParagraph` is the dialogue body layout substrate.
- Native and Web frame reports expose styled paragraph text and span metadata.
- `just css-style-parity` builds the wasm player and captures native/Web PNGs,
  but fails the existing default full-image threshold once the long styled
  paragraph fixture is present.
- `tools/verify-text-raster-parity.rs` can parse styled paragraph metadata, but
  it currently expands every span to the full paragraph bounds. This produces
  noisy failures instead of a useful paragraph-raster diagnosis.
- A direct `arcweft-render-wgpu -> arcweft-glyphon` dependency broke the
  `wasm32-unknown-unknown` Web player build because the current glyph-area
  adapter uses glyphon custom glyph-area types that are unavailable there.

## Goal

Design and implement the final evidence and validation closure for
renderer-owned styled paragraph raster parity across native and Web.

The result should make `just css-style-parity` useful again for the styled
paragraph fixture: it should either pass with justified thresholds or fail with
specific paragraph/glyph evidence that points to the remaining backend drift.
Do not solve this by hidden DOM text, browser CSS text, canvas 2D fallback text,
or unchecked threshold loosening.

## Required decisions

1. What paragraph evidence must be emitted by native and Web frame reports:
   line boxes, glyph bounds, source byte ranges, visible/revealed state,
   per-glyph or per-cluster color, font metrics, and transform metadata.
2. Which crate owns the evidence extraction so both native and Web consume the
   same renderer-prepared paragraph model.
3. Whether glyph transforms for wave/shake/jitter can be rendered through a
   wasm-safe shared path now, or must remain typed metadata until a separate
   glyph-area abstraction is available for Web.
4. How `tools/verify-text-raster-parity.rs` should compare styled paragraphs:
   paragraph union masks, per-line masks, per-glyph/cluster masks, or a
   combined layout-first plus mask-tolerance model.
5. How full-image `verify-webgpu-parity` thresholds should interact with
   text-specific thresholds after a long styled paragraph is present.
6. Whether `just css-style-parity` should generate all evidence before failing
   a gate, so failed runs still leave diagnosable JSON artifacts.

## Implementation requirements

- Keep native and Web rendering on the shared renderer-owned path.
- Do not reintroduce dialogue run-per-block layout or estimated text width.
- Do not add hidden DOM mirrors, HTML text overlays, browser-only CSS text,
  canvas 2D text fallback, or product/runtime compatibility shims.
- Keep renderer/data crates Sans I/O; file writes stay in tools/tests/adapters.
- Keep wasm build green for `arcweft-player-web`.
- Add typed evidence rather than reconstructing layout from screenshots.
- If glyph transforms cannot be rendered wasm-safely in this cut, record that
  as explicit typed unsupported evidence and keep rendering deterministic.

## Suggested implementation order

1. Audit current `RenderStyledParagraph`, `styled_paragraph_layout_evidence`,
   native frame report, Web frame report, and text-raster verifier shapes.
2. Define one shared paragraph evidence structure with line/glyph/cluster
   bounds and span/style mapping.
3. Emit that evidence from both native and Web frame reports.
4. Update `verify-text-raster-parity.rs` to compare paragraph evidence without
   expanding every span to the full paragraph bounds.
5. Decide and implement the wasm-safe glyph-transform strategy or explicitly
   keep transform rendering out of this cut with typed evidence.
6. Re-run default, compact, and HiDPI CSS-style parity and tune only justified
   text-aware thresholds.
7. Update `just css-style-parity` so report generation and gate failure order
   leaves enough evidence for review.

## Tests and validation to specify

- `cargo test -p arcweft-render-wgpu --test styled_paragraph --all-features`
- focused tests for paragraph evidence line boxes, glyph bounds, reveal state,
  and mixed style spans;
- Web report serialization tests for styled paragraph evidence;
- native frame report generation test or script self-test for styled paragraph
  evidence;
- `cargo +nightly -Zscript tools/verify-text-raster-parity.rs --self-test`
  plus at least one styled paragraph fixture self-test;
- `cargo build -p arcweft-player-web --target wasm32-unknown-unknown`
- `just css-style-parity`
- `just css-style-parity-profile`
- `cargo check -p arcweft-render-wgpu -p arcweft-player-web --all-features`
- `cargo clippy -p arcweft-render-wgpu -p arcweft-player-web --all-targets --all-features -- -D warnings`
- `cargo +nightly -Zscript tools/structure-audit.rs --root .`
- `git diff --check`

## Acceptance criteria

- Native and Web frame reports expose enough typed paragraph evidence to compare
  styled paragraph raster output without DOM/CSS/screenshot layout inference.
- The long CSS-style styled paragraph fixture has meaningful default, compact,
  and HiDPI evidence.
- `just css-style-parity` no longer fails before writing the evidence needed to
  diagnose text drift.
- Full-image thresholds are either still satisfied or replaced by a clearly
  stronger text-aware gate with documented rationale.
- The wasm player build remains green.
- Any remaining glyph-transform rendering gap is explicit, typed, and assigned
  to a follow-up sequence.
