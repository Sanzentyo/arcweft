## Current Problem

The current `web/ime-sample.html` path mixes Arcweft text-input glue with a DOM
sample UI:

- visible text field surface is a `div[role=textbox]`;
- committed text and composition are mirrored into `span` elements;
- the turquoise Arcweft caret is a CSS `.caret` element;
- caret geometry is driven by CSS variables and DOM layout;
- sample status/selection/font panels are visible HTML outputs;
- `web/ime-sample.css` controls text size, field sizing, and the visible caret.

This causes sample evidence that can look unlike the real player. For example,
the caret can be the wrong height or scale relative to rendered text because it
is not produced by Arcweft's renderer-backed text geometry. It also weakens the
architecture signal: users see a DOM textbox sample even though normal Arcweft
Web output should be canvas/WebGPU-rendered, with browser `EditContext` only as
an invisible platform input object.

The desired surface is:

```text
thin HTML host page
  -> Arcweft canvas/WebGPU player
  -> Arcweft-authored TextField/TextArea/SecureField sample bundle
  -> PreparedFrame focused text target
  -> player-owned EditContext bridge
  -> Arcweft-rendered caret, selection, composition, text, style, and status
```

## Request

Produce a zip package with concrete design, implementation overlay, tests,
fixtures, and validation notes that replaces the current Web IME sample with a
player-rendered Arcweft sample.

The package must make `just ime-sample-web` and `just ime-sample-check` exercise
the normal Web player path rather than a visible DOM textbox/mirror.

## Required Decisions

1. What authored `.arcw` or product fixture should be the canonical Web IME
   sample bundle?
2. Whether `web/ime-sample.html` should remain as a thin host page or be
   replaced by `web/index.html?bundle=...`.
3. Which DOM nodes are allowed in the sample page. The intended allowance is:
   canvas host, script/style/font preload tags, and minimal loading/fatal
   surfaces only. Visible text controls, caret, selection, composition,
   mirrored text, status cards, and layout panels must be Arcweft-rendered.
4. How sample status/evidence should be observed without visible DOM outputs.
   Prefer frame/runtime observation events, trace JSON, screenshot evidence, or
   test-only hidden metadata over user-facing HTML panels.
5. How the sample proves multiple font stacks and seq06-compatible styling
   without relying on CSS to render the field itself.
6. How `EditContext` geometry updates are driven from
   `PreparedFrame::focused_text_input_target()` and renderer-backed caret /
   character bounds, not DOM textbox bounds.
7. How Web tests detect caret scale/position regressions in a renderer-owned
   way.
8. Whether the old DOM sample should be deleted or moved to implementation
   documentation as historical evidence. Do not leave it as an active sample.

## Acceptance Criteria

- `just ime-sample-web` opens a Web sample whose visible field, text, caret,
  selection, composition, focus ring, status/evidence surface, and styling are
  Arcweft-rendered, not DOM-rendered.
- The page may contain a canvas host and minimal loading/fatal elements, but it
  contains no visible HTML textbox, mirrored text spans, CSS caret, DOM
  selection surface, or status cards used as the primary sample View.
- Normal player startup owns the active text-input session. App/sample authors
  do not instantiate `EditContext`, own model text, or convert IME events.
- Candidate window geometry is updated from Arcweft prepared text-input
  geometry. It must not use DOM textbox/mirror bounds as the source of truth.
- The turquoise Arcweft caret scales to rendered text metrics across at least:
  - default desktop viewport;
  - compact/mobile-width viewport;
  - high-DPI/device-scale test where available;
  - long Latin text;
  - Japanese preedit/commit text;
  - empty field placeholder state.
- Multiple font stacks are demonstrated through Arcweft product/style data and
  renderer output, not by styling a DOM textbox.
- Secure field rendering and evidence remain redacted.
- Unsupported browsers report typed unsupported state and install no hidden
  textarea/contenteditable fallback.

## Tests To Specify And Run

- Source/audit test proving active Web IME sample pages do not contain visible
  DOM textbox/mirror/caret/status UI.
- JS unit tests proving `web/player-editcontext.js` still owns `EditContext`
  as an invisible platform adapter and does not create hidden textarea or
  contenteditable fallback.
- Browser smoke test for the player-rendered sample:
  - launches the normal Web player;
  - focuses an Arcweft-rendered text field;
  - enters Latin and Japanese text where the browser supports real
    `EditContext`;
  - captures frame/runtime observation evidence;
  - verifies no visible DOM text mirror is used.

- `just ime-sample-check`.
- `cargo fmt --all -- --check`.

## Constraints

- Do not reintroduce hidden `textarea`, `contenteditable`, DOM input, DOM
  selection mirror, or keyboard fallback text insertion.
- Do not solve the caret scale problem by tweaking the CSS `.caret`; the
  visible caret must come from Arcweft renderer geometry.
- Do not use CPU-rasterized Takumi bitmap fallback for the text field. Use the
  normal player renderer path.
- Do not put DOM object identity, browser event objects, or `EditContext`
  objects into Sans I/O crates.
- Do not claim real Japanese IME acceptance unless a browser with usable
  `EditContext` was actually validated. If not validated, document the exact
  manual validation command and expected evidence.
- Do not leave the old DOM sample as an active runnable sample under a name
  that suggests it is the Arcweft Web player text-input sample.

## Non-Goals

- Windows TSF, macOS AppKit, Wayland, Android, or iOS native backend changes.
- Redesigning the shared seq06.3 text-input contract.
- Full rich-document editing beyond the current TextField/TextArea/SecureField
  scope.
- Browser support for non-EditContext engines through hidden DOM fallback.

## Parallelization Guidance

This request should be designed after, or with current-main evidence from,
seq06.4k.1.1 and seq06.4k.1.2 because it depends on product/runtime text-control
emission and write-back being present.

It can run in parallel with native TSF/AppKit validation work because it only
changes the Web sample/player surface. It should not run blindly in parallel
with a change that rewrites `PreparedFrame::focused_text_input_target()`,
`RenderTextInputControl`, or `web/player-editcontext.js`; coordinate the
geometry and JS bridge API first if those files are moving.
