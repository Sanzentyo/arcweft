## Why reconciliation is required

The accepted signature schema currently stores the pre-check validator as:

```rust
pub enum CallableValidator {
    // ...
    Trait(TraitCallableId),
    // ...
}
```

That validator is part of the immutable `CallableSignatureSchema` placed in an
accepted `CallableRecord`. It is constructed and frozen before body checking,
checked-catalog construction, or conformance publication. It is also consumed
by schema digesting, registered-call selection, resolver migration evidence,
and trait-method validation.

The `.3.1` contract simultaneously requires:

- freezing the accepted `RegisteredCallableCatalog` before checking;
- deleting `TraitCallableId`;
- deleting `CallableCandidateId::TraitMethod(TraitCallableId)`;
- constructing `CheckedCallableId` and conformance identity only after the
  accepted catalog is frozen; and
- retaining trait requirements, trait implementation methods, inherent
  methods, standard methods, and environment methods as typed accepted
  records.

It does not define the replacement payload and owner for
`CallableValidator::Trait`, nor whether that variant remains in a structurally
typed form or is replaced by another closed validator shape. A checked ID
cannot simply be stored there because it does not yet exist at registration
time. Reusing a display name, local implementation index, source string, or
sentinel would recreate an explicitly forbidden identity path.

The package also deletes the trait-method candidate variant but does not say
how the retained AW-AH-009.3 observational family
`CallableFamily::TraitMethod` is projected after accepted candidates become
`CallableCandidateId::Project(CallableDeclarationKey)`. That family is observed
by resolver work accounting, checker-owned call facts, signature help, and
registered/non-registered parity tests. Treating all project methods as the
ordinary `Project` family or preserving the obsolete candidate as a hidden
fallback would both be locally inferred behavior.

### 2. Define candidate-to-validator-to-checked identity joins


Cover requirement, implementation, inherent, standard, and environment rows.
State how ambiguity errors retain typed candidate evidence after
`AmbiguousTraitMethod { candidates: Arc<[TraitCallableId]> }` is deleted. No
step may reconstruct identity from trait/method spelling or a local index.

### 3. Close `CallableFamily::TraitMethod`

Decide explicitly whether `CallableFamily::TraitMethod` remains as a
non-authoritative resolver/signature-help accounting family.

If it remains, define the single owning inherent projection from the final
candidate/record/validator shape and distinguish trait requirements,
implementations, and inherent methods as required. If it is replaced, name the
exact final family rows and update the AW-AH-009.3 work-accounting and signature
projection requirements without collapsing trait methods into an unrelated
ordinary-project family.

The answer must preserve one shared resolver invocation, checker-owned call
facts, registered/non-registered parity, and no legacy dispatch. The family is
an observation, not a second semantic identity or catalog.
