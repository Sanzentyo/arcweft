# Seq-04.8.4 Request: Normal Build CLI Goldens and Cache Evidence

## Sequence Position

This follows seq04.8.2 and seq04.8.3 for implementation. Its design can be
started in parallel, but final golden fixtures must be generated against the
actual normal build behavior after those cuts are applied.

Seq04.8.1 proves actual bytecode/link records at the object and read-through
level. Seq04.8.2 and seq04.8.3 make ordinary build producers use those records.
This request fixes the user-visible CLI evidence so regressions are caught from
the normal `arcw build` route, not only from unit tests or package fixtures.

Do not redesign seq04.1 through seq04.8.3 cache substrate unless current
implementation evidence shows a concrete flaw.

## Request

Design and implement end-to-end CLI golden coverage for normal project builds
that exercise bytecode/link persistent cache reuse and conservative evidence.

The tests must run the same command shape users run, normalize host-specific
paths and digests where necessary, and prove that cache evidence is observable
through build JSON, snapshot JSON, and `arcw cache explain`.

## Required Decisions

1. Which minimal project fixture should represent normal build bytecode/link
   reuse.
2. Which CLI output is stable enough for checked-in goldens, and which fields
   require deterministic normalization.
3. Whether golden assertions should be inline Rust assertions, checked-in JSON
   files, `insta` snapshots, or a small repository-owned fixture verifier.
4. How to compare cached versus rebuilt AWFB/AWBC bytes without committing
   environment-sensitive target paths.
5. How to report conservative producers in the same golden suite without
   masking actual-reuse regressions.

## Required Implementation

- Add a normal project fixture under a dedicated persistent-cache fixture
  directory.
- Add CLI tests that run normal `arcw build` twice with a clean target/cache
  root and then inspect the generated build artifacts.
- Add cache explain coverage for the bytecode/link records written by the
  normal build route.
- Normalize paths, timestamps, host-specific roots, and machine-specific
  environment details in expected output.
- Add negative or drift fixtures for stale/corrupt/mismatched cache records if
  they are not already covered at the CLI level.
- Document the fixture regeneration command and keep generated outputs out of
  source control unless they are intentionally stable goldens.

## Tests To Specify

- First normal `arcw build` writes cache evidence and product artifacts.
- Second normal `arcw build` reports actual bytecode/link hits for ready
  producers.
- Rebuilt and reused product bytes have identical content roots and, where
  appropriate, identical AWFB/AWBC bytes.
- `arcw cache explain --json` reports bytecode/link actual hit evidence.
- Conservative producers, if any remain, appear with typed conservative reasons.
- A deliberately corrupt record is a typed soft miss and does not prevent a
  successful rebuild.

## Acceptance Criteria

- Normal build CLI coverage would fail if the full build route stopped calling
  actual bytecode/link builders.
- Normal build CLI coverage would fail if `cache explain` lost actual versus
  conservative distinction.
- Golden output contains no host absolute paths, local usernames, volatile
  timestamps, or machine-specific cache roots.
- Fixture regeneration is documented in `docs/implementation/` and available
  through an existing or new just command if the repository already has a
  matching fixture-regeneration pattern.
- The test suite does not rely on release publish, remote upload, native player,
  web player, or visual golden infrastructure.
