# Request: seq-08.2 standard Iterator / IntoIterator on DSL trait substrate package

## Sequence Position

Seq08.2 depends on seq08.1 DSL trait / impl / associated type substrate. It may
be designed in parallel with seq08.1 only if the design treats seq08.1 as the
source of truth for trait declarations, impl declarations, associated type
projection, bounds, coherence, and witness/conformance representation.

Production implementation must not proceed before the seq08.1 trait substrate is
available or before this package clearly includes the missing substrate as an
explicit dependency section.

Known current evidence:

- Runtime `for` state now uses `RuntimeIterator`, which implements Rust
  `Iterator<Item = RuntimeValue>`.
- `RuntimeIterator::from_value` accepts built-in runtime `Seq`, `Tuple`, and
  finite integer `Range`.
- DSL `for` does not yet resolve a user-authored `IntoIterator` trait impl.
- `docs/01-language/traits-seq-ranges.md` currently says the surface API uses
  `Seq<T>` / `IntoSeq` rather than Rust `Iterator`. This must be resolved as a
  design decision rather than left ambiguous.

## Problem

Arcweft should not keep `for` tied to concrete `Seq` / tuple / range cases once
the language has traits. The final model should allow standard library and
user-authored types to participate through a common trait contract.

However, implementing `Iterator` before the trait substrate would recreate the
same special-case problem under a different name. Seq08.2 must therefore use the
seq08.1 trait model, including associated types and conformance evidence.

## Goal

Design and implement the standard iterable abstraction on top of the DSL trait
substrate.

The package should decide and implement the final user-facing direction for
iteration:

- Rust-like `Iterator` / `IntoIterator`;
- retained Arcweft `Seq` / `IntoSeq`;
- or a staged replacement where `Seq` remains a collection/lazy-sequence type
  but `for` and generic iteration are expressed through `IntoIterator`.

If `IntoSeq` remains, the package must justify why it is not a compatibility
shim and how it composes with Rust-like traits.

## Required Decisions

1. Standard trait names and signatures:
   - `Iterator`
   - `IntoIterator`
   - associated `Item`
   - associated `IntoIter`
   - receiver form for `next` and `into_iter`, including mutation/ownership.
2. Surface syntax examples:
   - `for x in expr`
   - generic function bounds using `I: IntoIterator`
   - associated type constraints such as `Iterator<Item = T>`.
3. Relationship with `Seq`:
   - Whether `Seq<T>` is a concrete lazy sequence type that implements
     `Iterator` / `IntoIterator`.
   - Whether `IntoSeq` is removed from the stable design, retained as an
     explicit separate abstraction, or deferred.
4. Built-in implementors:
   - integer ranges;
   - `Seq<T>`;
   - `Vec<T>` / array / slice if they exist in current language surface;
   - tuple iteration, if it remains supported, including item type rules.
5. Lowering:
   - `for x in expr` should lower through trait resolution, not concrete
     range/sequence checks.
   - Runtime-plan should use the existing `RuntimeIterator` substrate where
     possible.
   - Decide whether user-defined iterators lower to static calls, witness
     calls, or a typed runtime iterator adapter.
6. Runtime and AWBC:
   - How `next` loops are represented in `FlowOp` / AWBC without materializing
     all values.
   - How finite range iteration remains zero-copy / non-materialized.
   - How iterator state is owned, cloned, serialized, or rejected.
7. Diagnostics:
   - no `IntoIterator` impl for `for` source;
   - missing/ambiguous `next`;
   - `Iterator::Item` mismatch with pattern;
   - unsupported infinite/non-serializable iterator in contexts that require
     deterministic replay;
   - concrete `Seq`/range fallback removed or explicitly forbidden.
8. Documentation:
   - Update `docs/01-language/traits-seq-ranges.md` so `for`, ranges, `Seq`,
     and standard iterable traits tell one story.

## Required Implementation Scope

- Define standard trait declarations in the appropriate prelude/core language
  model.
- Add built-in trait impls for current collection/range types.
- Change `for` type checking to require the selected standard iterable trait
  rather than hard-coded concrete iterable shapes.
- Change runtime-plan lowering to carry trait-resolved iteration evidence.
- Preserve the existing `RuntimeIterator` non-materialized range behavior.
- Add tests showing a user-defined type can implement the standard iterable
  trait and be used by `for`, if seq08.1 supports enough method bodies to make
  that executable.
- Add diagnostics tests for missing and ambiguous impls.
- Add an implementation note under `docs/implementation/`.

## Non-Goals

- Do not design a second trait/conformance system.
- Do not add a `protocol` keyword.
- Do not leave old concrete `for` fallbacks as compatibility shims.
- Do not require dynamic trait objects unless the package proves they are
  necessary.
- Do not silently materialize all ranges or sequences to make lowering easier.
