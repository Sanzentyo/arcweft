# Design request: seq-06.11d.4.1 native logical-axis Style contract

- Date: 2026-07-14
- Kind: independently throwable design request
- Output language: English

## Sequence position and delivery boundary

This is the first independent design cut after the implemented native typed
Style, sheet-owned product, and single computed-style resolver of
seq-06.11d.1 through d.3. It defines logical box-axis semantics for native
Style. It does not depend on a CSS adapter and must not recreate one.

Treat this document as the complete task input. The output must be a final
contract and implementation plan that can be handed directly to an
implementation agent. Do not rely on a prior request, package, or external
link for missing decisions.

## Problem and background

The native property inventory already contains logical size, spacing, inset,
translation, and overflow names, but the runtime lacks a single typed contract
that maps inline/block and start/end to physical coordinates. Treating inline
as `x`, block as `y`, start as top/left, or direction as a locale side effect
works only for one horizontal case. It becomes ambiguous for RTL and vertical
View layouts, for simultaneous physical and logical declarations, and for
invalidation when the axis context changes.

The missing contract is a View box/layout concern. RichText glyph writing
direction and vertical text layout are independently owned by the text system.
Neither may be inferred from the other.

## Confirmed substrate that must be preserved

- Arcweft Style is native-only: syntax AST -> native HIR ->
  `CheckedViewStyleCatalog` -> compiler-owned `ViewStyleProgram` -> runtime
  applications -> one `arcweft-view` resolver -> typed consumers.
- `ViewPropertyKind` already owns physical and logical property identities.
  Logical inventory includes inline/block size and min/max forms, logical
  padding/margin sides, logical inset sides, `translate-inline`,
  `translate-block`, `overflow-inline`, and `overflow-block`.
- `ViewSpecifiedValue`, `ComputedViewStyle`, property metadata, inheritance,
  application order, selector specificity, trace provenance, transition
  projection, and `ViewStyleInvalidationSet` are typed and deterministic.
- Physical width/height, top/right/bottom/left, x/y translation, and x/y
  overflow remain valid native properties; the design must define interaction
  rather than deleting them by assumption.
- Player and renderer consumers already project one current computed Style.
  There is no retained alternate cascade or fixed interaction-state mini-style.
- View runtime nodes have stable mounted identity and parent/boundary facts.
- RichText owns glyph direction, shaping, line progression, caret geometry, and
  vertical-writing behavior. Native box-axis context is not derived from a
  RichText run and must not mutate it implicitly.
- Canonical products/codecs contain typed values and deterministic source
  provenance; runtime and codecs do not reopen `.arcw` source.

Do not redesign the property/value catalog, cascade, resolver, or renderer
architecture without identifying a concrete defect required to support axis
resolution. A separate logical/physical alias conflict inside the existing
computed representation is such a possible defect; if found, describe and
repair only that boundary.

## Required decisions

1. Define the closed typed View logical-axis context. It must represent enough
   information to map inline/block and start/end for horizontal LTR, horizontal
   RTL, and the supported vertical progressions without string flags.
2. Define one canonical `.arcw` authoring surface for setting or selecting that
   context, including its default, inheritance/containment behavior, legal
   attachment points, and formatter output. If source authoring is deliberately
   absent in the first cut, define the typed producer and why every View still
   receives a deterministic context.
3. Provide the complete mapping table from each supported logical side/axis to
   physical width/height, top/right/bottom/left, x/y translation, and x/y
   overflow. Include sign conventions and coordinate origins.
4. Define whether block progression is independently selectable from inline
   direction and reject impossible or unsupported combinations with typed
   diagnostics instead of silently normalizing them.
5. Define the cascade relationship when declarations addressing the same final
   physical slot mix physical names, logical names, shorthands, and multiple
   Style applications. Preserve the existing priority tuple and declaration
   provenance; do not choose winners by a post-cascade hard-coded property
   preference.
6. Define the computed representation. Decide whether logical declarations are
   resolved into canonical physical slots before `ComputedViewStyle`, retained
   with an axis snapshot and projected later, or represented by a typed alias
   group. Specify how traces expose authored and resolved identities.
7. Define where axis resolution occurs relative to token resolution,
   inheritance, shorthand expansion, transitions, layout, clipping, hit
   testing, focus geometry, scrolling, and rendering.
8. Define axis-context propagation through nested Views. State whether a
   callee inherits its caller context, declares its own context, or receives an
   explicit call-boundary value, and how exported-part styling observes it.
9. Define how Row/Column/flex direction relates to logical inline/block axes.
   Container layout direction must not be conflated with the writing/axis
   context unless the final contract explicitly and consistently makes it so.
10. Define the authority for direction. Locale, host environment, theme, and
    text content must not change box axes implicitly unless a typed rule says
    they do. Specify deterministic native/headless defaults.
11. Define invalidation and cache identity when the axis context changes.
    Enumerate layout, paint, hit-test, scroll, focus, and text consumers that
    must be recomputed and which unaffected nodes may retain cache entries.
12. Define serialization, canonical ordering, decode validation, and merge
    behavior for the axis context or any new declarations. No runtime source
    parse or compatibility reader is allowed.
13. Define source ranges and diagnostics for unknown axis values, invalid
    combinations, illegal placement, conflicting declarations that cannot be
    represented, and consumers that do not support a resolved logical property.
14. Define formatter and LSP completion, hover, type information, definition,
    rename, semantic tokens, and diagnostics for axis values and logical
    property aliases.
15. Define how animations/transitions behave if an axis context changes while a
    logical property is transitioning. The result must not depend on frame
    timing or unordered map iteration.

## Constraints

- Native-only means no CSS `writing-mode`, `direction`, logical-property parser,
  cascade, CSSOM, Takumi dependency, browser fallback, or CSS-shaped sidecar.
- Do not redesign implemented seq-06.11d.1-d.3 property ownership, sheet
  ownership, application ordering, selector matching, token resolution, or the
  single resolver without a concrete blocking defect.
- Use Arcweft-owned enums/newtypes and inherent/context-owned conversions. Do
  not scatter string switches or free-standing endpoint-to-endpoint helpers.
- Axis mapping must be performed exactly once for each consumer path. Layout,
  render, hit test, avoidance, focus, and scroll geometry must agree.
- Keep `arcweft-core` and data-format crates Sans I/O and preserve architecture
  dependency direction.
- This is an unreleased contract. Replace an inferior provisional shape
  directly; do not add aliases, deprecated fields, dual readers, migrations, or
  compatibility wrappers.
- Do not add a source gate. Validate typed APIs and observable behavior.
- Preserve deterministic fixed-point numeric behavior and explicit overflow
  errors. Do not introduce implicit floating-point or platform locale behavior.

## Non-goals

- CSS compatibility or matching browser writing-mode edge cases.
- Changing RichText shaping, Unicode bidi, glyph orientation, line breaking,
  ruby layout, caret movement, or text selection semantics.
- A new general-purpose layout engine, grid implementation, or arbitrary
  transform coordinate spaces.
- Inferring box direction from text content, locale, font, or a child node.
- Adaptive environment/container condition authoring; those are separate cuts.
- Maintaining a provisional physical-axis shortcut as a compatibility mode.

## Required implementation order

1. Produce the closed axis type and exhaustive logical-to-physical mapping
   table, including defaults and unsupported combinations.
2. Freeze the source/AST/HIR/sema surface and canonical formatter form, or the
   explicit typed producer if no author surface is selected.
3. Define logical/physical alias-group cascade semantics and the exact computed
   representation with provenance.
4. Specify compiler and canonical codec changes, validation, and merge rules.
5. Implement the axis resolver at one owned boundary and remove consumer-local
   guesses exposed by that implementation.
6. Connect layout, transition, render, clipping, hit-test, focus, scroll, and
   nested-View consumers to the same resolved result.
7. Add formatter/LSP support and the diagnostic catalog.
8. Validate every mapping context, mixed declaration case, boundary, codec,
   invalidation, and rendered geometry before declaring logical properties
   supported.

## Required test specification

### Source, semantic, formatter, and tooling

- Every canonical axis value and logical property parses, lowers, type-checks,
  and formats idempotently with exact ranges.
- Unknown values, illegal combinations, invalid placement, malformed logical
  names, and value-kind mismatches produce structured diagnostics and recovery.
- Completion and hover expose the closed axis/value type; rename and references
  operate on typed tokens/properties rather than source text.

### Mapping and cascade

- Exhaustive table tests cover horizontal LTR, horizontal RTL, and each accepted
  vertical progression for size, min/max, padding, margin, inset, translate,
  and overflow.
- Physical/logical declarations in both source orders and different Style
  application orders select the correct winner through the existing cascade
  priority, with authored and resolved provenance retained.
- Shorthand/longhand and token-backed values follow the same alias semantics.
- Negative and overflow values follow each property's existing typed rules.

### Runtime and nested Views

- Axis context defaulting, inheritance, explicit override, nested calls, direct
  child roots, and exported parts are deterministic.
- RichText glyph writing mode is unchanged when only View box axes change, and
  changing RichText direction does not mutate the View box axis.
- Axis revision changes invalidate the exact required nodes/consumers and never
  reuse a stale computed or geometry cache entry.
- Mid-transition axis changes follow the selected snapshot/rebase rule exactly.

### Codec and product integrity

- Canonical program encode/decode round-trips every supported axis context and
  logical property with deterministic bytes/order and source provenance.
- Unknown enum tags, invalid combinations, malformed values, and tampered
  cross-section references fail decode within configured budgets.
- Multi-module merge preserves typed identity without string matching and no
  decoder accepts a discarded shape.

### End-to-end geometry

- Layout bounds, clipping, render transforms, hit regions, focus rings, scroll
  axes, and avoidance geometry agree pixel-for-pixel in every supported axis
  context.
- Deterministic native/headless captures cover at least one asymmetric fixture
  where every start/end mapping can be distinguished.

No test may inspect source-file spellings or file placement as correctness
evidence.

## Expected output

Deliver a self-contained design package with:

- the exact axis enums/newtypes, defaults, inheritance, and source grammar;
- an exhaustive mapping and sign table;
- the logical/physical alias cascade algorithm and computed representation;
- Rust-like AST/HIR/sema/product/runtime APIs and dependency ownership;
- codec schema, validation, canonicalization, merge, and tamper behavior;
- invalidation/cache/transition and nested-View rules;
- diagnostic codes and formatter/LSP contracts;
- a file-by-file implementation plan and complete test matrix;
- explicit non-goals and unsupported contexts.

## Acceptance criteria

The design is ready only when every logical property maps unambiguously in
every supported context, physical/logical conflicts use the existing cascade
order, all geometry consumers share one resolution, RichText remains a separate
owner, codecs and diagnostics are exact, and no implementation decision is left
to guesswork. It must add no CSS/Takumi path, compatibility surface, duplicate
resolver, or source gate, and must preserve d.1-d.3 absent a documented concrete
defect.
