# Request 01.5: Product AWFB Bytecode Migration Implementation Package

## Sequence Position

Submit this after seq-01.4 and seq-01.4.1 are designed and reflected in the
repository.

- seq-01.4 centralizes structured VM / AOT executor construction behind the
  shared runtime facade.
- seq-01.4.1 must define compact AWBC product runtime-step parity with the
  existing `RuntimeStepResult` surface.
- seq-01.5 owns the product container migration: AWFB products stop carrying
  structured `BytecodeProgram` as the executable payload and move to canonical
  AWBC-only executable payloads.

Do not redesign the already implemented and verified seq-01.1 through seq-01.4
substrate unless current repository evidence shows a concrete flaw. If
seq-01.4.1 is still absent or insufficient, state that clearly and either block
this package or include a separate follow-up request rather than silently
inventing product runtime parity inside 01.5.

## Request

Please produce a zip package that can be handed directly to an implementation
agent for seq-01.5 product AWFB bytecode migration.

The zip must include design, concrete implementation patch, overlay files, test
plans, and verification notes. The Rust toolchain is assumed unavailable in
your environment: do not claim `cargo fmt`, `cargo check`, `cargo test`,
`cargo clippy`, `just`, or the structural audit actually passed unless you ran
them. Instead, provide the exact commands the implementation agent must run
after applying the patch.

The package should be named like:

```text
arcweft-seq-01.5-product-awfb-bytecode-migration-YYYY-MM-DD.zip
```

## Required Implementation Cuts

The zip must design and patch the work in small reviewable cuts:

1. Inventory and source gates for all product structured-bytecode paths.
2. AWBC executable section data model and deterministic codec.
3. Builder path that emits AWBC executable payloads and stops silently emitting
   structured executable payloads for new products.
4. Decoder path that accepts AWBC products and rejects or explicitly gates old
   structured-only products with typed diagnostics.
5. Runtime-host/runtime-driver/native-player/CLI product load paths that require
   AWBC for new products and route through the seq-01.4/01.4.1 facade.
6. Fixture corpus for AWBC-only product decode, execution, signing, resource
   identity, and patch/generation identity.
7. Deletion of structured product executable conversions once gates pass.
8. Deletion of old `compact_bytecode` sidecar once no product/runtime path uses
   it.
9. Documentation updates and implementation-state audit.

If any cut requires missing design, split it into `requests/` with sequence
preserving names such as:

```text
requests/2026-06-25-seq-01.5.1-<topic>.md
```

Each split request must be independently throwable and must state why the topic
is excluded from the current implementation patch.

## Tests To Include Or Specify

The implementation patch or overlay must include tests for:

- AWFB decode of AWBC-only products;

  payload;
- explicit rejection or explicitly gated migration of structured-only products;
- malformed AWBC product diagnostics;
- missing AWBC executable payload diagnostics;
- source/display/resource map consistency;
- product signing/hash identity stability with AWBC included;
- patch/generation identity compatibility with AWBC identity;
- runtime smoke for AWBC-only product load through runtime-driver/runtime-host
  and native-player/CLI paths where seq-01.4.1 has provided runtime parity;
- source gates proving no product path depends on structured `BytecodeProgram`
  or old compact sidecars after deletion gates.

## Constraints From AGENTS.md

- Keep lower-level crates independent from higher-level crates.
- Keep `arcweft-core` and data-format crates Sans I/O.
- Do not couple product players to compiler-only crates.
- Prefer typed APIs over stringly typed APIs.
- Add behavior as inherent methods on owned Arcweft boundary types when the
  dependency direction allows it.
- Avoid ad hoc `foo_to_bar` conversion helpers, local extension traits,
  compatibility shims, and broad root re-exports.
- Do not preserve both executable product models as silent compatibility layers.
- Make migration compatibility explicit, documented, tested, and deletion-gated.
- Do not hard-code one-off names when a generic typed rule is required.
- Keep repository structure part of the result; include structural audit
  expectations and file-size/decomposition risks.
- Keep implementation-state notes in `docs/implementation/`; change stable
  design chapters only when the product format specification itself changes.

## Non-Goals

- Redesigning seq-01.1 AWBC lowering, seq-01.2 compact VM, seq-01.3 compiled
  regions, seq-01.4 executor construction facade, or seq-01.4.1 runtime-step

- Adding filesystem, network, signing I/O, or player platform I/O to Sans I/O
  data-format crates.
- Keeping structured product bytecode as an indefinite fallback.
- Claiming Rust validation without actually running the Rust toolchain.
