# Seq-02.9 Request: Release Trust End-to-End Fixtures Package

## Sequence Position

This follows seq02.1 through seq02.8. The production repository already has
compact resource codecs, patch schema 2, AWFR archive models, external payload
carriers, signing policy data, external payload HTTP(S) fetch wiring, release
publish/verify CLI surfaces, and adapter-side materialization mode threading.

Seq02.9 is a hardening slice. It must not redesign the seq02 production
contracts. Its job is to prove the release trust graph end to end with
deterministic fixtures and typed failure evidence.

Do not implement real remote publication in this request. Use local tempdirs,
fixture files, and local HTTP fixture servers only.

## Request

Design and implement end-to-end release trust fixtures that cover detached
signatures, signed base bundles, signed patch artifacts, materialized targets,
external payload cache state, and AWFR release verification.

Return the final work as a zip package with design, Rust implementation overlay,
fixtures, tests, implementation notes, validation notes, and apply instructions.

## Required Decisions

1. The deterministic fixture signing-key policy: where test-only keys live,
   how they are labeled as non-production, and how private key material is kept
   fixture-only.
2. The canonical fixture release graph:
   - signed base AWFB;
   - signed patch schema 2 artifact;
   - external payload descriptors and bytes;
   - materialized target;
   - target signature;
   - final AWFR archive.
3. Which signatures are detached, embedded, or manifest-bound in fixture data.
4. How signing transcripts are compared between publish-side fixture generation
   and consume-side verification.
5. How each `ExternalPayloadMaterializationMode` participates in the matrix:
   `MetadataOnly`, `RequiredResidency`, and `AllPayloads`.
6. How external payload cache states are represented:
   hit, missing, corrupt digest, wrong size, file mirror, HTTP(S) mirror, and
   metadata-only allowed.
7. How `arcw release verify` reports success and failure without duplicating
   policy logic outside the release adapter.
8. Which failure cases are hard trust failures versus recoverable cache or
   materialization misses.

## Required Implementation

Implement an end-to-end fixture suite. The expected fixture matrix includes at
least:

- success: signed base AWFB + signed patch v2 + external payload cache hit +
  materialized target digest match + AWFR signature/manifest match;
- success: metadata-only external payload materialization where the selected
  mode permits it;
- failure: missing base signature where policy requires it;
- failure: missing patch signature where policy requires it;
- failure: patch target identity mismatch;
- failure: materialized target digest mismatch;
- failure: materialized target signature missing where policy requires it;
- failure: external payload digest mismatch;
- failure: external payload missing in required-residency mode;
- failure: AWFR manifest tamper;
- failure: wrong signing policy for the same archive;
- failure: detached signature transcript mismatch.

The implementation must keep `arcweft-bundle` Sans I/O. Filesystem, local HTTP
fixture servers, key loading, and generated fixture files belong in
`arcweft-project-loader`, `arcweft-cli`, tests, or dedicated fixture helpers.

## Acceptance Criteria

- The fixture suite validates the whole local release trust graph, not isolated
  unit codecs only.
- Test-only keys are clearly marked and cannot be mistaken for production
  release credentials.
- Success and failure cases use typed signing, payload, materialization, and
  verifier evidence.
- Local HTTP fixture servers are bounded, deterministic, and test-owned.
- No remote upload backend is introduced by this package.
- No key access, network client, filesystem, or clock behavior is moved into
  `arcweft-bundle`.
- `arcw release verify` can be exercised from fixtures in JSON mode with stable
  machine-readable evidence.
- Existing seq02 source gates against product JSON fallback, codec probing, and
  patch schema compatibility shims remain valid.

## Tests To Specify And Run

```bash
cargo fmt --all -- --check
cargo test -p arcweft-bundle release --all-features
cargo test -p arcweft-project-loader release --all-features
cargo test -p arcweft-project-loader external_payload --all-features
cargo test -p arcweft-cli release --all-features
cargo test -p arcweft-cli cache --all-features
cargo check -p arcweft-bundle -p arcweft-project-loader -p arcweft-cli --all-targets --all-features
cargo clippy -p arcweft-bundle -p arcweft-project-loader -p arcweft-cli --all-targets --all-features -- -D warnings
cargo +nightly -Zscript tools/structure-audit.rs --root .
git diff --check
```

Focused tests must include CLI JSON verification for both a passing release
archive and at least three typed failure classes.

## Non-Goals

- No real remote publication backend.
- No S3, GitHub Releases, registry, CDN, or credential integration.
- No production signing-key management.
- No new signing algorithm policy beyond existing seq02 signing policy.
- No patch schema 1 compatibility reader.
- No product JSON fallback or codec probing.

## Parallelization Guidance

Seq02.9 should be implemented before seq02.10. Seq02.10 may be designed in
parallel if it treats seq02.9 as the trust-fixture dependency and does not
claim remote publication success without consuming the fixture matrix.
