# seq-06.11d.4.2.2.1 — parser recovery payload producer contract correction

## Sequence position

This request follows `seq-06.11d.4.2.2` typed parser error-kind
reconciliation. It is independently throwable. It must not redesign the
closed `ParseErrorKind` registry, the one-way `code()` and `label()`
projections, or the typed parser-to-compiler/LSP/Agent forwarding contract
unless current implementation evidence demonstrates a concrete defect.

## Why this correction is required

The `seq-06.11d.4.2.2` final contract requires one source-derived,
non-`Generic` parser error that simultaneously has:

- a nonempty `expected` list;
- a nonempty `found` value;
- at least one recovery suggestion;
- at least one concrete `RecoveryEdit`.

The pinned production parser does not produce that combination. Specialized
assertion, Style, environment, and View errors preserve their existing
`found = None` payloads. Parser production code also does not call
`RecoverySuggestion::with_edit` or `RecoveryEdit::new`; concrete edits exist
only in tests and shared diagnostic infrastructure.

The same contract separately requires exact preservation of existing
expected/found/recovery behavior and excludes inventing new grammar behavior.
Therefore the cross-adapter fixture cannot satisfy its prescribed payload
without making an additional product decision.

## Required decisions

Choose exactly one final direction:

1. Name an existing specialized parser diagnostic that will begin producing a
   concrete `found` value and `RecoveryEdit`. Specify the exact malformed
   source, byte ranges, replacement, applicability, recovery safety rule, and
   why changing the previously empty payload is correct.
2. Introduce a new current-grammar parser diagnostic for which the full
   payload is semantically justified. Specify its typed kind, stable code and
   label, parser owner, recovery behavior, and interaction with the closed
   registry.
3. Correct `SER-006` so adapter parity is checked against payload that the
   production parser actually emits. Keep concrete edit projection covered by
   owner-level/shared-diagnostic tests, without claiming a source-derived edit
   producer exists.

Do not select a removed spelling merely to manufacture a diagnostic. Do not
add a compatibility recognizer, migration diagnostic, or source gate.

## Implementation order to specify

2. Define the recovery edit safety and applicability policy, if an edit is

3. Update the owning parser and its positive/recovery tests.
