# Request: seq-06.11c final style declaration and component/View DSL package

## Sequence Position

This request sits between the seq06.1 UI/style substrate and the seq06.11
reactive UI authoring/style-resolution package.

Seq06.1 already established the intended authoring direction:

- `pub style name` is the default Arcweft style declaration syntax;
- `pub style name: .Css` is the CSS-flavored style declaration syntax;
- component overrides use `.style {}` and `.style(.Css) {}` as ordered layers;
- `component ... -> View` lowers to retained `UiProgram` data.

Current production code still exposes a transitional top-level `ui style`
syntax and sample path. This request closes that gap before more retained UI
authoring is built on top of the wrong surface.

## Problem

The current implementation has working lower-level UI resource pieces
(`UiStyleResource`, `UiProgramResource`, `UiStyleTable`, retained UI interaction
state, and renderer-side style resolution), but the authoring surface is not yet
the final Arcweft language shape:

- style declarations are currently authored as `ui style @style.foo { ... }`;
- the intended `pub style foo { ... }` declaration is not wired as a typed
  top-level item;
- `component ... -> View` syntax has AST substrate but is not fully parsed,
  lowered, semantically checked, and emitted into product UI resources;
- samples can therefore drift toward resource-side UI declarations instead of
  component/View authoring.

The result is confusing: `style`, `ui style`, UI style resources, and component
View syntax look like separate concepts even though the final language should be
component/View authoring with named style declarations.

## Goal

Design and implement the final style and component/View DSL surface, replacing
the transitional `ui style` authoring syntax in production samples and product
lowering.

The final authoring shape is:

```arcw
pub style primary_button {
    token accent = system(accent)

    Button:hover {
        background = rgba(54, 190, 170, 255)
    }
}

pub style danger_button: .Css {
    Button:hover {
        background-color: rgb(210 64 92);
    }
}

pub component ButtonRow(state: Binding<ButtonState>) -> View {
    Button("Confirm")
        .style(@style:.primary_button)
        .style {
            padding-x = 24
            padding-y = 12
        }
        .on_click {
            state.confirmed = true
        }
}
```

## Required decisions

- Define `style` as the language-level declaration family for UI styles.
- Make `pub style primary_button` the preferred declaration form, normalizing to
  the public id `style.primary_button`.
- In declaration ID contexts, support the existing Arcweft relative ID forms:
  - `pub style primary_button`
  - `pub style @.primary_button`
  - `pub style @style:.primary_button`
- In reference contexts, require a normal entity reference such as
  `@style:.primary_button` or an absolute style reference. Do not treat bare
  `@.primary_button` as a general expression reference outside declaration or
  scoped ID contexts.
- Decide the formatter preference:
  - declaration: `pub style primary_button`;
  - local/scoped style reference: `@style:.primary_button`;
  - absolute/root-level spelling only when the author intentionally needs it.
- Decide whether the CSS-flavored form is inline-only in this cut or also owns
  `from file(...)` / `from embed(...)` declarations. If external CSS is out of
  scope, record it explicitly and reject it with a structured diagnostic.
- Define how `.style(@style:.foo)`, `.style { ... }`, and `.style(.Css) { ... }`
  lower into ordered `UiStyleApply` / product UI style layers.
- Define whether existing `ui text_input` / `ui text_area` / `ui secure_field`
  declarations remain temporarily as text-control resource declarations or move
  into `TextField` / `TextArea` / `SecureField` View elements in this cut.
  Whichever choice is made must be explicit; do not silently mix both authoring
  models in samples.

## Implementation requirements

- Add or rename syntax AST so the user-facing item is `StyleItem` or equivalent,
  not `UiStyleItem` as the public language concept.
- Replace `ui style` parser classification with `style` declaration parsing.
  Removed syntax should fail through structured parser recovery/diagnostics; do
  not keep a hidden compatibility parser branch.
- Wire `style` through HIR lowering, sema checks, project index collection,
  symbol use collection, LSP features, source actions, and product bundle
  lowering.
- Preserve the existing compact `UiStyleResource` codec as the product resource
  format. The language syntax changes; the bundle section kind does not need to
  be renamed in this request.
- Wire `component ... -> View` parsing and lowering through the existing
  `arcweft-lang-syntax::ast::view` model instead of inventing a second view AST.
- Lower component/View authoring into deterministic `UiProgramResource` and
  style applications suitable for seq06.11 retained frame instantiation.
- Update samples that currently use `ui style`, including:
  - `samples/css-style-parity`;
  - `samples/native-text-input`;
  - any reactive UI style sample using resource-side style declarations.
- Update docs/examples that should represent current syntax.
- Add an implementation note under `docs/implementation/` describing the
  grammar replacement, sample migration, and any intentional non-goals.

## Constraints

- Do not introduce a separate `ui surface` grammar or resource-side authoring
  construct. UI authoring should be component/View based.
- Do not add hidden DOM, HTML control, canvas 2D, image-snapshot, browser CSS,
  or CPU-raster fallback behavior.
- Do not preserve `ui style` as a compatibility shim in the production parser.
- Do not redesign seq02.4.1 compact UI resource codecs unless the current codec
  contract is proven insufficient.
- Keep `arcweft-bundle` data/codec-only and Sans I/O.
- Keep renderer/backend/platform-specific behavior out of parser, HIR, sema,
  and bundle crates.

## Tests to specify and implement

- Parser accepts:
  - `pub style primary_button { ... }`;
  - `pub style primary_button: .Css { ... }`;
  - `pub style @.primary_button { ... }`;
  - `pub style @style:.primary_button { ... }`.
- Parser rejects old `ui style` with a structured diagnostic that points at the
  replacement syntax.
- ID normalization tests prove the preferred declaration form produces
  `style.primary_button`.
- Reference tests prove `.style(@style:.primary_button)` resolves to the style
  declaration and that invalid relative references are rejected outside allowed
  contexts.
- Component/View parser tests cover:
  - `Button`, `Text`, `RichText`, `TextField`, `TextArea`, and `SecureField`;
  - `.style(@style:.name)`;
  - `.style { ... }`;
  - `.style(.Css) { ... }`;
  - `.part(name)`;
  - `.on_click { ... }`.
- HIR/sema/project-index tests cover duplicate style IDs, unresolved style
  references, and symbol use collection.
- Bundle tests prove style declarations emit deterministic `UiStyleResource`
  bytes and component/View authoring emits deterministic `UiProgramResource`
  data.
- Sample tests prove migrated samples no longer contain `ui style` and still
  build to product AWFB.

## Non-goals

- Full CSS cascade/layout coverage remains seq06.12.
- Motion/effects coverage remains seq06.13.
- Full player retained UI interaction rendering remains seq06.11 and seq06.11b
  unless this package chooses to include a minimal smoke path.
- Text-submit flow behavior remains seq06.16 unless the package explicitly
  folds it into the component/View migration.
