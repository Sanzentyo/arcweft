# Request 06.4j.1: Cross-Platform Native IME Player-Rendered Sample And Validation Package

## Sequence Position

This follows the applied native/player text-input substrate:

- seq06.3 platform text-input contract integration.
- seq06.4b Windows TSF adapter work.
- seq06.4b.1/06.4b.2 Windows TSF real IME window integration attempts.
- seq06.4c macOS `NSTextInputClient` adapter work.
- seq06.4c.1/06.4c.2 macOS AppKit real IME window integration attempts.
- seq06.4g shared cross-platform editing behavior.
- seq06.4i renderer-backed text-editor geometry.
- seq06.4j native-player platform text-input bridge.
- seq06.4k player text-input/windowed path convergence.
- seq06.4k.1 real text-control schema to `PreparedFrame`.
- seq06.4k.1.1 product/runtime text-control emission.
- seq06.4k.1.2 runtime text-control submit/change write-back.

This request is the native counterpart to seq06.4a.4. It exists because the
current native sample path still does not provide a real, player-rendered
TextField/TextArea/SecureField scene or a cross-platform native text-input host
surface that can be used as final native IME acceptance.

Do not redesign the existing seq06 text-input contracts, runtime text-control
emission, write-back boundary, or renderer geometry unless current evidence
shows a concrete flaw.

## Current Problem

The current native IME story is split across useful but incomplete surfaces:

- `just ime-sample-native` runs an adapter-contract sample, not a real OS IME
  window sample.
- `windows-tsf-ime-sample` is a Windows backend diagnostic harness and can show
  a blank native window or terminal/viewport-anchored IME UI. It is not final
  Arcweft acceptance.
- macOS AppKit helper/sample paths are diagnostic or helper-process oriented,
  not the normal Arcweft native player acceptance path.
- Wayland, Android, and iOS have request-level adapter designs, but the current
  native player sample does not yet expose a shared host surface they can plug
  into without inventing platform-specific acceptance paths.
- `samples/native-text-input/src/main.arcw` is currently a narrative
  placeholder describing planned controls rather than a real player-rendered
  `TextField`, `TextArea`, and `SecureField` sample.
- The newer runtime text-control substrate now exists, so the sample and native
  bridge need to be re-closed against current `main` instead of older
  `focused_text_input_target() == None` assumptions.

The desired acceptance surface is:

```text
arcw run --runner native samples/native-text-input/... --text-input-trace-out target/...
  -> normal scene_windowed / WindowedRuntimeOwner path
  -> Arcweft-rendered TextField/TextArea/SecureField controls
  -> PreparedFrame focused text target
  -> NativeTextInputBridge
  -> platform backend:
       Windows TSF / macOS AppKit / Wayland text-input-v3 /
       Android InputConnection / iOS UITextInput / unavailable capability
  -> PlatformTextInputEvent batch
  -> InputController::text_input
  -> runtime text-control write-back queue
```

## Request

Produce a zip package with concrete design, implementation overlay, tests,
fixtures, and validation notes that makes native IME acceptance run through the
normal Arcweft native player with player-rendered text controls.

The design must be cross-platform first. Windows TSF and macOS AppKit may be
the first real-machine validation targets, but the player-facing API, sample,
trace schema, focus lifecycle, geometry publication, capability model, and
unavailable-backend behavior must be usable by Wayland text-input-v3, Android
InputConnection, and iOS UITextInput without redesigning the native player
surface.

The package must not treat backend diagnostic binaries, blank harness windows,
or synthetic contract samples as final acceptance.

## Required Decisions

1. What should be the canonical native IME sample source and manifest?
   Prefer updating `samples/native-text-input/` over adding another sample
   directory unless the existing name is misleading.
2. How should Arcweft-authored TextField/TextArea/SecureField controls be
   expressed in the sample using the current product/runtime UI resource path?
3. How should focus be acquired in the normal native player: pointer click,
   keyboard traversal, explicit initial focus, or a combination?
4. How should `NativeTextInputBridge` choose a backend:
   - Windows TSF when available;
   - macOS AppKit when available;
   - Wayland text-input-v3 when the native host runs on a Wayland-capable
     backend;
   - Android InputConnection when Arcweft has an Android native host;
   - iOS UITextInput when Arcweft has an iOS native host;
   - explicit unavailable capability elsewhere?
5. What owned enum, trait, or context object represents cross-platform native
   backend capabilities without leaking platform object identity? It should
   cover at least activation, focused snapshot update, geometry update,
   command/event drain, keyboard disposition, blur, secure redaction, and trace
   evidence.
6. How should Windows TSF, macOS AppKit, Wayland, Android, and iOS backends consume
   `PreparedFrame::focused_text_input_target()` geometry without owning
   independent text state?
7. How should candidate/composition rectangles convert from Arcweft renderer
   coordinates into each platform's screen/client coordinate space?
8. How should native trace output distinguish:
   - backend capability reports;
   - selected platform backend kind;
   - unavailable capability and reason;
   - focus activation/deactivation;
   - geometry updates;
   - platform composition/preedit/commit events;
   - routed `TextInput` batches;
   - runtime write-back events;
   - secure redaction?
9. Where should real-machine trace output go by default? Prefer `target/` for
   local runs and reserve checked-in `fixtures/` for reviewed, promoted
   evidence.
10. Which parts of `windows-tsf-ime-sample`, macOS helper samples, and future
    Wayland/Android/iOS harnesses remain useful diagnostics after the player
    sample works, and how should documentation prevent users from treating them
    as final acceptance?
11. How should this package coordinate with seq06.4k.2 if the native windowed
    runtime path is still being migrated?

## Required Implementation

- Replace or extend `samples/native-text-input` with a real Arcweft-rendered
  native IME sample containing:
  - one single-line `TextField`;
  - one multiline `TextArea`;
  - one `SecureField`;
  - deterministic public ids;
  - multiple font/style cases supported by the current renderer;
  - visible labels and focus states rendered by Arcweft;
  - change/submit handler metadata where current runtime write-back supports it.
- Ensure the sample runs through the normal CLI/player path:

  ```bash
  cargo run -p arcweft-cli --features native-player -- run \
    --runner native samples/native-text-input/src/main.arcw \
    --text-input-trace-out target/native-text-input-trace/native-player-ime.real.json
  ```

  The exact path may be refined if the sample manifest becomes the preferred
  entry, but the final command must remain `arcw run --runner native`, not a
  platform-specific binary.

- Connect the native player bridge to platform backends through a typed,
  cross-platform boundary. Do not call TSF/AppKit/Wayland/Android/iOS APIs
  directly from high-level scene logic.
- Add or refine a backend-neutral capability and command/event surface for:
  - backend availability;
  - session activation/deactivation;
  - snapshot update;
  - geometry update;
  - keyboard disposition;
  - platform event drain;
  - blur/composition cancellation;
  - secure redaction;
  - trace evidence.
- Windows:
  - connect the TSF backend to the focused player text target when running on
    Windows;
  - keep COM object identity, HRESULT plumbing, TSF ranges, and sink callbacks
    inside Windows-gated native/desktop modules;
  - use renderer-backed geometry for `ITextStoreACP` layout/candidate rectangle
    queries.
- macOS:
  - connect the AppKit bridge or helper boundary to the focused player text
    target when running on macOS;
  - keep AppKit object identity, `NSRange`, attributed strings, and responder
    details inside macOS-gated native/desktop modules;
  - use renderer-backed geometry for first-rect/candidate placement.
- Wayland:
  - do not require full text-input-v3 completion in this package unless the
    implementation is already ready;
  - provide the same backend boundary and typed unavailable or partial
    capability report so a Wayland backend can attach later without changing
    native player call sites.
- Android:
  - do not require a full Android host in this desktop package;
  - keep `InputConnection` object identity out of shared crates and define the
    player-facing host hooks it will consume.
- iOS:
  - do not require a full iOS host in this desktop package;
  - keep `UITextInput` object identity out of shared crates and define the
    player-facing host hooks it will consume.
- Non-target or unsupported platforms must report typed unavailable capability
  instead of pretending to support real native IME.
- Route all platform text edits through the shared
  `PlatformTextInputEvent`/batch and `InputController::text_input` path.
- Preserve runtime write-back behavior from seq06.4k.1.2 for committed text and
  submit/change events.
- Update `just ime-sample-native` or add a clearly named companion target such
  as `just ime-sample-native-real` if preserving the contract sample remains
  useful. Documentation must state which one is final acceptance.
- Update implementation docs and sample README with exact commands, expected
  behavior, and platform-specific validation gaps.

## Acceptance Criteria

- A normal native Arcweft player window displays player-rendered TextField,
  TextArea, and SecureField controls from the sample.
- Focus can move to a text control by pointer and keyboard traversal.
- On Windows with Microsoft Japanese IME enabled, Japanese preedit and commit
  enter the focused Arcweft text control through the player bridge and shared
  editor path.
- On macOS with Japanese IME enabled, Japanese preedit and commit enter the
  focused Arcweft text control through the same player bridge shape.
- On Wayland, Android, and iOS, the package either provides an implementation
  that consumes the same player bridge or records a typed unavailable/partial
  capability report with the exact backend hook still needed. It must not
  require a different player lifecycle or sample command.
- All native backends share one trace schema and one player-facing lifecycle for
  focus, snapshot, geometry, platform events, routed edits, write-back, blur,
  and secure redaction.
- IME candidate/composition UI is anchored near the Arcweft caret or composition
  range, not at the terminal, viewport origin, or a hidden harness widget.
- Arrow movement, deletion, selected-text replacement, pointer selection,
  shortcut handling, focus loss, and composition cancellation use shared
  cross-platform editor behavior.
- Runtime write-back receives committed change/submit events through the typed
  seq06.4k.1.2 path.
- Secure fields redact text, geometry, selected ranges, traces, capture
  metadata, diagnostics, and Agent-observable values according to the existing
  seq06 contract.
- Backend diagnostic binaries are documented as diagnostics only and are not
  the sample's final acceptance surface.

## Constraints

- Do not use `windows-tsf-ime-sample`, macOS helper samples, blank native
  windows, or synthetic contract batches as final acceptance.
- Do not add compatibility shims or parallel legacy text-input paths.
- Do not fabricate focus targets or platform events when no player-rendered
  text control is focused.
- Do not put platform object identity, COM pointers, AppKit objects, Wayland
  protocol objects, Android `InputConnection` objects, iOS `UITextInput`
  objects, native ranges, or OS event objects into Sans I/O crates.
- Do not write local real-machine traces into checked-in `fixtures/` by default;
  use `target/` unless evidence is intentionally reviewed and promoted.
- Do not mark any platform's real IME acceptance complete without real machine
  validation evidence for that platform.

## Non-Goals

- Browser/Web `EditContext` sample replacement; use seq06.4a.4 for that.
- Full Wayland, Android, and iOS backend completion is allowed only if the
  implementation can be validated cleanly. Otherwise, this package must still
  freeze the cross-platform native player surface they will consume and record
  typed unavailable/partial capability evidence.
- Full rich-document editing beyond TextField/TextArea/SecureField.
- Replacing the native renderer or window owner architecture outside what is
  required to make the normal scene path own text input.

## Parallelization Guidance

This request can be designed in parallel with seq06.4a.4 because Web and native
sample surfaces share the text-input contract but touch different player hosts.

Do not implement blindly in parallel with seq06.4k.2 if both changes touch
`scene_windowed.rs`, `WindowedRuntimeOwner`, native task pumping, or owned-window
driver registration. If seq06.4k.2 is in flight, agree first on the final native
window/runtime owner API, then let this request own text-input focus, backend
activation, and validation.

Windows TSF, macOS AppKit, Wayland, Android, and iOS backend specialists may
work in parallel after this request freezes the native player bridge API and
trace schema. They should not invent platform-specific acceptance commands or
player lifecycles.
