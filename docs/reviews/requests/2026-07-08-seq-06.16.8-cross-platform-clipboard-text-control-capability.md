# Request: Cross-platform clipboard capability for text controls

## Context

Arcweft text controls currently have enough editor-side behavior for in-app
copy, cut, and paste, but OS clipboard integration is not yet designed as a
platform contract.

The current observed behavior is:

- `Ctrl+C`, `Ctrl+X`, and `Ctrl+V` can work inside the running Arcweft player.
- Copied text does not appear in the Windows clipboard history and cannot be
  pasted into other applications.
- External clipboard text is not reliably available to Arcweft text controls
  through normal paste commands.
- Right-click / context-menu text-control affordances can now focus and place
  the caret, but actual menu item presentation and host clipboard-backed menu
  actions are not yet designed as a platform contract.
- Editor selection and cut boundaries can diverge from Unicode grapheme
  cluster behavior; for example, cutting only `U+FF9F HALFWIDTH KATAKANA
  SEMI-VOICED SOUND MARK` out of `Дﾟ` is not acceptable for normal text-control
  semantics.

This suggests the current implementation is still app-local clipboard state,
not a host clipboard bridge. The follow-up design must cover the full boundary
between presentation/editor code and platform clipboard APIs without pushing
OS, browser, or privacy-policy concerns into low-level editor logic.

## Requested Scope

Design the final Arcweft clipboard contract for runtime text controls and
provide an implementation-ready plan. The request should be independently
actionable by an implementation agent.

The design must cover native desktop, web, and Apple-platform privacy behavior,
and it must preserve deterministic editor behavior when host clipboard access is
denied, unavailable, async, or disabled by policy.

## Required Decisions

1. Define the clipboard ownership boundary.
   - Keep editor/presentation crates free of direct OS/browser clipboard APIs.
   - Decide the typed intent/output model for copy, cut, paste, clear, and
     clipboard errors.
   - Decide whether existing `TextEditorClipboard` remains only a fallback
     in-app clipboard, is renamed, or is replaced by a host-facing abstraction.
   - Specify how `TextEditorOutput::ClipboardWrite(...)` or its replacement is
     consumed by native/web host adapters.

2. Define host adapter APIs.
   - Provide a trait or equivalent adapter boundary for clipboard read/write.
   - Keep the adapter async-capable for web while allowing synchronous native
     backends.
   - Specify error categories such as unavailable, denied, unsupported format,
     busy, stale, secure-field-blocked, and internal failure.
   - Specify whether text controls should retry, ignore, surface diagnostics, or
     fall back to app-local clipboard on each error category.
   - Specify how context-menu actions (`Copy`, `Cut`, `Paste`, `Select All`,
     and disabled/secure states) are requested by the player and fulfilled by
     the host adapter without putting menu UI policy into the editor core.

3. Define platform-specific behavior.
   - Windows: account for the global clipboard object and avoid parallel access
     patterns that can fail or deadlock.
   - Linux: account for X11/Wayland ownership/lifetime differences and decide
     whether the chosen crate is sufficient.
   - macOS: account for current and upcoming pasteboard privacy alerts, user
     initiated paste exceptions, and pasteboard access behavior.
   - iOS/iPadOS: account for pasteboard read prompts and user-intent
     requirements.
   - Web: use Clipboard API when available, including secure-context and
     permission failures, and specify fallback behavior for copy/cut/paste
     events when direct `navigator.clipboard` access is unavailable.

4. Decide dependency strategy.
   - Evaluate `arboard` for native desktop text clipboard support.
   - State whether platform-specific adapters are still required around
     `arboard`.
   - State whether web needs a separate wasm/browser adapter instead of sharing
     the native crate.
   - Include the reason if another crate or direct platform API is preferred.

5. Define permission and capability policy.
   - Decide Arcweft capability names, for example `clipboard.read` and
     `clipboard.write`.
   - Distinguish user-initiated copy/cut/paste from background/programmatic
     clipboard access.
   - Define default policy in `arcweft.toml` or runtime config.
   - Define how DSL/runtime requests can ask for additional clipboard
     capability without silently escalating privileges.
   - Explicitly forbid polling or background clipboard reads unless a future
     request designs that capability.

6. Define secure text-field behavior.
   - Password/secret fields must not copy, cut, expose selection text in traces,
     or write to host clipboard unless a separate explicit design allows it.
   - Paste into secure fields should be policy-controlled and should not log
     pasted content.
   - Diagnostics should reveal policy category, not secret text.

7. Unify text selection units with clipboard operations.
   - Copy, cut, delete, selection expansion, and paste replacement must use the
     same editor text-index model.
   - Grapheme clusters must be honored consistently across caret movement,
     selection, delete, and cut.
   - Include tests for `Дﾟ`, `( ﾟДﾟ)`, kana combining marks, emoji modifiers,
     variation selectors, CRLF, multiline selection, and masked text.
   - The design must prevent cutting only `U+FF9F` from `Дﾟ` in normal
     grapheme-mode text controls.

8. Define data formats and future extension boundaries.
   - Plain UTF-8 text is required for this request.
   - Decide whether rich text, HTML, images, file lists, and custom MIME data
     are explicit non-goals or future extension points.
   - Define newline normalization rules for Windows, web, and internal text
     state.

9. Define observable diagnostics and tracing.
   - Add structured trace events for clipboard requests and outcomes.
   - Do not log clipboard payload text by default.
   - Include enough metadata to debug platform denial, missing permission,
     unavailable adapter, and secure-field blocking.

10. Define tests and validation.
    - Unit tests for editor copy/cut/paste behavior and grapheme boundaries.
    - Host-adapter tests with fake clipboard providers.
    - Native smoke tests for Windows clipboard round trip where available.
    - Web tests for async success and denied/unavailable paths.
    - Regression tests proving copied text can leave Arcweft through the host
      clipboard and external clipboard text can enter Arcweft through paste.
    - Context-menu tests proving right-click menu commands use the same
      clipboard capability boundary as keyboard shortcuts and platform
      clipboard events.
    - Negative tests for secure-field copy/cut and denied permissions.

## Implementation Order To Specify

The design should propose an implementation order similar to:

1. Introduce the typed clipboard adapter boundary and fake provider tests.
2. Route editor clipboard write/read intents through the adapter without
   changing the visible text-control behavior.
3. Add native desktop adapter support, preferably behind the native player
   crate boundary.
4. Add web adapter support with async permission/error mapping.
5. Add permission policy integration and diagnostics.
6. Add secure-field policy enforcement.
7. Unify grapheme-boundary selection/cut behavior and add regression tests.
8. Add native/web smoke validation and documentation.

## Constraints

- Do not add OS, browser, or Apple pasteboard APIs to low-level editor,
  presentation, text-layout, or core crates.
- Do not introduce compatibility shims for old clipboard behavior.
- Do not silently read clipboard contents outside a user-initiated paste or an
  explicitly granted future capability.
- Do not leak clipboard payload text into logs, traces, diagnostics, snapshots,
  or panic messages.
- Do not treat app-local clipboard fallback as equivalent to host clipboard
  integration.
- Do not redesign unrelated text input, IME, or rendering systems unless
  concrete evidence shows they are required for clipboard correctness.

## Expected Output

Return a zip or patch set containing:

- A detailed design document.
- Proposed Rust module/crate ownership.
- Proposed typed APIs and error types.
- Platform behavior matrix for Windows, Linux, macOS, iOS/iPadOS, and web.
- Permission/capability policy proposal.
- Test plan with concrete fixture strings and expected outcomes.
- Implementation notes listing non-goals and follow-up requests, if any.
