# Request: seq-06.10 cross-backend text raster parity package

## Sequence position

Seq06.10 follows the CSS-style parity scale repair recorded in
`docs/implementation/2026-06-30-css-style-parity-startup-scale-profile.md`.

The viewport scale contract, `RenderViewport::scale_factor`, native offscreen
capture path, web player capture path, and `css-style-parity.awfb` sample should
be treated as already implemented substrate. Do not redesign them unless the
package demonstrates a concrete flaw with current evidence.

## Why this split exists

Default, compact, and HiDPI CSS-style parity captures now line up geometrically,
but native/web image metrics remain lower than ideal because text antialiasing,
font fallback, subpixel positioning, and glyph raster behavior differ between
the native offscreen capture and browser WebGPU capture.

This request is not about layout scale. It is about whether Arcweft wants a
stricter text-raster parity contract and, if so, how to make it measurable and
production-safe.

## Required decisions

- Define the expected parity level for renderer-owned text across native and
  web:
  - exact pixel identity;
  - bounded perceptual similarity;
  - text-mask/layout identity with backend-specific antialias allowance.
- Decide whether parity should compare full PNG metrics only or include
  text-aware evidence such as glyph bounding boxes, text masks, or per-run
  raster metadata.
- Decide how font loading should be pinned for CSS-style parity:
  - checked-in font bytes;
  - fixture-local font catalog;
  - platform font fallback explicitly recorded as non-deterministic.
- Decide whether subpixel text positions should be snapped, preserved, or
  reported as typed raster evidence.
- Define threshold ownership for `tools/verify-webgpu-parity.rs`, `imq`
  reports, and future text-specific golden checks.

## Implementation requirements

- Produce a zip package with docs, patches or overlay files, tests, and
  validation notes, matching prior Arcweft sequence package style.
- Preserve the existing native/web shared renderer path.
- Do not introduce hidden DOM text rendering, canvas-overlay text rendering, or
  browser-only styling paths.
- Do not loosen CSS-style parity thresholds without replacing them with a
  stronger explanation or a text-specific evidence mechanism.
- Keep renderer/data crates Sans I/O. File reads, screenshots, and browser
  capture must remain in tools, tests, or adapter layers.
- Keep metrics deterministic enough to run locally on Windows and in a disabled
  CI design if the environment lacks stable WebGPU/font behavior.

## Suggested implementation order

1. Inspect current default/compact/HiDPI native and web PNGs plus `imq` reports.
2. Add or design a text-specific evidence extractor for prepared frames and/or
   captured PNGs.
3. Pin font inputs used by CSS-style parity capture and document fallback
   behavior.
4. Update `tools/verify-webgpu-parity.rs` or add a companion tool only if the
   existing full-image metric cannot express text parity safely.
5. Extend `just css-style-parity` validation without hiding real drift.
6. Record the final thresholds, platform caveats, and promotion workflow.

## Tests and validation to specify

- `just css-style-parity`
- `just css-style-parity-profile`
- Focused renderer text/glyph layout tests, if new public behavior is added.
- Native/web default, compact, and HiDPI capture comparison with JSON evidence.
- `cargo check` / `cargo clippy` for touched crates and tools.
- Structural audit when a crate boundary, public contract, or large renderer
  responsibility changes.
