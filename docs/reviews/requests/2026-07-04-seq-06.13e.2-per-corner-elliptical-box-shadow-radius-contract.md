# Request: seq-06.13e.2 per-corner elliptical box-shadow radius contract

> **Superseded (2026-07-13):** Arcweft Style is now native-only. The CSS authoring and Takumi product-path premises in this request were removed; see [Native-only typed Style path](../../implementation/native-only-style-path-2026-07-13.md). Do not use this request to reintroduce or reimplement CSS/Takumi Style behavior.

## Sequence Position

Seq06.13e.2 follows the applied seq06.13d CSS box-shadow lowering package and
seq06.13e CSS inset box-shadow rendering package.

Seq06.13d and seq06.13e deliberately preserve the existing scalar box-shadow
radius contract. This request defines the separate renderer contract for
per-corner and elliptical radii.

This request must not redesign already implemented outer or inset shadow
support unless current implementation evidence shows a concrete flaw.

## Why This Split Exists

Takumi exposes border radii as four possibly elliptical corners, but the current
Arcweft-owned shadow renderer contract carries a scalar radius. Seq06.13d and
seq06.13e therefore use deterministic scalar selection and explicitly keep
exact per-corner / elliptical radius parity out of scope.

Per-corner and elliptical radii affect data contracts, planning, shader math,
diagnostics, CSS lowering, and visual evidence together, so they need their own
design package rather than being folded into PNG golden promotion or inset
shadow rendering.

## Goal

Design and implement an Arcweft-owned per-corner / elliptical radius contract
for outer and inset box shadows, end to end from typed CSS lowering through
renderer planning and visual tests.

## Required Decisions

- Define the public renderer data model:
  - whether `ViewBoxShadow` gains a corner-radius struct;
  - whether the existing scalar radius remains as a convenience constructor;
  - whether outer and inset shadows share one radius contract.
- Define how Takumi's computed corner radii lower into Arcweft-owned typed data.
- Define canonicalization rules for zero, negative, non-finite, oversized,
  mixed, and elliptical radii.
- Define shader math for per-corner circular and elliptical rounded boxes,
  including spread and blur interaction.
- Define compatibility and migration behavior for existing scalar-radius tests
  without adding compatibility shims or broad root re-exports.
- Define diagnostics for unsupported radius forms if the package intentionally
  implements only a subset.
- Define visual evidence requirements and whether exact PNG promotion remains a
  separate pinned-environment task.

## Implementation Order

1. Audit the existing seq06.13b-06.13e shadow data model, planner, WGSL, and
   Takumi lowering path.
2. Introduce the minimal typed radius model at the owning renderer/resource
   boundary.
3. Update Takumi adapter lowering to pass typed per-corner / elliptical radii
   without source-string parsing.
4. Update outer and inset shadow planning to preserve the authored radius
   contract.
5. Update WGSL/uniforms and compositor pass encoding.
6. Update existing scalar-radius tests and add new per-corner / elliptical
   success and diagnostic tests.
7. Update support matrices and implementation notes.

## Tests To Specify And Implement

- CSS with four different corner radii lowers into the typed shadow radius
  contract.
- CSS elliptical radii lower deterministically without collapsing to a scalar
  unless the design explicitly decides to diagnose them.
- Outer shadow planning preserves per-corner radii.
- Inset shadow planning preserves per-corner radii.
- Spread and blur remain deterministic for mixed corner radii.
- Non-finite and degenerate radius values emit typed diagnostics.
- Existing scalar-radius outer and inset tests remain valid.
- GPU smoke fixture covers at least one mixed-corner outer shadow and one
  elliptical inset shadow.

## Constraints

- Do not parse production CSS through ad hoc string scanning.
- Do not add DOM, browser CSS, SVG filter, canvas, bitmap, or CPU raster
  fallback paths.
- Do not silently drop unsupported non-empty shadows.
- Do not redesign text, clip, mask, blend, or unrelated compositor contracts.
- Do not claim exact visual parity until the required renderer tests and visual
  evidence pass.
- Do not make exact native/web PNG promotion part of this request unless it is
  run in the pinned visual-golden environment.
