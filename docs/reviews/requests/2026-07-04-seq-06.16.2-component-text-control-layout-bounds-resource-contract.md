# Request: seq-06.16.2 component text-control layout-bounds resource contract

## Sequence Position

Seq06.16.2 follows:

- seq06.16 player-rendered text submit button substrate;
- seq06.16.1 component/View text submit button lowering;
- the applied component text-input unification cut documented in
  `docs/implementation/component-text-input-unification-2026-07-04.md`.

The previous cut intentionally did not add a new layout-bounds resource
contract. Runtime text-control bounds still use the existing stacked/default
resource behavior. This request closes that remaining contract gap.

## Why This Split Exists

Component/View text controls now generate canonical `UiInputResource`,
`UiTextResource`, semantic target, action button, sema, and project-index data
without top-level `ui text_input` declarations. Layout bounds are a separate
resource/runtime/presentation contract and should not be smuggled in through
ad hoc defaults or sample-specific geometry.

## Goal

Design and implement typed layout-bounds data for component-authored
`TextField`, `TextArea`, and `SecureField` controls, so runtime/player text
controls receive deterministic bounds from the component/View lowering path
rather than the existing stacked/default fallback.

## Required Decisions

- Decide where authored bounds live:
  - component/View props;
  - View layout modifiers;
  - `UiInputResource`;
  - `UiProgramResource` semantic target metadata;
  - or a dedicated UI layout/bounds resource table.
- Define the typed bounds model:
  - logical rect, min/max/intrinsic size, flow layout slot, or resolved layout
    output;
  - units and coordinate space;
  - device-pixel conversion responsibility;
  - relationship to semantic target bounds and hit bounds.
- Define how TextField/TextArea/SecureField defaults behave when bounds are not
  authored.
- Define how bounds interact with root `style`, layout containers, focus rings,
  text selection/caret geometry, and action button activation.
- Decide validation behavior for invalid, non-finite, negative, overlapping, or
  missing bounds.
- Decide whether existing runtime `UiRuntimeTextControlBounds` remains the
  public runtime shape or is replaced by a more explicit layout contract.

## Implementation Order

1. Audit current component/View text-control lowering and runtime
   `UiRuntimeTextControlBounds` consumers.
2. Define the smallest typed contract that preserves existing successful
   samples while replacing the stacked/default fallback where component bounds
   are available.
3. Wire parser/AST/lowering only if new authoring syntax is needed; otherwise
   derive bounds from existing layout data.
4. Update bundle resource codecs and runtime snapshot conversion.
5. Update player-scene/render lowering to use the new contract.
6. Add tests and update implementation notes/support docs.

## Tests To Specify And Implement

- Component-only TextField emits deterministic runtime bounds.
- TextArea and SecureField emit deterministic runtime bounds.
- Bounds survive compact UI resource round-trip and canonicalization.
- Semantic target bounds and text-control bounds agree where the contract says
  they should.
- Missing bounds use the documented default without top-level input
  declarations.
- Invalid/non-finite bounds emit structured diagnostics.
- Existing component text submit and button activation tests still pass.
- Native sample bundle output no longer relies on stacked/default text-control
  placement for controls whose component layout is known.

## Constraints

- Do not restore top-level `ui text_input`, `ui text_area`, or
  `ui secure_field` compatibility declarations.
- Do not introduce platform-widget, DOM, CSS screenshot, or source-string
  fallback behavior.
- Do not redesign seq06.16/seq06.16.1 action button or submit substrate unless
  implementation evidence shows a concrete flaw.
- Keep low-level resource/data crates Sans I/O.
- Keep the contract typed and deterministic.
