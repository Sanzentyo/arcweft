# Request seq06.4k.1.2: Runtime Text Control Submit/Change Write-Back Package

## Sequence Position

This follows seq06.4k.1.1, which emits authored/product runtime text controls
into the shared renderer/player text-input path and reflects player-owned live
edits in the next frame.

Do not redesign the seq06.4k / seq06.4k.1 / seq06.4k.1.1 renderer-player
boundary unless current implementation evidence shows a concrete flaw.

## Problem

Seq06.4k.1.1 intentionally stops at frame-local live editing. The next missing
piece is a typed boundary for submitting or changing text-control values back to
runtime/product state. Without that, text fields can edit visually, but authored
flows cannot observe committed form values through a stable runtime contract.

## Required Output

Produce a zip package with:

- concrete design markdown;
- Rust overlay or patches;
- tests and implementation documentation;
- implementation note;
- validation instructions and any blocked platform validation.

The package must be independently applicable to current `main` after
seq06.4k.1.1.

## Required Design Decisions

1. Which runtime owner receives committed text-control changes:
   `BundleSession`, a presentation/input command queue, line-task requests, or a
   dedicated text-control event channel.
2. Which authored declarations represent submit/change handlers and how they map
   to runtime IDs without stringly payloads.
3. Whether write-back updates a runtime binding, a UI resource state overlay, or
   emits typed events consumed by AWBC.
4. How IME composition differs from committed text for change/submit purposes.
5. How secure fields avoid leaking values into diagnostics, traces, Agent
   observation, capture metadata, and replay.
6. How native and Web keep the same write-back path without platform-specific
   branches.
7. How hot-swap handles pending live edits and submitted values.

## Implementation Requirements

- Preserve `RenderScene::text_inputs` and
  `PreparedFrame::focused_text_input_target()` as the only renderer/player text
  input geometry and IME activation path.
- Do not add hidden DOM textarea/contenteditable fallback.
- Do not add sample-owned sessions or platform-specific submit paths.
- Do not use JSON/stringly ad hoc payloads for text-control values.
- Prefer owned typed APIs and inherent methods on Arcweft-owned boundary types.
- Keep data-format/core crates Sans I/O.
- Add repository-visible implementation notes for any intentionally deferred
  runtime handler behavior.

## Tests To Specify And Implement

- Commit/change event from `InputController` reaches the runtime owner as typed
  data.
- Submit event is distinguishable from ordinary change.
- Runtime-visible value persists across the next frame without bypassing the
  live editor overlay.
- Secure field values are redacted from traces/diagnostics/capture metadata
  unless an explicit approved secure channel exists.
- Native and Web scene builders use the same write-back entrypoint.
- Hot-swap behavior for live text values is deterministic and tested.
- Implementation notes and focused tests cover hidden platform submit handlers
  and stringly value payload risks without relying on brittle source spelling
  scans.

## Acceptance Criteria

- A normal Arcweft product text field can be edited and submitted through native
  and Web player paths.
- Runtime/AWBC-facing logic can observe the submitted value through a typed
  contract.
- The implementation remains platform-independent above the text-input adapter
  layer.
- Secure text controls preserve redaction guarantees.
