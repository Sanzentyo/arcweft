## Sequence position and split rationale

AW-AH-009.4.2 first supplies one exact source-backed dialogue-content
application in the typed HIR expression/body model. This request consumes that
site and decides how it becomes an accepted project line identity.

The following topics are intentionally one request:

```text
typed source owner
  -> explicit/generated line-ID candidate
  -> project-wide collision transaction
  -> accepted line/text-key identity
  -> primary/secondary diagnostic evidence
```

They cannot be safely split because changing owner qualification changes the
generated ID, which changes collision keys, accepted output, diagnostic
identity, cache invalidation, and rename behavior. Runtime wire encoding and
dialogue View projection remain later consumers and are not redesigned here.

## Frozen semantic results from AW-AH-009.4

The following source-visible results are fixed and must not be redesigned:

### Flow owner example

For flow `flow.game.intro`, named scopes `scene`, `greeting`, and the second
generated application under that prefix:

```text
say.flow.game.intro.scene.greeting.002
```

### Callable owner example

For package `game`, canonical module `game.dialogue`, function `phone_line`,
named scope `retry`, and the first generated application:

```text
say.fn.game.game.dialogue.function.phone_line.retry.001
```

Every typed nested callable-owner path segment appears between owner family
and callable name.

### Explicit IDs

```arcw
id = @.greeting
id = @say:.greeting
id = @say.opening.greeting
```

- relative and family-relative forms resolve under the exact flow/callable
  source-owner prefix;
- `@super` removes one named scope and cannot traverse above the source owner;
- absolute IDs are validated as `@say.*`;
- explicit text keys are validated as `@text.*`.

### Generation and collision

- generated ordinals count generated content applications only within one
  exact prefix, in accepted source order;
- ordinals are decimal, padded to at least three digits, and continue above
  999;
- explicit and generated IDs share one project-wide namespace;
- any duplicate rejects the accepted project;
- a generated candidate never silently skips an occupied value;
- absent text key derives `text.` plus the complete line-ID body after
  `say.`;
- no character, alias, callee label, display name, `.say` spelling, or source
  spelling contributes to identity;
- character rename cannot alter a generated or explicit line ID;
- line rename is independent of character rename;
- a content application outside a typed flow or callable owner requires an
  absolute `@say.*` ID.

The request selects implementation ownership for these rules; it does not
change the rules.

## Production contradictions to resolve

### Package/module identity is available at different stages

Current accepted-project production and AW-AH-009.3.2 first supply package
identity when constructing:

```rust
HirProject::new(package, modules)
```

Proof-concurrency v6.1.1 instead specifies:

```rust
HirModuleKey {
    package: CallablePackageId,
    path: CanonicalModulePath,
    document: SourceDocumentId,
}
```

and a package-aware `LoweringRequest`. AW-AH-009.4 does not decide whether
line-ID materialization occurs during module lowering, project assembly, or a
two-stage candidate/acceptance process. It also does not define migration order
between these accepted models.

### No exact project collision owner or output

AW-AH-009.4 requires one transactional project-wide inventory, two source
labels, and no accepted project on collision. It does not define:

- candidate and accepted record types;
- inventory/context owner;
- method signatures;
- deterministic insertion order;
- rollback boundary;
- returned accepted facts;
- relationship to `HirProject`, project symbols, sema, and accepted snapshots;
- cache/invalidation keys.

### HIR error shape cannot carry the contract

Current `HirLowerError` has a message and at most one `TextRange`, with a
generic lowering diagnostic code. It cannot directly express AW-CD-013,
AW-CD-020, two revision-bound source labels in different documents, or
structured diagnostic identity.

The repository has reusable `arcweft_source::Diagnostic`,
`DiagnosticLabel`, `SourceSpan`, and subsystem primary/secondary diagnostic
patterns. Proof-concurrency specifies diagnostic ordering and source-backed
HIR identity but refers to `HirDiagnostic` without freezing its exact Rust
shape. The final owner and projection path remain undecided.

## Required decisions

### 1. Exact typed source-owner model

Define the exact owned types for flow and callable line sites. At minimum the
model must carry or reference:

- owning package;
- canonical module;
- revision-bound source document;
- source-backed application `ExprId` or the exact owner selected by
  AW-AH-009.4.2;
- complete flow ID or callable declaration identity;
- callable owner family and typed nested owner path;
- callable name;
- ordered named lexical scopes;
- exact application and explicit-coordinate `SourceSpan`s;
- accepted source-order ordinal input.

Specify private fields, constructors, accessors, derives, visibility,
session-only versus persistent identity, and whether each fact is stored or
projected from existing HIR/project records.

Do not encode owner family/path as an unchecked dotted display string when an
existing typed owner is available.

### 2. Candidate construction and explicit-ID resolution

Define exact types and checked context APIs for:

- generated line-ID candidates;
- explicit absolute IDs;
- explicit relative IDs;
- family-relative IDs;
- named-scope parent traversal;
- explicit text keys;
- derived text keys;
- ownerless absolute-ID sites.

Specify:

- which stage validates the `say`/`text` family;
- whether a failed candidate consumes an ordinal;
- how ordinal 1,000 and greater format;
- normalization and length checks;
- behavior at root scope and attempted traversal above owner;
- wrong-family, malformed, dynamic-expression, missing-owner, overflow, and
  limit failures;
- whether candidate construction is module-local and how its output remains
  source ordered.

Use inherent methods on the owning ID or a dedicated named builder/context.
Do not add scattered `{source}_to_{target}` helpers or re-parse source text.

### 3. Package-aware lowering versus project acceptance

Reconcile proof-concurrency v6.1.1 and AW-AH-009.3.2 explicitly. Select one
final staged architecture, including exact APIs, for:

```text
module lowering
  -> line candidate inventory
  -> HirProject assembly
  -> project-wide line acceptance
  -> accepted HIR/sema publication
```

Decide:

- whether package/module qualification is finalized during lowering or
  project assembly;
- how current `lower_to_hir` callers migrate to package-aware requests;
- which object owns unaccepted candidates;
- which object owns accepted line identities;
- whether `HirProject` construction itself performs collision acceptance or a
  dedicated checked project builder does so;
- how an accepted project exposes line identity/source facts to sema,
  tooling, rename, runtime-plan, and tests;
- how declaration-free modules and dependency modules participate;
- what happens to recovered/non-executable HIR modules;
- how no-op and changed HIR revisions invalidate the inventory.

No caller may construct a second HIR project or publish line facts separately
from the accepted project generation.

### 4. Transactional project collision inventory

Define one exact inventory/builder with:

- bounded input records;
- deterministic module and source-site traversal order;
- one namespace for explicit and generated IDs;
- source spans for every candidate;
- temporary insertion state;
- collision detection before publication;
- atomic rollback;
- accepted immutable output;
- stable ordering and deduplication.

Clarify:

- which of two colliding sites is primary and which is secondary, or the
  deterministic rule for selecting them;
- collision between two explicit IDs;
- collision between explicit and generated IDs in either source order;
- collision between two generated IDs;
- collisions across modules/source documents;
- duplicate candidates from recovered HIR;
- whether one failure suppresses later independent diagnostics;
- diagnostic and work-budget exhaustion behavior;
- why a generated counter never skips an occupied candidate.

A failed transaction must not reserve an ID, increment an accepted revision,
mutate the current accepted project, or alter the next valid candidate.

### 5. Exact diagnostics and source labels

Define exact diagnostic owners, Rust enums/records, constructors, accessors,
stable codes, labels, ordering, deduplication, and projection for at least:

```text
AW-CD-013 InvalidLineIdFamily
AW-CD-020 LineIdCollision
ownerless relative/generated ID
relative traversal above owner
dynamic/non-IdRef id or text_key coordinate
invalid text-key family
candidate/work/diagnostic limit failure
source identity or revision mismatch
```

For AW-CD-020, retain the exact ID and both revision-bound source spans. State
whether the later site is primary, how cross-document related information is
rendered, and how deterministic ordering works.

Decide whether each failure belongs to:

- module HIR lowering diagnostics;
- project construction errors;
- accepted project diagnostics;
- sema diagnostics;
- fatal typed construction failure.

Replace or bypass current single-range `HirLowerError` directly where required.
Do not wrap it with a string-only compatibility diagnostic. Reuse
`arcweft_source::Diagnostic` for final rendering rather than inventing a
second transport format, while keeping domain-specific structured identity in
its owning layer.

### 6. Text-key acceptance

Define exact typed derivation and validation:

```text
say.<complete-body> -> text.<complete-body>
```

Specify:

- the owned input/output types;
- explicit versus derived provenance;
- family and byte-length validation;
- collision behavior, if text-key uniqueness is separately constrained;
- source range for an explicit key and source-site evidence for a derived key;
- rename behavior;
- accepted fact exposure to localization/runtime-plan/tooling;
- whether a line collision prevents text-key publication.

No segment may be interpreted as CharacterId.

### 7. Limits, ordering, and invalidation

Freeze:

- maximum line candidates per module and project;
- maximum line/text-key bytes using existing AW-AH-009.4 limits;
- maximum named scopes and parent traversal;
- maximum diagnostics and related labels;
- maximum collision work;
- checked arithmetic requirements;
- deterministic sort keys;
- cache keys and invalidation on module/source/project revision;
- behavior for stale source spans or accepted-project generations.

Reuse existing production budgets where they already govern the same work.
Do not add an unbounded project scan or user-configurable identity budget.

### 8. Public and crate boundary

State which APIs are:

- public HIR/project inspection;
- public accepted semantic facts;
- crate-private staged builders;
- compiler/LSP diagnostic projection;
- runtime-plan input;
- non-Serde session identity;
- persisted public line/text-key identity.

Avoid broad root re-exports and duplicate public carriers. Prefer one
responsibility module and inherent/context methods.

### 9. Direct migration and cut correction

Inventory and order the removal of:

```text
DialogueSpeakerSlug
speaker-derived generated prefixes
.say stripping
callee-display/source-spelling identity
character-name-derived line IDs
post-lowering source scans
module-local silent collision skipping
single-range/string-only errors used for line identity
parallel line inventories outside the accepted project
```

Correct the AW-AH-009.4 implementation handoff so public syntax/HIR deletion
through sema/runtime/tooling migration is one direct replacement with no
reviewable push point that leaves the workspace uncompilable.

## Required implementation order

The returned contract must specify compiling/package-frontier cuts in this
order:

1. Implement AW-AH-009.4.2 and prove one exact typed application/source owner.
2. Introduce final private staged candidate and diagnostic types against the
   existing typed package/module/source owners.
3. Make module lowering package-aware according to the selected
   proof-concurrency/accepted-project reconciliation.
4. Produce bounded module-local candidates without accepting or publishing
   them.
5. Add one transactional project collision/acceptance builder and immutable
   accepted output.
6. Switch `HirProject`, accepted project publication, sema, source index,
   rename, runtime-plan, compiler, LSP, and tooling consumers atomically.
7. Delete speaker/string identity, old helpers, parallel inventories, and old
   error projections.
8. Run focused tests, workspace check/Clippy/tests, Tier 2 when the accepted
   Agent/MCP/runtime path is affected, and the canonical structural audit.

The handoff must use the AW-AH-009.3.1 direct-replacement model: independently
mergeable substrate may land first; the public replacement series is committed
or merged only when the workspace again has one compiling model.

## Mandatory direct tests

Define exact named tests for at least:

### Owner and generation

- the frozen flow example produces
  `say.flow.game.intro.scene.greeting.002`;
- the frozen callable example produces
  `say.fn.game.game.dialogue.function.phone_line.retry.001`;
- nested callable owner paths retain every typed segment;
- generated ordinals 1, 2, 999, 1,000, and a configured maximum format
  correctly;
- counters are independent per exact prefix;
- explicit applications do not consume generated ordinals;
- failed/recovered candidates do not mutate accepted counters;
- character, alias, local variable, callee label, display-name, and source
  spelling changes do not alter generated IDs.

### Explicit and relative IDs

- `@.greeting` and `@say:.greeting` resolve to the same owner-relative ID;
- `@super` removes one named scope;
- repeated parent traversal follows the selected exact syntax;
- traversal cannot escape the flow/callable owner;
- valid absolute `@say.*` is preserved exactly;
- wrong-family absolute and family-relative IDs produce AW-CD-013 at the
  authored ID span;
- ownerless relative/generated application is rejected while ownerless
  absolute `@say.*` succeeds;
- dynamic expressions are not re-parsed as IDs.

### Collision transaction

- duplicate explicit IDs produce AW-CD-020 with both exact spans;
- explicit/generated collisions work in both source orders;
- two generated sites that produce one candidate collide rather than skip;
- cross-module and cross-document collisions retain both source identities;
- one failed project build leaves the previous accepted project and next valid
  build unchanged;
- deterministic module input permutations produce byte/equality-identical
  accepted inventories and diagnostics;
- recovered/non-executable modules follow the selected publication rule;
- diagnostic/work-limit failure is atomic.

### Text keys and rename

- absent text key derives `text.` plus the complete line-ID body;
- explicit valid `@text.*` is retained;
- wrong-family and oversized keys reject with exact source evidence;
- line collision publishes no derived text key;
- character rename does not alter line or text key;
- line rename updates the independent line-reference inventory according to
  the selected contract;
- no consumer parses a line ID to recover CharacterId.

### Accepted lifecycle and diagnostics

- package/module/document identity comes from the selected existing typed
  owner, never display strings;
- source revision mismatch cannot publish candidates;
- no-op HIR/project rebuild reuses the selected accepted identity and cache;
- changed source invalidates exactly the affected module/project facts;
- accepted HIR lookup, sema, LSP, Agent/tooling query, and runtime-plan consume
  the same accepted project generation;
- AW-CD-020 projects primary and secondary labels through
  `arcweft_source::Diagnostic`, including cross-document related information;
- diagnostic ordering and deduplication are deterministic;
- current single-range `HirLowerError` is not used to erase structured
  identity or a related span.

Use typed behavior, negative, transactional, source-revision, and projection
tests. Do not use repository source scans or file-placement assertions.
