# Request 01.3: Full-Script Compiled Region Lowering

## Sequence Position

Submit this after compact VM semantics and parity testing have been designed.
It may be implemented after the compact VM is available behind test/dev
selection.

## Request

Please design baseline full-script compiled-region lowering over AWBC.

The executable-runtime-core overlay implements the shared safe Rust
`CompiledRegion` ABI, artifact/cache identity, dispatcher-owned budget, and
transactional zero-budget VM fallback substrate. This request covers the missing
design for turning verified AWBC into whole-script executable regions and
selecting them safely.

## Why This Needs A Separate Design Cut

Request 01 asked for a baseline full-script AOT/JIT ABI. The overlay provides
the ABI substrate but not a concrete region-lowering pipeline or backend plan.
The design still needs enough detail to implement a first baseline backend
without optimizing codegen.

## Required Design Decisions

Please provide concrete answers for:

1. What is the boundary between AWBC verification, compiled-region eligibility,
   backend lowering, artifact creation, and dispatch?
2. What region granularity is required for the first implementation: whole
   script, entrypoint, function, block group, or another unit?
3. Which AWBC opcodes and host-boundary operations are eligible for compiled
   execution in the first baseline backend?
4. Which opcodes force region rejection, safe return, or zero-budget VM
   fallback?
5. What does the first backend produce: an interpreter-like compiled closure,
   generated Rust, Cranelift IR, or another artifact?
6. How are safe points, resume points, frame layouts, traps, source maps, and
   host exits represented inside generated regions?
7. How are `CompiledStepExit` variants validated and mapped back into
   `FiberState`?
8. How are cache keys, generation dispatch keys, artifact metadata, and policy
   decisions connected to actual region selection?
9. How does the baseline backend avoid duplicating compact VM semantics
   permanently?
10. What parity/fallback tests are required before any product runtime can
    select compiled regions?

## Required Implementation Order In The Design

Please propose small cuts in this order or justify a better order:

1. Add region eligibility analysis over verified AWBC.
2. Add baseline backend metadata and artifact construction.
3. Implement the first effect-free compiled region path.
4. Add safe-point/trap/return mapping into `FiberState`.
5. Add zero-budget VM fallback and rejection reporting tests.
6. Add policy-controlled selection behind explicit dev/test configuration.

## Tests To Specify

The design should include tests for:

- eligible and rejected AWBC regions;
- artifact/cache identity stability;
- `CompiledStepExit` validation;
- safe-point suspend/resume mapping;
- trap/source-map mapping;
- fallback restores checkpoints and consumes zero budget;
- compact VM and compiled region parity on eligible fixtures.

## Constraints

- Do not use `unsafe`.
- Do not allow generated regions to perform host I/O.
- Do not compile regions that cannot preserve compact VM observations.
- Keep backend-specific dependencies behind feature flags or adapter crates.

## Expected Output

Please produce one design document with:

- region-lowering architecture;
- eligibility rules;
- first backend choice and rationale;
- ABI mapping details;
- cache/policy integration;
- fallback behavior;
- implementation cuts;
- focused tests;
- explicit non-goals.
