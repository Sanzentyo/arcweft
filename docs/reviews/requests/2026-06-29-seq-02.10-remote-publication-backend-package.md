# Seq-02.10 Request: Remote Publication Backend Package

## Sequence Position

This follows seq02.9. The repository already has local atomic release publish
staging and release consume verification. Seq02.10 is the first slice allowed
to introduce a real remote publication backend.

Implementation must wait for seq02.9 release trust fixtures or must include an
explicit conservative dependency note if only a design-first package is
returned.

Do not move credentials, network clients, clocks, retry policy, or remote
object handles into `arcweft-bundle`.

## Request

Design and implement one concrete remote publication backend for Arcweft
release artifacts, plus a dry-run plan mode, recoverable failure reports, and
fixture-backed integration tests.

Return the final work as a zip package with design, Rust implementation
overlay, fixtures, tests, implementation notes, validation notes, and apply
instructions.

## Required Inputs

- Current Arcweft `main`.
- The seq02.9 package result, or the current repository after applying seq02.9.
- `docs/implementation/2026-06-28-seq-02-6-02-7-adapter-validation.md`.
- Current `arcweft-project-loader::release_adapter::publish` code.
- Current `arcweft-cli` release publish/verify commands.
- Current external payload fetch/cache adapter code.
- Current signing-policy and AWFR archive data models.

## Backend Choice

Implement exactly one production-shaped backend first. The preferred order is:

1. a remote-like filesystem/object-directory backend with remote semantics for
   deterministic tests;
2. an S3-compatible object-store backend;
3. a GitHub Releases backend.

If the package chooses something other than the filesystem/object-directory
backend as the first implementation, it must explain why that backend is the
cleaner first production boundary and how it can be tested without private
credentials.

## Required Decisions

1. Which crate owns the backend trait and backend implementations.
2. The publication plan model:
   artifact list, destination keys, content digests, size budget, signing
   requirements, external payload mirrors, and AWFR finalization.
3. The dry-run output shape and how it differs from a committed publish.
4. The commit protocol:
   staging writes, upload order, signature generation, manifest/AWFR final
   write, commit marker if any, and cleanup.
5. The recovery model for partial failures:
   which files are committed, which are staged, which should be rolled back,
   and which require manual cleanup.
6. Retry, timeout, byte budget, and checksum verification behavior.
7. Credential and secret handling:
   where credentials are read, how they are redacted in logs, and which tests
   prove secrets are not serialized into reports.
8. How remote publish reports connect to `arcw release verify` and seq02.9
   trust fixtures after publication.

## Required Implementation

The implementation must include:

- an adapter-owned remote publication backend trait or equivalent existing
  boundary extension;
- one concrete backend implementation;
- dry-run/plan mode exposed through CLI or a focused adapter API;
- recoverable publish reports with typed states for staged, uploaded,
  committed, rolled back, and abandoned artifacts;
- checksum verification after upload or write;
- redacted report/log behavior for credentials;
- integration tests using local fake backend or local remote-like directory;
- implementation documentation under `docs/implementation/`.

The implementation must preserve the publish ordering from the existing local
atomic adapter: payloads and signatures before final AWFR publication.

## Acceptance Criteria

- Remote publication is adapter-owned and does not contaminate
  `arcweft-bundle`.
- Dry-run mode reports exactly what would be published without writing remote
  objects.
- Failed publication leaves a typed recoverable report.
- Successful publication writes the final AWFR artifact last.
- Uploaded or written bytes are verified by digest/size.
- Credentials are redacted from diagnostics, reports, and fixture output.
- Local deterministic tests cover success, dry-run, retryable failure,
  non-retryable failure, rollback/recovery report, and verification after
  publication.
- Seq02.9 release trust fixtures remain passing.

## Tests To Specify And Run

```bash
cargo fmt --all -- --check
cargo test -p arcweft-project-loader release --all-features
cargo test -p arcweft-cli release --all-features
cargo test -p arcweft-cli cache --all-features
cargo check -p arcweft-project-loader -p arcweft-cli --all-targets --all-features
cargo clippy -p arcweft-project-loader -p arcweft-cli --all-targets --all-features -- -D warnings
cargo +nightly -Zscript tools/structure-audit.rs --root .
git diff --check
```

Focused tests must cover:

- dry-run plan stability;
- successful remote-like publish;
- final AWFR published last;
- checksum mismatch after upload/write;
- interrupted publish with recoverable report;
- credential redaction;
- published archive verified through `arcw release verify`.

## Non-Goals

- No new release trust semantics; consume seq02.9 verifier fixtures instead.
- No production credential provisioning UX beyond the narrow backend boundary.
- No background daemon, scheduler, or live update service.
- No product bundle codec changes.
- No patch schema changes.
- No signing-key access inside `arcweft-bundle`.

## Parallelization Guidance

Seq02.10 can be designed while seq02.9 is being implemented, but production
implementation should land after seq02.9 so remote publication can reuse the
end-to-end trust fixture matrix. If a design-first package is produced early,
it should mark remote trust validation as pending on seq02.9.
