# Seq-03.5 Request: Windowed Runtime Owner Scene Integration Package

## Sequence Position

This follows seq03.1 through seq03.4, which added the generation runtime table,
generation-bound task dispatch, code-generational `BundleSession` behavior, and
`arcweft-player-native::windowed_runtime::WindowedRuntimeOwner`.

## Request

Design and implement the production wiring that makes `scene_windowed.rs` use
`WindowedRuntimeOwner` as the single owner of the active native patch endpoint,
runtime session, image catalog, patch queue, and patch reports.

Return the final work as a zip package in the established overlay-package
format. The package must be directly applicable to the current `main` after the
seq03.1-03.4 production cut and must include Rust implementation, tests,
implementation notes, and validation instructions.

## Required Scope

- Replace direct `NativeSceneState` ownership of `BundleSession` and
  `BundleImageCatalog` with `WindowedRuntimeOwner` where the event loop needs
  session/images access.
- Preserve the existing renderer, window, surface, device, queue, input
  controller, visual clock, and prepared frame ownership in `NativeSceneState`.
- Drain typed `WindowedPatchEvent` values only at
  `FrameBoundary::AfterRenderSubmitted`.
- Ensure invalid patch events update the retained patch report and do not kill
  the running window or mutate the previous session/catalog.
- Refresh image catalogs only through `WindowedRuntimeOwner` after successful
  apply or restart.
- Keep filesystem watching, socket servers, network fetch, AWFR trust
  verification, and release publication outside this package. The package may
  expose a narrow in-process enqueue API for adapters to call later.

## Required Decisions

- How should `NativeSceneState` expose the current `BundleSession` and
  `BundleImageCatalog` to rendering/input code after those values move behind
  `WindowedRuntimeOwner`?
- What exact call site represents `AfterRenderSubmitted` in
  `scene_windowed.rs`?
- Should the first implementation process at most one queued patch per frame or
  drain all ready patches at the safe boundary?
- How should patch reports be surfaced for future debug overlay/logging without
  adding visible UI in this cut?
- Which renderer caches must be invalidated for content-only or code-changing
  patches in the current renderer model?

## Tests To Specify And Implement

- A source-level test or narrow unit test proving `scene_windowed.rs` no longer
  stores a direct `BundleSession` plus `BundleImageCatalog` pair outside
  `WindowedRuntimeOwner`.
- A unit test for the scene/owner boundary proving unsafe boundaries do not pop
  queued patches.
- A focused test proving an invalid patch report leaves the previous session and
  image catalog observable.
- A focused test proving a content-only patch refreshes the image catalog at the
  safe frame boundary.

If full `winit`/GPU execution cannot run in the package environment, document
the exact manual/headless validation steps required after applying the zip.

## Constraints

- Do not add syntax/HIR/sema/compiler/verifier/CLI dependencies to product
  player crates.
- Do not use `unsafe` or unstable Rust.
- Do not introduce cross-thread mutable session access.
- Do not redesign seq03.1-03.4 runtime generation semantics unless the current
  implementation evidence shows a concrete flaw.

## Expected Zip Contents

- `overlay/` files for the Rust implementation.
- `patches/` or an apply script only if direct overlays are insufficient.
- `docs/implementation/seq-03-5-windowed-runtime-owner-scene-integration-2026-06-28.md`
- Tests under the owning crates.
- `VALIDATION.md` with commands run and commands blocked by missing GPU/window
  capability.
- A short `README.md` stating assumptions, apply order, acceptance criteria, and
  non-goals.

## Parallelization Guidance

This can be designed in parallel with seq03.6 because it should consume the
existing single-entry `BundleSession` API. Apply seq03.5 to `main` before any
seq03.6 implementation that changes session start/spawn APIs, unless seq03.6
explicitly provides a compatibility-free replacement and updates this request's
integration points.
