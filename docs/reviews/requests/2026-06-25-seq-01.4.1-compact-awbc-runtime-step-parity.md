# Seq-01.4.1 Compact AWBC Product Runtime Step Parity Design Request

## Sequence Position

This request is split from seq-01.4 after applying the runtime driver / host
executor-construction migration. Seq-01.4 can centralize structured VM and AOT
executor construction behind the shared facade, but the current design package
does not specify enough product-runtime behavior to replace the structured
`RuntimeStepResult` path with the compact AWBC VM.

Design this before product code starts executing compact AWBC as the default
runtime-driver, runtime-host, native-player, CLI, or Agent controller executor.

## Why This Split Is Needed

The compact AWBC VM currently exposes typed `VmExit`, `VmObservation`, and
`FiberState` data. Existing product runtime callers consume `RuntimeStepResult`,
`FlowFiberStatus`, line effects, task requests, source/stream events, audio
requests, diagnostics, flow events, pure-helper acceleration stats, and native
host task dispatch.

The missing design is the exact parity contract between those two surfaces.
Without it, upper crates can stop constructing `BytecodeVmExecutor` directly,
but they cannot safely run product bundles through compact AWBC.

## Required Decisions

- Define how each compact AWBC `VmExit` maps to product runtime status,
  stop reason, diagnostics, and retry/resume behavior.
- Define how `VmObservation` entries become existing product output channels:
  line effects, dialogue flow events, task requests, source events, stream
  events, audio commands, metrics, and diagnostics.
- Define the host resume protocol for dialogue, choice, await, await-many,
  host-call, source, stream, and budget-yield suspensions.
- Specify how root bindings, runtime input events, task events, audio events,
  and source events are materialized into `FiberState`.
- Specify pure-helper and intrinsic host binding rules, including how existing
  runtime pure acceleration stats are preserved or intentionally replaced.
- Define deterministic error types for envelope decode, AWBC verification,
  fiber creation, VM execution, host resolution, parity conversion, and
  unsupported compact features.
- Decide where the product AWBC executor facade lives and what typed input it
  accepts: AWBC bytes, decoded `AwbcProgram`, selected entry/route, legacy
  structured bytecode fallback, or a product bundle view.
- Define the compatibility policy while seq-01.5 has not removed structured
  bytecode from products.

## Implementation Order To Specify

1. Product-step parity data model and typed error taxonomy.
2. Compact AWBC executor facade that can run a minimal return-only program and
   produce a `RuntimeStepResult`-equivalent report.
3. Dialogue and choice suspension/resume mapping.
4. Await, await-many, host-call, source, and stream mapping.
5. Pure-helper and intrinsic host binding.
6. Runtime-driver integration behind an opt-in tier.
7. Runtime-host/native-player/CLI/Agent controller routing behind the same tier.
8. Product-default migration or explicit deferral into seq-01.5.

## Tests To Specify

- Return-only AWBC program parity with structured VM status and step stats.
- Dialogue, choice, await, await-many, host-call, source, stream, and budget
  yield parity cases.
- Error cases for invalid AWBC envelope, invalid entry, route-selection
  required, unknown host intrinsic, missing pure helper, and fiber trap.
- Source gates proving application-facing crates do not construct low-level VM
  executors directly.
- Cross-tier golden cases comparing structured VM, structured AOT, and compact
  AWBC product-step output where semantics overlap.

## Constraints

- Do not redesign cuts 1, 2, 7 substrate or the already implemented
  seq-01.1-01.4 facade migration unless current implementation evidence shows
  a concrete flaw.
- Keep `arcweft-core` Sans I/O.
- Do not make low-level AWBC VM code depend on runtime-host, CLI, native-player,
  presentation, filesystem, network, GPU, audio, or OS adapters.
- Keep product AWFB migration, product default AWBC-only behavior, structured
  product payload deletion, and `compact_bytecode` deletion in seq-01.5 unless
  this design explicitly moves them with an implementation-ready migration plan.

## Expected Output

- A concrete product-step parity specification with typed Rust API sketches.
- A crate-boundary diagram and dependency-direction check.
- A test matrix with required fixtures and expected output fields.
- A migration plan that states which seq-01.4 implementation pieces remain
  unchanged and which seq-01.5 work becomes unblocked.
