# Request: seq-06.11d.4.1.1 native logical-axis host seed and provider invalidation contract

Date: 2026-07-14

## Sequence position and reason for the split

This request follows the implemented seq-06.11d.4.1 logical-axis core and
precedes physical-box completion, scroll anchoring, and provider-revision
motion behavior. It combines mount seed injection with provider/barrier
invalidation because a provider revision begins at the host seed and both must
share one identity and propagation contract.

The d.4.1 package specified the desired outcome but did not identify the host
API, mount lifecycle owner, revision allocator, cache eviction seam, or nested
View propagation algorithm. Implementing those by guesswork would create a
public runtime contract.

This request is independently throwable. It must not redesign the implemented
axis enum, owner mapping, canonical computed slots, cascade priority, or
physical packet unless repository evidence demonstrates a concrete defect.

## Fixed substrate

- `ViewBoxAxisMode` has exactly four modes and owns the exhaustive mapping.
- `box-axes` is typed, inherited, discrete, non-appendable, and resolved before
  ordinary declarations.
- `ComputedViewStyle` stores canonical physical keys, effective axes, provider
  revision/source, provenance, transition targets, and axis usage.
- The root currently uses `HorizontalLtr`; child resolution can inherit a
  parent computed snapshot through the existing resolver seam.
- A local `box-axes` winner is distinguishable even when equal to its parent.

## Required decisions

1. Exact typed API by which a host supplies a per-mount axis seed, including
   defaulting, ownership, lifetime, and whether mutation is allowed.
2. The owner and allocation rules for `ViewBoxAxisRevision`; define wrap,
   remount, restore, clone, replay, and deterministic-test behavior.
3. How top-level roots, direct children, nested call roots, and exported parts
   receive one inherited snapshot without consulting locale or text.
4. Exact local-provider barrier identity and how equal-value overrides remain
   barriers.
5. The descendant dependency index, propagation order, stopping rule, cache
   key update, eviction policy, and work budget.
6. How runtime-driver and player revisions interact with existing application,
   parent, container, and environment revisions.
7. Typed outcomes for stale mounts, missing parents, cycles, budget exhaustion,
   and revision mismatch.

## Implementation order to specify

1. Freeze host seed and revision APIs with lifecycle examples.
2. Add runtime-driver seed propagation for top-level and nested View roots.
3. Materialize provider identity and local barriers beside existing scope data.
4. Build bounded descendant invalidation and cache eviction.
5. Connect player/headless/web mount adapters to the same typed seam.
6. Add deterministic trace evidence without changing the finalized trace DTO.

## Required tests

- Default and explicit seeds for every mode; independent simultaneous mounts.
- Parent inheritance, equal-value local barrier, changed local override, nested
  calls, exported parts, unmount/remount, restore/replay, and stale revisions.
- Propagation stops at barriers and does not invalidate siblings or other
  mounts; exact-limit and one-over budget cases are deterministic.
- Cache hit/miss identity includes mode and provider revision.
- Native, headless, and web adapters produce equal typed snapshots.
- Tampered/missing/cyclic provider facts fail through typed errors, not panic.

## Constraints and non-goals

- No locale, host language, RichText direction, theme, or text-content inference.
- No second resolver, string axis flags, CSS direction/writing-mode model, or
  public compatibility shim.
- Do not redesign cascade ordering, logical mappings, Style grammar, or trace
  transport without a demonstrated substrate flaw.
- Physical box semantics, scroll-start anchoring, and transition disposition
  are handled by later requests.

## Expected output

Produce a standalone final design with exact Rust APIs and crate ownership,
mount/nested-View state diagrams, revision and cache algorithms, budgets,
errors, invalidation pseudocode, wire/persistence implications, file-by-file
implementation order, and the complete positive/negative/tamper test matrix.
