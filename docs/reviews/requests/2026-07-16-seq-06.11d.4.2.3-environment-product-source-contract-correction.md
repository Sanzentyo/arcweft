## Reproduced contradictions

### 1. The required canonical multi-source authority does not yet exist

The d.4.2.1 package says that it consumes the d.2.1.1.1 predecessor's canonical
multi-source `ProductSourceId`, `SourceMapIndex`, normalized source extent,
digest, and complete-product typestate. The current production reconciliation
explicitly records those multi-source contracts as design-gated in
[`view-exported-part-production-reconciliation-2026-07-16.md`](../../implementation/view-exported-part-production-reconciliation-2026-07-16.md).

Production currently has `SourceMapIndex::from_source(&BundleSource)`. Although
the index uses an internal map, the only public construction route accepts one
`BundleSource`; it is not the package's canonical multi-source
`ProductSourceId`/binary `SourceMapSection` authority or validated-product
typestate. The safe d.4.2.1 reconciliation can validate environment references
against that one indexed source, but must not invent a parallel source identity
or silently freeze the predecessor's still-open API.

This request must consume the corrected source-map owner selected by the
independent exported-part contract correction. If that answer is not yet
available, state the dependency and return this request as blocked rather than
creating another source registry.

### 2. Product clauses do not carry individual field/value provenance

The package requires every clause field range and value range to be contained
by its clause range during complete-product validation. Production
`ViewEnvironmentClause` stores one typed `ViewEnvironmentTest` plus one
`ViewStyleSourceId` for the complete clause. The serialized View resource
therefore has a condition reference and one reference per clause, but no
individual field, comparison, value, or percentage-unit source references.

Parser and HIR records retain those component ranges, so compiler-time checks
can inspect them before projection. After projection, however, a product decoder
cannot reconstruct or validate individual component containment without parsing
source text, guessing offsets, or adding new serialized provenance. The current
resource shape cannot satisfy the stated complete-product invariant.

### 3. A parenthesized condition range cannot contain its guarded rule

The package calls `ViewEnvironmentCondition::source` the complete outermost
wrapper range and requires it to contain both every clause and the guarded rule.
Production compiler lowering uses `CheckedStyleEnvironmentPath::source_range()`;
the exact compiler test proves that the resulting source slice is the
parenthesized predicate, for example `(text-scale >= 125.5%)`.

The guarded rule is authored after that predicate, inside the following body.
Consequently `condition_range` containing `guarded_rule_range` is impossible
with the current meaning of the condition source. Nested wrappers sharpen the
ambiguity: semantic flattening keeps the outermost predicate range while the
resulting rule may depend on several wrapper scopes. Re-labeling the predicate
range as a wrapper-body range would lose the exact condition provenance already
used by compiler and tooling tests.
