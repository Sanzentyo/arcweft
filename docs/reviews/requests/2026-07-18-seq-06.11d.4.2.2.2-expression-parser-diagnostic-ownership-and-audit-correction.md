# seq-06.11d.4.2.2.2 — expression parser diagnostic ownership and audit correction

## Sequence position

This request follows `seq-06.11d.4.2.2` typed `ParseErrorKind`
reconciliation and is independent of the recovery-payload decision in
`seq-06.11d.4.2.2.1`. It must not reopen the accepted 30-variant
`ParseErrorKind` mapping unless the final decision explicitly merges another
diagnostic owner into `ParseError`.

## Why this correction is required

The `seq-06.11d.4.2.2` structural audit claims that all strings matching
`syntax.parse.*`, `syntax.assert.*`, `style::*`, or `view::*` occur only in
`ParseErrorKind::code()`. That is not true at the pinned revision:

- `ExprParseError` independently owns `syntax.assert.statement_only` and
  `syntax.assert.unknown_mode`;
- `SyntaxLintCode` independently owns several `style::*` lint codes.

These are typed owners, not raw `ParseError` producers or reverse readers.
Moving them into `ParseErrorKind` would either violate the exact 30-variant
contract or collapse distinct expression/lint diagnostic models without a
design decision. Leaving the package audit unchanged yields a guaranteed false
failure even when the `ParseError` migration is correct.

There is also a semantic collision: both statement parsing and expression
parsing emit `syntax.assert.unknown_mode`, while only the former is represented
by `ParseErrorKind::AssertionUnknownMode`.

## Required decisions

Decide all of the following:

1. Is `ParseErrorKind` specifically the discriminator for `ParseError`, or the
   universal owner for expression-parser and syntax-lint diagnostics as well?
2. If owners remain separate, define non-overlapping structural audits by Rust
   type/producer boundary rather than by broad code-prefix spelling.
3. Decide whether the shared `syntax.assert.unknown_mode` code intentionally
   denotes one logical diagnostic across two owners, or whether expression
   parsing receives a distinct typed code.
4. Decide whether `ExprParseError` keeps its current typed/static code field,
   receives its own closed kind enum, or lowers into `ParseError` with full
   payload preservation.
5. Confirm that `SyntaxLintCode` remains an independent lint owner and is
   excluded from parser-error representation checks.

## Implementation order to specify

1. Inventory every `ExprParseError` code producer and every conversion into
   repository parser diagnostics.
2. Inventory independent syntax-lint code owners that share broad prefixes.
3. Select the final ownership graph and stable code policy.
4. Update direct behavioral tests before changing any owner.
5. Replace the false-positive audit with structured ownership evidence.
6. Run syntax, expression, parser, lint, compiler, LSP, and CLI diagnostics
   tests plus workspace check/clippy and the structural audit.

## Tests to specify

- exhaustive mapping for every closed owner that remains;
- expression assertion-call rejection with exact type, code, range, and
  message;
- statement assertion rejection with exact `ParseErrorKind`;
- conversion tests proving no code/message parsing occurs;
- syntax lint projection tests that remain independent of `ParseError`;
- uniqueness expectations scoped explicitly per owner or globally, whichever
  the contract chooses;
- a structured audit that does not pass or fail by scanning source spellings.

## Constraints

- No source gates or automated source-spelling checks.
- No compatibility aliases, dual readers, `Other(String)`, or string-to-enum
  reconstruction.
- Do not add a 31st `ParseErrorKind` variant merely to silence an audit unless
  the ownership decision requires it semantically.
- Do not redesign already accepted assertion statement syntax or native Style
  grammar.
- Preserve exact expression ranges and parser recovery behavior.

## Expected output

Return an implementation-ready final contract with one explicit ownership
model, a collision policy for `syntax.assert.unknown_mode`, corrected
non-source-gate verification, concrete migration order, and
`OPEN_QUESTIONS=0`.
