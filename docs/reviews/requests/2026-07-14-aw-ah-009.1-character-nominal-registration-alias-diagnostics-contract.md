## Readiness result and task kind

This is a **final-design task**, not an implementation task. A 2026-07-15
readiness review found that the repository proves the defect and exposes the
relevant seams, but does not choose the registration owner, nominal scope,
alias collision rules, provenance model, diagnostic payloads, or limits. Those
choices change public semantic behavior, so an implementer must not infer them
from the current maps or builders.

The assignee must return one decision-complete contract. Every alternative in
the required decisions below must be resolved to one final choice; `TBD`,
"either", deferred API shapes, and implementation-selected policy are not
acceptable. Production changes are intentionally deferred to a new
implementation task created from that final contract.

## Sequence position and reason for the split

This request follows the implemented AW-AH-009 structural nominal identity
core and precedes character-aware definition/rename and signature-help work.
It is independently throwable.

The AW-AH-009 re-upload fixes in-memory identity and the existing profile
completion/hover path, but its builder API still cannot report duplicate or
conflicting owners, and it models only the canonical `character.*` name plus
the existing compact name. The package does not specify how project modules,
imports, arbitrary source aliases, manifest source ranges, or compiler and LSP
environment construction share one fallible registration transaction.

This request must not redesign the implemented
`TypeKind::CharacterNominal(CharacterNominalType)` payload, validated ID
owners, equality/hash tuple, or presentation-only `source_label()` unless
repository evidence demonstrates a concrete defect.

At minimum, reconcile the final design with these current seams:

- `arcweft-lang-sema::env::TypeCheckEnv::with_character_manifest` is an
  infallible consuming builder. It inserts canonical and compact spellings and
  extends enum sets, so repeat/conflict behavior is an incidental map effect.
- `arcweft-character::catalog::CharacterCatalog` validates manifests and
  rejects a duplicate `CharacterId`, but has no import/alias scope or source
  provenance transaction.
- `arcweft-cli::app::project` and `arcweft-lsp::profiles` separately load a
  `CharacterCatalog` and fold its manifests through the infallible sema builder.
- `arcweft-project-loader::character_manifest::load` returns the decoded
  manifest, not a manifest-token source map.

These are evidence of the missing contract, not defaults that the design must
preserve. The final design must name which API is replaced and how every caller
migrates to the one authoritative path.

## Fixed substrate

- `CharacterNominalType` has exactly `Look { character }`,
  `Part { character }`, and `Variant { character, part }` families.
- `CharacterId` and `CharacterPartId` remain owned by `arcweft-character`.
- Manifest enum inventories are keyed by structural `TypeKind` values.
- Canonical and compact character spellings resolve to one `CharacterId` in
  the current environment; no synthetic `TypeKind::Named` grammar remains.
- `CharacterCatalog` already rejects a duplicate `CharacterId` while loading
  one catalog, but `TypeCheckEnv::with_character_manifest` is currently an
  infallible public builder and can be called outside that loader.
- No persisted semantic-type boundary was found in the audited path.

## Required decisions

1. Exact owner and typed API for fallible manifest registration. Decide
   whether the semantic environment consumes a validated catalog snapshot,
   accepts one manifest through a `Result`, or uses a dedicated registrar.
2. Nominal scope identity across packages, project modules, imports, and
   simultaneous profiles. State precisely when equal `CharacterId` values
   share one owner and when they are conflicts.
3. Duplicate and conflict policy for identical manifests, differing manifests
   with the same owner, repeated imports, and aliases that collide with local
   symbols or another character.
4. Exact typed representation of canonical names, compact names, qualified
   imports, and arbitrary source aliases. Aliases may select an identity but
   must never become part of equality or create compatibility identities.
5. How manifest, project, import, and alias source ranges reach structured
   diagnostics without moving filesystem I/O into sema or character data
   crates.
6. Structured error variants for unknown owner, unknown part, duplicate owner,
   conflicting manifest, alias collision, and look/part/variant mismatches.
   Expected and actual nominal identities must remain typed fields; messages
   must use inherent labels and must not be reparsed.
7. Exact construction path used by compiler, CLI, LSP, tests, and future
   project services so one surface cannot bypass registration validation.
8. Hard limits for manifests, aliases, parts, variants, diagnostics, and
   registration work, including deterministic exact-limit behavior.
9. Whether any current query cache or digest includes the environment
   inventory. If one does, specify a typed versioned descriptor; otherwise
   explicitly retain an in-process-only contract.

## Implementation order to specify

1. Freeze the scope, registration transaction, and structured error types.
2. Add source-provenance input without adding I/O to Sans I/O crates.
3. Route catalog/profile/project construction through one registrar.
4. Add module qualification and alias binding to the ordinary semantic symbol
   rules.
5. Switch character look checking and tooling environment queries to the
   finalized registration result.
6. Delete any bypassing builder or duplicate alias table; retain no dual path.

## Required tests

- Two modules importing the same owner through different aliases obtain equal
  and equal-hash nominal types.
- Canonical, compact, qualified, and arbitrary alias spellings select the same
  identity; shadowing and alias conflicts follow one documented rule.
- Identical repeat, conflicting repeat, duplicate catalog entry, unknown owner,
  and unknown part produce exact structured outcomes with source ranges.
- Matching local look/part/variant strings across two characters and two parts
  remain incompatible through assignments, equality, collections, function
  parameters/returns, and generic containers.
- Invalid IDs fail in the character/manifest boundary before any environment
  map mutation; a failed registration is atomic.
- Compiler, CLI, and LSP construct equivalent inventories from the same project
  facts, including deterministic order and exact-limit/one-over-limit cases.
- No test searches repository source text or depends on synthetic label parsing.

### Mandatory negative and atomicity matrix

The final contract must state the exact error kind, stable code, typed fields,
source ranges, and mutation outcome for each of the following:

- invalid character/part/member ID before registration;
- unknown owner and unknown part;
- identical repeat, same owner with a differing manifest, and duplicate entry
  inside one catalog;
- repeated import of one owner, two aliases for one owner, and one alias bound
  to two owners;
- alias collision with a local symbol, canonical spelling, compact spelling,
  and qualified import;
- look/part/variant family mismatch and a variant under the wrong part;
- stale provenance, missing provenance, exact budget limit, and one-over limit.

Every failure that occurs before commit must leave symbols, aliases, enum
inventories, revisions, and caches unchanged. Tests must observe typed public or
crate-owned behavior; they must not inspect implementation source spellings.

## Constraints and non-goals

- No manifest format, rendering, stage-slot, CSS, AWBC, bundle, or save redesign.
- No compatibility alias, dual reader, extension trait, or deprecated string
  constructor.
- Do not redesign general user-declared nominal types without a demonstrated

- Keep `arcweft-character` and semantic data Sans I/O; path reads remain in
  project/profile adapters.
