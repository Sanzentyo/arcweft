# Seq-03.6 Request: Multi-Entry Generation Runtime API Package

## Sequence Position

This follows seq03.1 through seq03.4. The current production cut has a
generation runtime table and a single foreground entry rebind API:
`BundleSession::restart_active_entry_on_current_generation`.

## Request

Design and implement the next runtime-driver API that generalizes the
single-active-entry model into explicit generation-bound entry/fiber starts
without introducing a speculative full scheduler.

Return the final work as a zip package in the established overlay-package
format. The package must be applicable after seq03.1-03.4 and must include Rust
implementation, focused tests, implementation notes, and validation commands.

## Required Scope

- Replace or extend `restart_active_entry_on_current_generation` with a typed
  entry/fiber start API that can bind a new entry to the current active
  generation.
- Preserve the current single foreground fiber behavior until a real multi-flow
  scheduler is explicitly designed. Do not invent background scheduling policy.
- Make generation binding explicit in the API result so callers can observe
  which generation a new entry uses.
- Keep host task generation routing deterministic by `TaskSequence`.
- Preserve retire semantics: old generation images may be dropped only when no
  active fiber, task pin, explicit pin, or windowed handoff needs them.
- Keep runtime images generation-local and avoid moving executor ownership into
  `ProgramGeneration`.

## Required Decisions

- What is the minimal type that represents a started foreground entry or fiber
  in the current runtime-driver model?
- Should the API be named around `start_entry`, `restart_entry`, or
  `bind_entry`, and what ownership does the name imply?
- How should missing entrypoints, non-flow entries, and runtime-image lookup
  failures be reported?
- Which parts of `BundleSessionOptions` are reused for new entries, and which
  must be supplied by the caller?
- How should this API remain compatible with future multi-fiber support without
  adding placeholder scheduler abstractions?

## Tests To Specify And Implement

- New entry starts on `SwapSession.active_generation_id()` after a
  code-generational commit.
- Old foreground fiber remains on its old generation until explicitly replaced
  or finished.
- Pending host task completion from the old generation still releases the old
  task pin after a new entry starts.
- Old generation runtime image remains while old fiber/task pins exist and is
  pruned once all pins are released.
- Error cases for missing runtime image and invalid entry selection are typed
  and deterministic.

## Constraints

- Do not add product player, compiler, syntax, HIR, sema, verifier, CLI, GPU, or
  OS adapter dependencies to `arcweft-runtime-driver`.
- Do not use string ids where existing typed ids or owned enum behavior can
  express the rule.
- Do not preserve a compatibility shim for any API replaced by this package.
- Do not use `unsafe` or unstable Rust.

## Expected Zip Contents

- `overlay/` implementation files.
- Focused runtime-driver tests.
- `docs/implementation/seq-03-6-multi-entry-generation-runtime-api-2026-06-28.md`
- `VALIDATION.md` with cargo fmt/check/test/clippy/structure-audit results or
  honest blockers.
- `README.md` with assumptions, public API changes, non-goals, and migration
  notes.

## Parallelization Guidance

This can be designed in parallel with seq03.5. Apply it after seq03.5 unless
the implementation changes `BundleSession` APIs that seq03.5 needs; in that
case, update seq03.5's package against the seq03.6 API before applying either
implementation.
