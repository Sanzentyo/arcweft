## Concrete contract defects to correct

### 1. Preserve the reconciled manifest ownership

Lang-01.5.1 explicitly places the only schema-1 manifest decoder,
`ArcweftManifestDocument`, `ProfileSpec`, and the revision-bound
`ManifestSourceMap` in `arcweft-launch`. It keeps
`arcweft-manifest-model` as a neutral lower owner of identities, hashes, and
metadata-compatible wire primitives. It expressly rejects adding presentation
types to that lower crate.

The returned Lang-01.5.1.1 package instead places `DialogueProfileSpec`, dedicated dialogue
source-map structs, and `decode_manifest_document` in
`arcweft-manifest-model`, and prescribes direct dependencies from that crate to
`arcweft-view` and `arcweft-dialogue`.

That would pull presentation/dialogue ownership into neutral consumers such as
`arcweft-adapter-metadata` and `arcweft-resource-model`, duplicate the current
generic source map, and move the sole decoder away from its accepted owner.

The repository has already retained the following cycle-free direction and
implemented the non-conflicting owner substrate:

```text
arcweft-manifest-model
    neutral IDs, hashes, metadata-compatible primitives
            ↓
arcweft-dialogue / arcweft-view
    owned dialogue and View/Style nominal types
            ↓
arcweft-launch
    sole schema-1 decoder, ProfileSpec, ManifestSourceMap,
    DialogueProfileSpec, pure profile resolution
```

Do not select a different graph. If current production evidence reveals a
concrete cycle or responsibility defect, return `STATUS=NOT_READY` with that
evidence rather than moving the decoder or adding presentation dependencies to
the neutral manifest model.

### 2. Catalog validation is assigned before the catalog exists

The current project-loader topology loads the accepted manifest, source
modules, Character package manifests, generated external-module metadata, and
adapter facts, then freezes that source topology. It does not compile View
programs.

The current immutable `ViewProgramCatalog` is constructed later in
`arcweft-runtime-driver` from an already compiler/bundle-validated
`ValidatedViewProduct`. Its constructor is crate-private, and its
dialogue-input capability query is crate-private. Project-loader cannot consume
that runtime catalog without reversing the layer direction or duplicating the
catalog.

Lang-01.5.1.1 nevertheless requires project-loader topology admission to
produce `CheckedDialogueProfile` only after validating against that accepted
View/Style catalog and its `AcceptedViewProgramRevision`.

Specify the exact real admission stage and owner that has all of:

- the accepted manifest and exact dialogue field ranges;
- the selected `SourceSetRevision`;
- compiler-produced View and Style definitions;
- dialogue-input capability facts;
- accepted resource dependencies;
- the accepted View-program revision; and
- the previous complete candidate for atomic rollback.

Do not make project-loader depend on runtime-driver, construct a second View
catalog, reparse source, or validate only by ID spelling. If a lower,
runtime-neutral accepted View/Style catalog product must be extracted from the
current runtime-driver implementation, specify its exact crate, public
typestate, revision fields, construction input, and consumers. If validation
belongs in compiler/bundle acceptance instead, specify exactly how diagnostics
retain the manifest ranges and how CLI/LSP/runtime share the checked result.

### 3. Source-map duplication

Lang-01.5.1 already has one generic manifest source map keyed by typed path
segments and bound to the accepted `SourceDocumentIdentity`. Lang-01.5.1.1
specifies parallel dialogue-only source-map records.

Decide whether dialogue fields are represented by typed path accessors over the
existing map or by another non-duplicating projection. No second manifest scan,
detached byte range, copied source text, or parallel independently revisioned
map may exist.

### 4. Exact wire spelling and policy representation

Lang-01.5.1 uses the schema's established kebab-case field
`inline-failure` and directly decodes the dialogue owner's strict tagged policy
type. Lang-01.5.1.1 changes the field/table to `inline_failure` and changes the
fallback wire shape and enum spellings.

The repository has retained `inline-failure` and the dialogue owner's current
strict tagged wire type. Treat those as fixed. State explicitly that the
conflicting Lang-01.5.1.1 rows are superseded and carry the existing wire
unchanged through checked admission. No decode-only bridge enum, alias, or dual
spelling is permitted.
