# Request seq-06.17: Focus Navigation and Controller DSL Package

## Sequence Position

This follows seq06.16.1 component/View submit buttons and the current
player-side automatic spatial focus navigation. Do not redesign the existing
player-rendered `TextField` / `TextArea` / `SecureField` / `Button` action
substrate unless the current implementation evidence shows a concrete flaw.

## Problem

Arcweft now has player-rendered text controls, action buttons, focus rings, and
automatic arrow-key focus movement derived from prepared frame geometry. This
is enough for simple layouts, but product UI still needs a typed authoring and
runtime contract for:

- controller D-pad / left-stick / confirm / cancel navigation;
- explicit focus order or directional overrides when geometric inference is not
  the desired UX;
- focus groups, modal traps, disabled/hidden behavior, wrap policy, and initial
  focus;
- deterministic parity between native and web players.

This must be an Arcweft-owned UI/navigation contract, not a DOM/native widget
fallback and not a platform-specific shortcut table.

## Required Design Decisions

1. Define the product data model for focus navigation:
   - focusable target id;
   - direction: up, down, left, right, next, previous;
   - target resolution: explicit target, auto, none, group boundary;
   - group id and parent group;
   - initial focus policy;
   - wrap policy;
   - disabled/hidden target skip behavior;
   - modal/trap policy.
2. Decide where the model lives:
   - `arcweft-bundle` compact UI resource model;
   - runtime-driver display snapshot;
   - render-wgpu prepared frame;
   - player-scene input controller.
3. Specify the DSL syntax. Candidate shapes are acceptable only as design
   inputs; the package must choose one final syntax:

   ```arcw
   pub component SettingsPanel() -> View {
     VStack(nav: .vertical, wrap: false, initial: @button:.apply) {
       Button("Back", id: @button:.back)
         .nav(right: @button:.apply, down: auto)

       Button("Apply", id: @button:.apply)
         .nav(left: @button:.back, down: none)
     }
   }
   ```

   The chosen syntax must fit the final `style` / `component` / `View` model.
   Do not introduce `ui surface` or parallel UI declaration families.
4. Define controller input normalization:
   - keyboard arrows;
   - Tab / Shift+Tab;
   - D-pad;
   - left analog stick threshold, repeat delay, and dead zone;
   - confirm/action button;
   - cancel/back button.
5. Define conflict resolution:
   - explicit DSL edge wins over automatic geometry;
   - disabled or invisible explicit target is skipped according to policy;
   - missing target is a structured diagnostic during build, not runtime guesswork;
   - geometry fallback is deterministic.
6. Define accessibility and inspection output:
   - focus graph exposed in agent observe / debug resource;
   - focused target and navigation candidates visible in trace output;
   - no web/native divergence.

## Implementation Requirements

The package must include Rust overlay implementation, tests, docs, and
validation notes.

Required implementation cuts:

1. Add typed focus navigation resource structs to the UI resource model.
2. Add compact encode/decode support and deterministic round-trip tests.
3. Extend component/View AST and parser for the chosen navigation syntax.
4. Lower DSL navigation into the product UI resource.
5. Thread navigation data into runtime-driver display snapshots and
   render-wgpu `PreparedFrame`.
6. Make player-scene input resolution use:
   - explicit direction edge when present;
   - automatic spatial navigation otherwise;
   - linear next/previous for Tab-like movement.
7. Add controller/D-pad normalization in native and web player input adapters
   where applicable. If a platform cannot be validated in the package
   environment, keep the implementation and document the exact validation
   steps.
8. Add a sample that includes:
   - at least four buttons/text controls in a 2D layout;
   - one explicit override that differs from geometry;
   - one disabled target skipped by navigation;
   - one focus group or modal trap;
   - keyboard and controller acceptance notes.

## Tests To Specify And Implement

- parser success tests for the chosen DSL syntax;
- parser/build diagnostics for missing navigation targets;
- compact UI resource deterministic bytes and round-trip;
- automatic geometry fallback parity;
- explicit edge overrides geometry;
- disabled/hidden target skip behavior;
- wrap/no-wrap policy;
- keyboard arrows and Tab;
- controller D-pad / confirm / cancel adapter mapping;
- native/web shared prepared-frame route does not diverge;
- sample `arcw check` and `arcw bundle`.

## Constraints

- Keep lower-level crates Sans I/O.
- Do not add DOM or native widget fallback.
- Do not use source gates as the main correctness mechanism.
- Do not introduce compatibility shims or accept removed syntax.
- Do not add broad root re-exports unless they are deliberate facade API.
- Use typed enums and boundary structs rather than stringly navigation helpers.
- Preserve existing automatic spatial navigation as the default fallback.

## Expected Output

Return a zip package containing:

- `overlay/` with production Rust edits;
- tests and fixtures;
- a runnable sample;
- `docs/implementation/seq06.17-focus-navigation-controller-dsl-YYYY-MM-DD.md`;
- `VALIDATION.md` with exact commands run and any platform-specific validation
  that could not be performed;
- an overlay manifest listing changed files and intentional non-goals.

The package should be independently applicable after seq06.16.1 and the
automatic prepared-frame spatial navigation cut.
