# Request 06.4i: Renderer-Backed Text Editor Geometry Package

## Sequence Position

This follows the applied seq06.4g shared text editor, seq06.4a.2 Web
EditContext glue, and the seq06.1/seq06.2 View style and renderer lowering work.

It can be designed and implemented in parallel with seq06.4h real Web IME
validation and the native Windows/macOS OS bridge packages. It must provide the
renderer geometry substrate those packages consume.

## Problem

`TextEditorLayout` currently provides deterministic monospaced fixture geometry.
That is useful for pure tests, but production IME candidate placement, pointer
hit-testing, ranged selection painting, and multiple-font styling need
authoritative glyph geometry from Arcweft layout and renderer output.

Without this bridge, Web/native adapters can only estimate caret positions from
DOM mirrors or monospaced assumptions, which is not good enough for mixed
Japanese/Latin text, font fallback, style changes, transforms, scroll, DPI, or
vertical writing.

## Request

Produce a final zip package containing design, implementation overlay, tests,
fixtures, validation notes, and apply instructions for renderer-backed
`TextEditorLayout` construction and geometry pumping.

The package should keep `arcweft-presentation` Sans I/O. Renderer, font, GPU,
window, and DOM details must stay in renderer/player adapter crates and feed
typed geometry snapshots back into the shared editor contract.

- Current Arcweft `main`.
- `crates/arcweft-presentation/src/text_editor.rs`.

- `crates/arcweft-view` TextField/TextArea style and layout types.
- `crates/arcweft-render-wgpu` UI/text rendering path.
- `crates/arcweft-render-text` and/or `crates/arcweft-text-layout` glyph layout
  owners.
- `crates/arcweft-player-web/src/web_text_input.rs`.
- `web/player-editcontext.js`.
- seq06.1 and seq06.2 implementation notes.
- Browser/native adapter requests for geometry consumers.

## Required Decisions

1. Which renderer/layout crate owns conversion from rendered glyph runs to
   `TextEditorLayout`.
2. The typed geometry data needed for:
   - caret rect;
   - selection rects;
   - composition range rects;
   - character bounds;
   - control rect;
   - text-local to viewport/screen transforms.
3. How font fallback, multiple font families, Japanese glyphs, emoji, combining
   marks, surrogate pairs, and mixed Latin/Japanese text map to ranges.
4. How scroll, transform, DPI scale, window movement, style changes, and layout
   reflow trigger fresh geometry snapshots.
5. How pointer coordinates are hit-tested against real glyph positions.
6. How Web glue receives runtime geometry without relying on DOM mirror
   measurement as production truth.
7. How native adapters query the same geometry for TSF/AppKit candidate APIs.
8. Which fixture geometry remains monospaced test-only and how that is enforced.

## Required Implementation

- Add renderer-backed construction of `TextEditorLayout` or a more precise
  geometry snapshot type consumed by `TextEditorState`.
- Wire TextField/TextArea runtime/render output so focused text controls publish
  fresh text-input geometry after edits, selection movement, scroll, transform,
  DPI, font fallback, and layout changes.
- Update Web player glue to prefer runtime geometry from Arcweft over DOM mirror
  estimates when available.
- Keep monospaced layout as test fixture support only.
- Add mixed-font and Japanese sample coverage, including explicit multiple font
  families in style/CSS-compatible decoration.
- Add deterministic tests for caret, range selection, composition range, and
  character bounds from real glyph layout.
- Add `docs/implementation/seq06-4i-renderer-backed-text-editor-geometry.md`.

## Acceptance Criteria

- Focused TextField/TextArea geometry comes from Arcweft renderer/layout data,
  not DOM mirror estimates or production monospaced assumptions.
- Caret, selection, composition, and character bounds are stable for mixed
  Japanese/Latin text, combining sequences, surrogate pairs, and font fallback.
- Multiple font family styling affects glyph geometry and remains observable in
  tests.
- Web EditContext receives non-origin selection/caret bounds from Arcweft
  runtime geometry when available.
- Windows TSF and macOS AppKit bridge packages can consume the same geometry
  snapshots without owning independent layout.
- Secure fields redact text and sensitive geometry according to the existing
  text-input security policy.

## Tests To Specify And Run

- Pure geometry tests for mixed text, font fallback, combining marks, emoji, and
  Japanese strings.
- Renderer/player tests proving focused text controls emit fresh geometry after
  edit, selection move, scroll, transform, DPI, font/style change, and reflow.
- Web glue tests proving runtime geometry overrides DOM-estimated geometry.
- Native adapter contract tests or fixtures for TSF/AppKit geometry consumers.
- Visual or raw-pixel smoke for caret/selection placement where deterministic.
- `cargo fmt --all -- --check`.
- Focused `cargo check`/`cargo test`/`cargo clippy` for changed crates.
- `npm run test:ime` after Web geometry wiring.
- Structural audit because renderer, UI, player, and presentation boundaries are
  connected.

## Constraints

- Keep `arcweft-presentation` Sans I/O.
- Do not move renderer, GPU, DOM, window, or OS identity into presentation data.
- Do not duplicate text movement/deletion semantics in renderer crates.
- Do not leave production candidate geometry dependent on DOM mirror fallback.
- Do not redesign seq06.3 text-input contracts unless a defect is documented
  and fixed with tests.

## Non-Goals

- Real Web IME trace capture; that is seq06.4h.
- Windows TSF COM bootstrap; that remains seq06.4b.1.
- macOS AppKit bridge; that remains seq06.4c.1.
- Wayland, Android, or iOS OS bootstrap.
