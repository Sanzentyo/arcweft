# Seq 06.16.6 - Scoped Presentation Resource Handles

## Sequence Position

This request follows seq 06.16.5 component-scoped render capture and the
runtime-control rendering work from seq 06.16.4.x. It should design scoped
presentation resource handles after the existing explicit image/component mount
substrate has been verified.

## Why This Split Is Needed

The current Arcweft surface supports reusable declarations such as `image` and
`component`, and it displays them only when a flow explicitly emits or mounts
the corresponding presentation object. It does not yet support a lexical or
runtime-scope handle model such as:

```arcw
let background = image(@image.menu_background)
let menu = component(@component.MainMenu)
```

where leaving the scope automatically hides, unmounts, or releases the created
presentation objects. Adding that behavior touches language lowering, runtime
lifetime, presentation snapshots, save/resume determinism, and tooling observe
semantics, so it should not be smuggled into renderer fixes.

## Required Decisions

- Decide whether handles are lexical resources, runtime-owned entities, or both.
- Define the difference between hidden, unmounted, released, and destroyed
  presentation resources.
- Decide whether dropping a handle is deterministic at block exit, flow return,
  cancellation, overlay pop, scene transition, or explicit `dispose`.
- Specify how handles survive waits, choices, async effects, save/load, and
  rollback.
- Specify whether images, components, menus, overlays, text boxes, and runtime
  controls all share one handle trait or use typed handle families.
- Define ownership when a handle is passed to another component or stored in
  state.
- Define how scoped handles interact with depth, layers, focus, input capture,
  and component-scoped render capture.
- Define diagnostics for leaked handles, double-dispose, hidden-but-focused
  resources, and resources that outlive their owner flow.

## Implementation Order To Specify

1. Add a typed HIR/lowering representation for presentation handle creation,
   visibility changes, and disposal.
2. Extend runtime presentation snapshots with stable handle identities and
   lifecycle operations.
3. Add deterministic cleanup on flow/block exit without relying on host GC.
4. Teach native, web, and Agent observe to apply the same lifecycle operations.
5. Add component-scoped capture behavior for mounted handles and hidden handles.
6. Add focused overlay/menu examples that maintain the underlying flow state
   while an overlay is visible.

## Tests To Specify

- Parser/lowering success and diagnostics for handle creation and disposal.
- Runtime tests for block exit, flow return, cancellation, save/load, and
  overlay pop cleanup.
- Native/web/observe parity tests proving hidden or disposed resources are
  absent from rendered frames, hit testing, focus navigation, and captures.
- Component-scoped capture tests for a selected handle and for a hidden handle.
- Regression tests showing existing explicit `image(...)` and `component(...)`
  presentation emissions still work.

## Constraints

- Do not redesign already implemented explicit image/component declarations or
  mount behavior unless current implementation evidence shows a concrete flaw.
- Keep resource lifecycle deterministic and serializable.
- Keep lower-level rendering crates unaware of language scopes; they should
  receive prepared presentation state only.
- Preserve existing component-scoped render capture resource identifiers.
- Avoid compatibility shims for removed or rejected syntax during the internal
  parser/compiler refactor.

## Expected Output

- A design document defining the scoped handle grammar, typed runtime contract,
  presentation snapshot operations, lifecycle rules, diagnostics, and examples.
- A migration note explaining how the design coexists with the current explicit
  mount API.
- Concrete acceptance criteria and test names for implementation.
