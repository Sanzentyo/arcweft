# Request: AW-AH-009.2 character nominal definition and rename contract

Date: 2026-07-14

## Sequence position and reason for the split

This request follows AW-AH-009 structural identity and depends on the finalized
AW-AH-009.1 registration/alias/provenance contract. It is independently
throwable once that prerequisite design is available.

The current LSP definition feature resolves presentation-style contributors,
not character manifests or typed member identities. The rename module is an
explicit placeholder. The AW-AH-009 package nevertheless marked these original
acceptance items as separate features without specifying their ownership,
locations, edits, conflicts, or failure semantics.

This request must not redesign the implemented structural nominal identity,
enum inventories, completion details, or typed hover disambiguation unless a
concrete defect is shown.

## Fixed substrate

- A character enum identity contains a validated owner and, for variants, a
  validated owning part.
- Look, part, and variant member inventories are queried by typed identity.
- Source labels are display only and have no inverse parser.
- Renaming an import/source alias does not change nominal identity.
- Renaming `CharacterId` or `CharacterPartId` is a breaking identity change and
  must not create a runtime compatibility alias.
- LSP profiles currently retain decoded manifests but not a complete typed
  manifest-token source map.

## Required decisions

1. Exact typed symbol descriptor for character owners, look members, part
   members, and per-part variant members, including manifest source provenance.
2. How a cursor token is resolved through module qualification, aliases,
   expected `CharacterNominalType`, and local member spelling without parsing a
   label.
3. Definition targets for a character reference, look, part, and variant;
   specify URI/range behavior for JSON manifests, directory manifests, imports,
   generated manifests, and unavailable sources.
4. Rename categories and scope: source alias only, public `CharacterId`, look
   ID, part ID, and variant ID. State which files and manifest references are
   edited for each category.
5. Atomic preflight, conflict detection, edit ordering, version checks, stale
   document handling, and workspace edit limits.
6. Whether public-ID and part-ID rename is offered automatically, requires an
   explicit breaking-operation flag, or is rejected by ordinary LSP rename.
7. Structured errors for ambiguous owner/member, stale inventory, missing
   provenance, read-only/generated manifest, collision, invalid replacement,
   and partial workspace coverage.
8. Cache invalidation and project/profile rebuild after a successful edit.

## Implementation order to specify

1. Freeze typed symbol/provenance and cursor-resolution APIs.
2. Preserve manifest token ranges at the I/O adapter boundary.
3. Implement go-to-definition for owners and all member families.
4. Implement alias-only rename, then explicitly gated breaking ID/member
   renames with atomic preflight.
5. Connect session capabilities, invalidation, and deterministic workspace edits.

## Required tests

- Definition for canonical, compact, qualified, and aliased owner references.
- Definition for same-spelling look/part/variant members across characters and
  across parts, resolved only by typed context.
- Alias rename changes source spellings without changing nominal identity.
- Owner and part rename follow the documented breaking-operation policy and
  update every required manifest/project/source reference atomically.
- Invalid replacement, collision, ambiguity, generated/read-only source,
  stale version, missing file, exact edit limit, and one-over limit fail without
  partial edits.
- Multi-root and simultaneous-profile projects do not leak definitions or edits
  across nominal scopes.
- No source-text gate and no `source_label()` parsing.

## Constraints and non-goals

- No compatibility aliases or migration shims for renamed public IDs.
- No ad-hoc global text replacement.
- No manifest I/O in sema, character data, or core crates.
- Do not expand rename to unrelated Arcweft symbols in this request.

## Expected output

Produce a standalone final design with exact Rust and LSP APIs, provenance and
resolution data flow, rename decision table, atomic workspace-edit algorithm,
limits/errors, cache invalidation, implementation order, and full test matrix.
