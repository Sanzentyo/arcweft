# Seq-01.6.2 Product AWBC Audio Payload Parity

## Sequence Position

This request follows seq-01.6.1 Product AWBC `RuntimeStepResult` parity
closure. Seq-01.6.1 closes the implementation-ready product AWBC runtime-step
rows without restoring structured product fallback. The remaining audio row is
split out because product AWBC currently stores only the audio operation name
in an `AwbcEffectKind::Audio` effect plan, while structured execution owns a
typed `RuntimeAudioCommand` that is evaluated into an `AudioCommandEnvelope`.

## Why This Split Is Needed

The existing design is not implementation-ready for product AWBC audio parity:

- `LineEffectRequest::Audio(Box<RuntimeAudioCommand>)` carries typed command
  payloads with `RuntimeExpr` fields.
- Runtime-plan AWBC lowering currently lowers audio effects to
  `AwbcEffectKind::Audio` with static args containing only
  `RuntimeAudioCommand::operation_name()`.
- Product-step mapping intentionally reports a typed unsupported capability
  diagnostic because it cannot reconstruct the typed audio command payload.
- Reconstructing audio by parsing string operation names would violate the
  typed-boundary rules and would not preserve expression evaluation semantics.

This request must design the canonical AWBC representation for typed audio
commands before implementation continues.

## Required Decisions

- Decide whether audio commands should be represented as:
  - dedicated AWBC audio command tables;
  - typed constants/records/variants;
  - effect-plan payload records;
  - or a small audio-specific product table referenced by `AwbcEffectPlan`.
- Specify how `RuntimeExpr` fields inside `RuntimeAudioCommand` are lowered,
  evaluated, and type-checked in product AWBC.
- Specify whether audio command evaluation belongs in compact VM instructions,
  product-step mapping, or a small owned adapter module.
- Define the canonical codec shape and verifier rules for audio payloads.
- Define the product-step failure mode for malformed audio payloads, missing
  resources, invalid identifiers, and unsupported command variants.
- Decide whether all current `RuntimeAudioCommand` variants must be supported
  in the first product row or whether a deliberately smaller supported subset
  is acceptable.

## Implementation Order To Specify

1. Add or extend AWBC schema structures for typed audio command payloads.
2. Add deterministic canonical codec support and verifier validation.
3. Lower `LineEffectRequest::Audio` into the chosen AWBC payload shape without
   stringly operation-name reconstruction.
4. Map product AWBC audio payloads to `AudioCommandEnvelope` requests through
   the existing typed runtime audio command/evaluation path or a specified
   equivalent.
5. Add differential fixtures comparing structured and AWBC product execution
   for at least one simple audio command and one expression-bearing command.
6. Add product-step malformed-payload tests and update the seq-01.6.1
   implementation note with the final audio coverage result.

## Tests To Specify

- `audio.stop_all` or another no-identifier command reaches identical
  `RuntimeStepOutput.requests.audio`, `stats.audio_commands`, stop reason, and
  facade status in structured and product AWBC execution.
- An expression-bearing command, such as bus gain or voice gain, evaluates
  bindings identically in both tiers.
- Invalid identifiers and malformed payloads produce typed diagnostics without
  panics or structured fallback.
- Product AWFB execution remains AWBC-only and source gates still reject direct
  structured bytecode product execution.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` and
  the structure audit remain clean.

## Constraints

- Do not redesign seq-01.6.1 runtime-step parity rows that are already
  implemented and verified unless the audio payload design exposes a concrete
  flaw in those rows.
- Do not add a structured product fallback.
- Do not parse audio operation names as a compatibility shim.
- Keep `arcweft-core` Sans I/O. Product-step may emit typed audio requests but
  must not call CPAL, WebAudio, filesystems, clocks, or device APIs.
- Keep data-format crates Sans I/O and deterministic.
- Prefer owned typed APIs and enum-owned behavior over ad hoc conversion
  helpers.

## Expected Output

- A concrete markdown design under `docs/reviews/requests/` or
  `docs/implementation/` that specifies the AWBC audio payload schema, codec,
  verifier, lowering, product-step mapping, and test matrix.
- A clear implementation-ready acceptance checklist for the audio parity row.
- Explicit non-goals if any current `RuntimeAudioCommand` variants remain
  future work.
