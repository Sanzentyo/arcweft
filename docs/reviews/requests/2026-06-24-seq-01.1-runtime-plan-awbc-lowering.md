# Request 01.1: RuntimePlan to AWBC Lowering

## Sequence Position

Submit this after Request 01 has produced the AWBC schema/codec/verifier/fiber
substrate, and before compact VM execution or runtime-driver migration.

This request narrows the part of Request 01 that remains insufficiently
actionable in `docs/02-runtime/executable-runtime-core.md`: how the existing
`RuntimePlan` / `FlowOp` / `RuntimeExpr` model lowers into canonical AWBC.

## Request

Please design the compiler-side AWBC lowerer in enough detail that it can be
implemented as small compiling Rust cuts.

The design should not redesign AWBC v1. Treat `arcweft-core::awbc::{schema,
codec, verify, fiber}` as the already established executable contract and
define how compiler/runtime-plan structures are translated into it.

## Why This Needs A Separate Design Cut

The executable-runtime-core overlay implements AWBC schema, codec, verifier,
fiber state, and compiled-region ABI substrate. It explicitly does not
implement or fully specify the concrete lowerer from current structured runtime
plans into AWBC.

The current Request 01 design gives broad lowering rules, but it is not yet
specific enough about:

- the exact `arcweft-runtime-plan` module/API boundaries;
- inventory construction for constants, functions, frames, content, tasks,
  sources, helpers, host calls, source maps, and display maps;
- temp/register allocation and scope layout;
- how every existing `FlowOp` and `RuntimeExpr` variant maps to AWBC;
- error reporting and source-anchor preservation;
- structured parity fixture generation before the compact VM becomes default.

## Required Design Decisions

Please provide concrete answers for:

1. Which new modules and public APIs should be added under
   `arcweft-runtime-plan`, including the shape of `awbc_lower::{inventory,
   frame, expr, flow, line, source}` or any better module split?
2. What is the typed input/output contract of the lowerer?
3. How are `RuntimePlan` entrypoints mapped to AWBC functions, frames, blocks,
   resume points, safe points, and entry records?
4. How are constants, runtime types, helper calls, host calls, resource refs,
   content units, line task groups, stream plans, source plans, display maps,
   and source maps interned deterministically?
5. How does frame-slot allocation work for locals, temps, captures, pattern
   bindings, loop variables, and call destinations?
6. What is the complete mapping from each current `FlowOp` variant to AWBC
   blocks and opcodes?
7. What is the complete mapping from each current `RuntimeExpr` variant to AWBC
   expression instructions, helper calls, branches, traps, and temps?
8. How should dialogue, choice, await, await-many, source, match, loop,
   dynamic target, host task, and effect constructs preserve current behavior?
9. Which lowerer diagnostics are required for unsupported or impossible
   structured forms, and what source spans/anchors should they report?
10. What focused tests should be added before compact VM execution exists?

## Required Implementation Order In The Design

Please propose small cuts in this order or justify a better order:

1. Add deterministic table inventories and ID allocation.
2. Add frame/slot allocation and block builder infrastructure.
3. Lower expressions and patterns with unit tests over small synthetic plans.
4. Lower flow/control operations and source/dialogue operations.
5. Emit AWBC, run `AwbcProgram::verify`, and snapshot stable codec bytes.
6. Add parity fixture generation that can feed both structured and future
   compact executors.

## Tests To Specify

The design should include tests for:

- deterministic lowering output and canonical bytes;
- one fixture per existing `FlowOp` family;
- one fixture per existing `RuntimeExpr` family;
- source/display map preservation;
- structured error spans for unsupported constructs;
- verifier rejection when lowerer invariants are intentionally broken;
- no dependency from `arcweft-core` back into compiler/runtime-plan crates.

## Constraints

- Keep `arcweft-core` Sans I/O and compiler-free.
- Keep lowering compiler-side; AWBC product payloads must not depend on
  structured `RuntimePlan`.
- Do not add compatibility shims that execute both models indefinitely.
- Do not hard-code individual sample names or enum variants when a typed
  registry or generic lowering rule is the real design.

## Expected Output

Please produce one design document with:

- affected crates/modules;
- new public/private lowerer types;
- per-variant lowering tables;
- frame/register/scope allocation rules;
- deterministic inventory rules;
- diagnostics;
- implementation cuts;
- focused tests;
- explicit non-goals.
