# Request: seq-06.16.7.1 Windows IME upstream handling investigation

## Sequence Position

This request precedes the native-player Windows TSF backend implementation
request:

- `docs/reviews/requests/2026-07-06-seq-06.16.7-native-player-windows-tsf-ime-backend.md`

It must investigate comparable Windows IME handling before Arcweft commits to a
specific backend design. Do not redesign Arcweft text-control editing,
selection, focus navigation, style, or write-back contracts unless the
investigation finds concrete evidence that one of those contracts causes the
reported behavior.

## Why This Split Exists

The current native player uses winit window IME. A reported Windows Japanese IME
case shows a small white native composition popup near the Arcweft-rendered
caret, and focus switching during conversion previously exposed a freeze path.
The freeze path has a local Arcweft state-machine fix, but the duplicate white
composition UI still needs root-cause analysis.

The user has not seen the same behavior in egui or windows-rs/reactor-based
applications, so this request asks for a comparative investigation instead of
jumping directly to a TSF rewrite.

## Required Investigation

- Identify the exact Arcweft native text-input stack in the current checkout:
  - winit version and backend crate;
  - `WindowEvent::Ime` handling path;
  - `request_ime_update` calls;
  - caret/candidate geometry data;
  - focus loss, blur, preedit, commit, and composition-end routing.
- Inspect how egui handles Windows IME in current source:
  - whether egui uses winit IME directly, a custom Win32/TSF path, viewport IME
    positioning, composition suppression, or text-edit widget policy;
  - how it updates cursor/candidate rectangles;
  - how it handles focus loss during active composition;
  - whether it renders preedit inline while suppressing native composition UI.
- Inspect how windows-rs / Win32 / TSF examples and reactor-style Windows event
  loops handle IME:
  - `WM_IME_STARTCOMPOSITION`, `WM_IME_COMPOSITION`,
    `WM_IME_ENDCOMPOSITION`, `WM_IME_SETCONTEXT`;
  - `ImmSetCompositionWindow`, `ImmSetCandidateWindow`,
    `ImmAssociateContextEx`;
  - TSF `ITextStoreACP` / document manager focus;
  - UI element suppression or display-attribute handling if used.
- Compare against winit's current Win32 backend:
  - where winit masks native composition UI;
  - where it still calls `DefWindowProc`;
  - which public `ImeRequestData` fields Arcweft can control;
  - what behavior is outside winit's public API.
- Reproduce or explain the white popup in terms of native message flow:
  - whether it is the IME composition window, candidate UI, reconversion UI,
    marked-text UI, or another platform popup;
  - why it appears for the Arcweft multiline control;
  - why egui or comparable apps do not show it, if confirmed.
- Reproduce or explain focus-switch behavior:
  - message order when the user alt-tabs or clicks another window during
    preedit;
  - whether late `Ime::Disabled` / `Ime::Commit` events should be ignored,
    committed, or cancelled by policy;
  - whether synchronous disable/blur calls can re-enter or stall native IME
    processing.

## Required Output

Return a research/design package that includes:

- exact dependency versions and source references inspected;
- a message-flow timeline for Arcweft's current path;
- a message-flow timeline for at least one egui or egui-winit path;
- a message-flow timeline for at least one windows-rs / Win32 / TSF reference
  implementation;
- root-cause candidates ranked by evidence;
- a clear statement of what is proven, what is inferred, and what remains
  unverified;
- concrete fix options with tradeoffs:
  - small Arcweft/winit-request-data adjustment;
  - winit version/update or upstream patch;
  - custom Win32 IMM adapter;
  - Windows TSF backend;
  - configurable fallback/feature gate;
- implementation order for the recommended fix;
- tests and manual evidence required before merging the fix.

## Tests And Evidence To Specify

- A Windows Japanese IME manual script that records:
  - typed text;
  - preedit text;
  - candidate window position;
  - whether duplicate white composition UI appears;
  - focus loss and return during active conversion;
  - player responsiveness after return.
- A trace format or log capture for native message/event order around focus
  loss and composition end.
- A comparison screenshot/video evidence plan for Arcweft, egui, and the chosen
  windows-rs / Win32 / TSF reference.
- Automated unit or source-gate coverage for the selected Arcweft state-machine
  policy.
- Native interactive smoke coverage for the final backend choice.

## Constraints

- Do not remove the existing player-rendered text-control contract.
- Do not hide the candidate window merely to hide the duplicate white popup;
  candidate selection must remain usable.
- Do not assume TSF is required until the comparison evidence shows winit/IMM
  cannot provide the necessary behavior.
- Do not put HWND, COM, TSF, AppKit, Android, Wayland, or web platform identity
  into shared presentation, scene, runtime-plan, or core crates.
- Do not introduce a new native backend without fallback behavior and trace-safe
  backend identity.
