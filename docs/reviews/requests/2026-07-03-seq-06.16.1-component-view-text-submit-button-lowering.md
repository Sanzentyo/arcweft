# seq-06.16.1 View text submit button lowering

## Sequence Position

This follows seq-06.16 player-rendered text submit button substrate.
Seq-06.16 added the product/runtime/player route for action buttons:

- compact View resource action button records;
- runtime presentation snapshots carrying action buttons;
- player-scene lowering to WGPU render nodes;
- pointer and keyboard activation producing the same text-control submit
  write-back path as Enter/IME send.

The authoring surface is intentionally not closed by seq-06.16. A top-level
action-button declaration would harden the wrong model. The final language
surface must be View authoring with named `style` declarations.

## Goal

Design and implement View lowering for a player-rendered `Button`
that submits a text control through the existing seq-06.16 substrate.

The user-facing shape should be View based, for example:

```arcw
pub style primary_button {
  Button:hover {
    background = rgba(54, 190, 170, 255)
  }
}

pub view FeedbackForm() {
  VStack {
    TextField(@input:.feedback)
      .placeholder("Type text")
      .submit_action(.send)

    Button("Send")
      .style(@style:.primary_button)
      .on_click {
        text_submit @input:.feedback
      }
  }
}
```

The exact syntax may change if the View grammar has a better local
shape, but the implementation must not introduce a separate resource-side
button declaration.

## Required Decisions

- Define the typed View AST for `Button`, button labels, enabled/disabled state,
  focusability, hover/pressed/focused state, and activation action.
- Define the View event body representation for text submit. It must lower to a
  typed action, not a stringly handler name.
- Decide how IME composition policy is expressed from View authoring:
  commit, cancel, or reject with a structured diagnostic.
- Decide how `TextField`, `TextArea`, and `SecureField` View elements reference
  text-control identity while early top-level text-control declarations remain
  in transition. If that spelling stays for this cut, document that it is the
  input resource declaration and `Button` is the View action surface.
- Define how `.style(@style:.name)`, inline `.style { ... }`, and state
  selectors such as `Button:hover` apply to the button.
- Define deterministic lowering from View data to
  `ViewProgramResource.action_buttons` and associated text sources/semantic
  targets.

## Implementation Requirements

- Do not add top-level action-button, button, or surface syntax.
- Do not expand transitional style syntax. Use or prepare for the root
  `style` declaration direction from seq-06.11c.
- Use the existing `arcweft-lang-syntax::ast::view` substrate where possible
  instead of creating a second View AST.
- Wire the chosen View surface through parser, CST classification,
  AST, HIR, sema, project index, symbol uses, LSP-relevant IDs, and bundle
  emission.
- Lower View button activation into the existing
  `ViewActionButtonResource` / `ViewRuntimeActionButton` route from seq-06.16.
- Update `samples/text-submit-flow/` or create a new sample that shows:
  text input, visible player-rendered submit button, Enter/IME submit, and
  button activation all reaching the same `text_submit` flow behavior.
- Keep web and native on the same player-backed render/input path. Do not use
  DOM buttons, platform widgets, hidden controls, or sidecar-only behavior.

## Tests To Specify And Implement

- Parser tests for View `Button("Send").on_click { text_submit ... }`.
- Removed top-level action-button syntax falls through structured parser
  recovery instead of being accepted as compatibility syntax.
- HIR/sema tests for unresolved text-control references, duplicate button IDs,
  invalid IME policy values, and button action type mismatches.
- Bundle tests proving View button authoring emits deterministic
  `ViewProgramResource.action_buttons` and matching text/semantic records.
- Player-scene tests proving pointer click, keyboard activation, and IME policy
  all produce typed submit write-backs or diagnostics through the same route.
- Native and web sample smoke documentation, including how to run each sample
  and where trace output is written.

## Constraints

- Do not redesign the seq-06.16 resource/runtime/player substrate unless
  implementation evidence shows a concrete flaw.
- Do not keep compatibility aliases or fallback parser branches for removed UI
  syntax.
- Keep lower-level data crates Sans I/O.
- Keep platform-specific code out of parser, HIR, sema, and bundle crates.
- Prefer typed enums and owned boundary methods over string matching helpers.
