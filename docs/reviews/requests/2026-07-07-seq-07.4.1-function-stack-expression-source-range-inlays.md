# Request: Function Stack Expression Source Ranges and Arbitrary Type Inlays

## Sequence Position

Split from
`2026-07-07-seq-07.4-function-stack-capture-effect-lsp.md` after the
function-stack implementation established let-binding RHS source ranges and
function-valued `let` inlays.

## Why This Split Is Needed

Current sema records source ranges only for parser-provided `let` RHS roots.
That is enough for inferred function-valued `let` inlays, but it is not a
complete contract for arbitrary expression inlays. The source AST `Expr` nodes
do not own stable spans for every expression family, nested call argument,
selector target, closure body, branch condition, dialogue interpolation
expression, or block value.

Implementing arbitrary inlays without a first-class expression-span contract
would couple LSP traversal order to sema judgment order and would fail under
nested expression rewrites such as pipe-placeholder substitution, partial
placeholder abstraction, method-chain fallback, and closure body checking.

This request must not redesign the existing implemented let-binding inlay
path unless the design finds a concrete correctness flaw. Treat the current
`let` RHS range matching as the already-verified substrate.

## Current Implementation Progress

As of 2026-07-08, this request is partially implemented well beyond the
original `let` RHS root boundary. Source-backed expression judgments now cover
many authored expression families, including function-like body values,
control expressions, value-producing blocks, pipe/desugared expressions,
selector expressions, dialogue interpolation and dialogue calls, action/defer
and assignment expressions, control-transfer expressions, container child
expressions, computation blocks, braced closures, guarded `if let`, effect and
prefix expressions, `wait(...)`, and dialogue-call line-plan colon blocks such
as `let cue = at(...):`, plus thread expression body statement sources.

The request remains open for the audit/closure pass: identify expression
families that are still untested or missing ranges, add focused coverage, and
add internal diagnostics or stats for judgments that should have a source range
but do not.

## Required Decisions

- Define whether expression spans live directly on `Expr`, in a side table keyed
  by stable syntax node identity, or in a lowering inventory produced alongside
  HIR.
- Define the stable identity used to connect syntax/HIR expression sites to
  sema `TypeExpressionId` judgments after desugaring and expected-type
  checking.
- Define how generated/desugared expressions report source ranges:
  - pipe RHS `^` substitution;
  - data-last call rewriting;
  - `_` partial-placeholder abstraction;
  - implicit returned closure proxy callables;
  - generated expression nodes introduced by HIR lowering.
- Define which expression judgments should produce LSP type inlays by default.
  Avoid noisy inlays for every literal or trivial path unless a profile/lint
  policy explicitly enables them.
- Define suppression rules for explicit type ascriptions, explicit closure
  return types, diagnostics-producing expressions, and generated/no-source
  expression nodes.
- Define line/column placement for expression inlays:
  - after the expression;
  - after callee/selector;
  - after binding pattern for `let` forms;
  - inside dialogue interpolation or rich-text fragments.
- Define snapshot and diagnostic policy for stale/mismatched expression-span
  inventories.

## Implementation Order

1. Add the expression-span inventory at the syntax/HIR boundary without
   changing type-checking behavior.
2. Thread expression-span identity through sema `TypeJudgment` recording for
   every expression family that has a stable source site.
3. Keep existing `LetBinding` inlay matching intact, but migrate it to the same
   inventory once the inventory proves equivalent on current tests.
4. Add LSP policy for arbitrary expression type inlays. Default should remain
   conservative and profile-gated until the output is ergonomic.
5. Add diagnostics or internal warnings for sema judgments that should have a
   source range but do not.
6. Add runtime-plan/compiler tests only where typed expression evidence depends
   on the new identity contract. Do not use inlay-only spans as runtime
   lowering evidence unless the contract explicitly says they are stable enough.

## Tests To Specify

- Nested call argument expression judgments carry the exact argument source
  range.
- Selector and method-chain fallback expressions carry the visible selector or
  full expression range according to the chosen policy.
- Pipe RHS with `^` keeps source ranges attached to authored RHS sites and does
  not pretend the substituted LHS was authored inside the RHS.
- Data-last pipe without `^` reports the authored RHS call range and separately
  records the LHS source range if needed.
- `_` partial-placeholder abstraction records authored placeholder body ranges
  and distinguishes expression `_` from pattern wildcard `_`.
- Closure body expressions carry ranges inside both inline and braced closure
  bodies.
- Dialogue interpolation expressions carry source ranges relative to the
  original `.arcw` document, not only the virtual dialogue fragment.
- Existing inferred function-valued `let` inlays remain byte-for-byte
  equivalent after migration to the shared inventory.
- LSP arbitrary expression inlays are profile-gated and do not appear for
  literals/trivial paths under the default profile unless explicitly enabled.

## Constraints

- Do not make `arcweft-lang-syntax` depend on sema, LSP, CLI, runtime-plan, or
  runtime crates.
- Do not make sema depend on LSP types.
- Preserve structured diagnostics with stable codes.
- Do not add compatibility shims or traversal-order fallback paths that silently
  accept missing source identities.
- Keep parser recovery spans distinct from expression spans. Recovery ranges
  should not be treated as authoritative typed expression sites.

## Expected Output

- A source-span/identity contract for expression judgments.
- Syntax/HIR/sema implementation and tests for expression source ranges.
- LSP policy and tests for arbitrary expression type inlays.
- Updated implementation evidence under `docs/implementation/`.
