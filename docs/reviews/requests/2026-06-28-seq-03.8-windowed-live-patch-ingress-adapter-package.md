# Seq-03.8 Request: Windowed Live Patch Ingress Adapter Package

## Sequence Position

This follows seq03.5 and seq03.7. Seq03.1 through seq03.4 added generation
runtime semantics and `WindowedRuntimeOwner`; seq03.5 should wire the owner into
`scene_windowed.rs`; seq03.7 should add real windowed live-patch smoke fixtures.

## Request

Design and implement the adapter-side ingress path that feeds typed live-patch
events into an already running windowed native player. The package must keep
transport, filesystem watching, local sockets, and trust/release policy outside
`arcweft-runtime-driver`.

Return the final work as a zip package in the established overlay-package
format. The package must include Rust implementation, focused tests,
implementation notes, and validation instructions.

## Required Scope

- Add a narrow adapter-owned ingress API for pushing `WindowedPatchEvent` values
  into the windowed event loop.
- Support the first development transport needed by `arcw run --watch` or an
  equivalent local sidecar producer.
- Preserve the event-loop mutation rule: adapters may enqueue events, but only
  the event-loop owner may mutate session/catalog/runtime state at
  `FrameBoundary::AfterRenderSubmitted`.
- Keep release archive fetch, HTTP mirrors, signature verification, and trust
  policy above this layer. This request may consume already verified local bytes
  or already materialized local sidecars, but must not implement release trust
  logic.
- Provide typed errors and retained reports for malformed ingress messages,
  disconnected event-loop proxies, wrong base roots, and unsupported transport
  actions.

## Required Decisions

- Should the first ingress be a `winit::EventLoopProxy` custom event, an
  embedding handle, or both?
- Which crate should own the ingress adapter: `arcweft-player-native`,
  `arcweft-cli`, or a small adapter module bridging them?
- How should `arcw run --watch` discover and enqueue local patch sidecars
  without giving `arcweft-runtime-driver` filesystem responsibilities?
- What backpressure or coalescing rule should apply if patches arrive faster
  than frame boundaries?
- Which status should be observable by CLI/dev tooling before a patch reaches
  the safe frame boundary?

## Tests To Specify And Implement

- Adapter enqueues a content-only patch event without directly mutating the
  session.
- Multiple queued events preserve FIFO ordering or follow an explicitly
  documented coalescing rule.
- Disconnected event-loop proxy or closed player reports a typed adapter error.
- Malformed sidecar/local bytes are rejected into the retained report path.
- Wrong-base patch does not mutate the active session/catalog.
- `arcw run --watch` or the chosen dev entrypoint has a deterministic smoke
  test or a documented platform-gated validation command.

## Constraints

- Do not add filesystem, socket, network, release, signing, or trust dependencies
  to `arcweft-runtime-driver`.
- Do not introduce cross-thread mutable access to `BundleSession`,
  `BundleImageCatalog`, renderer state, or window state.
- Do not redesign seq03 generation semantics or seq02 release/trust policy.
- Do not use `unsafe` or unstable Rust.
- Prefer typed events and owner methods over stringly dispatch.

## Expected Zip Contents

- `overlay/` implementation files.
- Focused tests under the owning crate or crates.
- `docs/implementation/seq-03-8-windowed-live-patch-ingress-adapter-2026-06-28.md`
- `VALIDATION.md` with commands run, platform used, and blocked window/GPU
  validation if any.
- `README.md` with assumptions, apply order, acceptance criteria, non-goals, and
  explicit dependency on seq03.5/seq03.7.

## Parallelization Guidance

Design can begin in parallel with seq03.5 and seq03.7, but implementation should
wait until seq03.5 defines the concrete event-loop owner integration and seq03.7
defines the fixture/regeneration path. It is independent of seq03.6 unless
seq03.6 changes the public entry/fiber API consumed by windowed restart or
new-entry binding.
