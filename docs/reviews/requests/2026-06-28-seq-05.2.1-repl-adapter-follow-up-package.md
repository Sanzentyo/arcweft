# Seq-05.2.1 Request: REPL Adapter Formatting And Host Adapter Follow-Up Package

## Sequence Position

This follows seq05.2 and consumes the accepted seq05.1 transaction/session substrate, the accepted seq05.2 typed command/result API, and the accepted seq05.3 warm/codegen command handler surface.

Seq05.2.1 is an adapter follow-up. It must not redesign `arcweft-agent-repl::command`, the seq05.1 session state machine, or the seq05.3 tiering manager. Its job is to make existing frontends and host/runtime adapters consume the typed command API cleanly.

## Boundary Decision

Seq05.2 owns typed command semantics. Seq05.2.1 owns adapter presentation and integration:

- CLI REPL formatting for `ReplCommandResult`;
- MCP/LSP formatting adapters where those surfaces already expose Agent/REPL command output;
- runtime-driver-backed host adapters for task/cancel command behavior;
- deterministic tests proving adapters format typed evidence without peeking into command/session internals.

This package must keep `arcweft-agent-repl` Sans I/O except for existing adapter traits. Filesystem, terminal, MCP, LSP, runtime-driver task ownership, and process-facing formatting belong in adapter/tooling crates.

## Request

Design and implement the seq05.2 adapter follow-up for typed REPL command results and host task/cancel integration.

Return the final work as a zip package with design, Rust implementation overlay, tests, validation notes, and apply instructions.

## Required Decisions

1. Which crate owns human-readable CLI formatting for `ReplCommandResult`.
2. Whether CLI formatting should be a reusable formatter module or a thin adapter around a formatter trait/value type.
3. How each `ReplCommandEvidence` variant formats without lossy stringly conversion inside `arcweft-agent-repl`.
4. How large evidence values should be summarized, paginated, or rendered in JSON mode.
5. How `Warm` and `Codegen` evidence from seq05.3 should format deterministically.
6. Which MCP/LSP surfaces need immediate formatting adapters, and which should remain documented future work.
7. How `:tasks` and `:cancel` should be backed by runtime-driver task state without duplicating scheduler ownership.
8. How read-only trace mode interacts with task/cancel adapters.
9. How adapter errors map to typed `ReplCommandDiagnostic` values rather than ad hoc strings.
10. Which integration tests prove existing CLI/MCP/LSP behavior uses the typed result model.

## Required Implementation

- Add or update CLI REPL code so command input is parsed through `parse_repl_input` / `parse_repl_command` and displayed from `ReplCommandResult`.
- Add a deterministic formatter for all accepted `ReplCommandEvidence` variants, including:
  - cell list and cell submission rejection;
  - observe/step/tasks/cancel/load/reload;
  - undo/reset summaries;
  - capabilities/generations/bindings/tiers;
  - warm/codegen evidence from seq05.3;
  - diagnostics and rejected/read-only command results.
- Preserve JSON output as typed structured data where the CLI already supports JSON; do not reparse formatted text.
- Add MCP/LSP adapter implementations or explicit no-op/design notes for surfaces that are not yet present.
- Add runtime-driver-backed task/cancel host adapter implementation where the current runtime-driver surface is sufficiently stable.
- If task/cancel runtime-driver ownership is not sufficiently stable, return a narrow typed adapter trait plus a follow-up request instead of hard-coding task state into `arcweft-agent-repl`.
- Add tests for CLI formatting and host adapter behavior.
- Add implementation documentation under `docs/implementation/`.

## Expected Adapter Surface

The final design should expose an adapter-facing boundary equivalent to:

```rust
pub struct ReplCommandFormatOptions;
pub struct ReplCommandFormattedOutput;

pub trait ReplCommandResultFormatter {
    fn format_result(
        &self,
        result: &ReplCommandResult,
        options: &ReplCommandFormatOptions,
    ) -> ReplCommandFormattedOutput;
}
```

This is not a required exact API. If the implementation chooses a different shape, explain why it is cleaner in the design and implementation notes.

Runtime-driver task/cancel integration should use an owned adapter boundary equivalent to:

```rust
pub trait ReplTaskHostAdapter {
    fn list_tasks(&mut self, command: &TasksCommand) -> ReplCommandResult;
    fn cancel_task(&mut self, command: &CancelCommand) -> ReplCommandResult;
}
```

The final implementation may use existing `ReplCommandHost` methods if that is the better current boundary. Do not add a parallel adapter trait unless it removes real duplication or matches existing ownership.

## Acceptance Criteria

- CLI REPL uses typed `ReplCommandResult` formatting rather than a separate stringly command table.
- Formatting covers every current `ReplCommandEvidence` variant, including seq05.3 warm/codegen evidence.
- JSON-capable outputs remain structured and deterministic.
- MCP/LSP adapter status is either implemented or explicitly documented as not present / future work with evidence from current source inspection.
- Runtime-driver task/cancel behavior is adapter-owned and does not duplicate task scheduler state inside `arcweft-agent-repl`.
- Product players remain free of REPL/CLI/MCP/LSP dependencies.
- Read-only trace mode still rejects mutating task/cancel behavior.
- Tests cover success, rejected/read-only, diagnostics, and unsupported-adapter paths.

## Non-Goals

- Do not redesign seq05.1 transaction/session APIs.
- Do not redesign seq05.2 command parsing or evidence ownership.
- Do not redesign seq05.3 tiering/warm/codegen behavior.
- Do not implement a new REPL protocol or product-player command surface.
- Do not add JIT/AOT execution, persistent compiled cache, or background scheduler semantics.
- Do not put terminal, MCP, LSP, runtime-driver, filesystem, or process I/O inside low-level REPL command model modules.

## Parallelization Guidance

This can be designed after seq05.2 and seq05.3 are accepted. It can run in parallel with later seq05 backend work because it should treat warm/codegen evidence as typed formatter input, not as an executor implementation detail.

For best results, ask for design plus implementation package in one pass. If runtime-driver task/cancel ownership is found insufficient, require the package to return a small follow-up request for that specific adapter rather than broadening seq05.2.1.
