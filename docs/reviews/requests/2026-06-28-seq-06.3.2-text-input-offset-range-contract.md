# Request 06.3.2: Text Input Offset and Range Contract

## Sequence Position

This is a split-out contract design request from seq06.3. It should be resolved
before platform-specific adapter implementation for APIs that primarily expose
UTF-16 or platform-native text positions, especially Windows TSF, macOS
`NSTextInputClient`, Android `InputConnection`, and iOS `UITextInput`.

This request may run in parallel with seq06.3.1, seq06.3.3, and seq06.3.4. It
must preserve the existing session, focus generation, serial, privacy, and
TextField preedit model unless evidence shows a concrete contract flaw.

## Why This Split Is Needed

Arcweft already has `TextByteOffset`, `TextUtf16Offset`, and
`TextScalarOffset`, but the current platform-normalized text operations mostly
carry byte-oriented ranges. Many platform IME APIs use UTF-16 code-unit offsets,
opaque text positions, or platform range objects. The design must define where
conversion happens, how invalid boundaries are rejected, and how delete
surrounding behaves around emoji, combining marks, surrogate pairs, and
grapheme clusters.

Without this design, each adapter may invent local conversion rules and create
subtle corruption bugs around Japanese IME, emoji, and mobile keyboard deletion.

## Required Research

Review range and offset behavior for:

- Web EditContext:
  - MDN `EditContext`: https://developer.mozilla.org/en-US/docs/Web/API/EditContext
  - W3C EditContext draft: https://w3c.github.io/edit-context/
- Windows TSF:
  - Microsoft Text Services Framework: https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework
- macOS AppKit:
  - Apple `NSTextInputClient`: https://developer.apple.com/documentation/appkit/nstextinputclient
- Wayland text-input-v3:
  - wayland-protocols XML: https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/unstable/text-input/text-input-unstable-v3.xml
- Android:
  - Android `InputConnection`: https://developer.android.com/reference/android/view/inputmethod/InputConnection
- iOS:
  - Apple `UITextInput`: https://developer.apple.com/documentation/uikit/uitextinput

The research must identify the native index unit, range semantics, invalid
range failure behavior, and delete-surrounding unit for each API.

## Required Decisions

1. Whether `TextInputOperation` should keep byte ranges, accept UTF-16 ranges,
   or use a boundary-checked range wrapper that records the source unit.
2. Where offset conversion belongs: platform adapter, runtime-host dispatch,
   TextField edit policy, or a shared Sans I/O text indexing module.
3. How adapters should validate that byte, scalar, UTF-16, and grapheme
   boundaries are legal before emitting a `PlatformTextInputEvent`.
4. How `DeleteSurrounding` should map platform requests expressed in UTF-16,
   Unicode scalar, byte, or grapheme units.
5. How replacement ranges in preedit and commit operations should behave when
   platform APIs specify replacement by native range object rather than numeric
   offsets.
6. How secure redaction changes surrounding text and selection offsets without
   making platform callbacks impossible to validate.
7. Whether failed conversion should reject the event, clamp to legal
   boundaries, request a fresh snapshot, or end the session.
8. Which conversion helpers should be inherent methods or typed contexts rather
   than free-standing `{source}_to_{target}` helpers.

## Required Output

Produce an implementation-ready design markdown that contains:

- a platform-by-platform offset-unit matrix;
- exact Arcweft canonical range rules for committed text, preedit text,
  selection, replacement, character bounds, and delete-surrounding;
- proposed Rust type/API changes, if any;
- conversion and validation algorithms for UTF-8, UTF-16, scalar, and grapheme
  boundaries;
- error and diagnostic policy for invalid platform ranges;
- secure-field redaction offset policy;
- implementation order and tests;
- a list of platform-specific questions that remain for adapter requests.

If code changes are proposed, include the exact files to edit and the expected
public API after the change.

## Implementation Order To Specify

1. Add or refine shared text index conversion APIs in the lowest appropriate
   Sans I/O crate.
2. Update `TextInputOperation` or construction APIs only if required.
3. Add runtime-host validation for platform event ranges if validation cannot
   live entirely in adapters.
4. Update TextField editing tests for emoji, combining marks, Japanese preedit,
   and surrogate-pair delete-surrounding.
5. Update platform request documents to reference the canonical range policy.

## Tests To Specify

- UTF-16 delete-surrounding around a surrogate pair does not split text.
- Combining marks and grapheme clusters are deleted according to the requested
  unit.
- Replacement ranges reject invalid byte boundaries.
- Platform UTF-16 ranges convert to canonical Arcweft ranges deterministically.
- Secure snapshots expose redacted offsets that cannot leak original text
  length where the security policy forbids it.
- Invalid platform ranges produce structured diagnostics and do not mutate the
  document.

## Constraints

- Do not duplicate conversion algorithms in each platform adapter.
- Do not accept invalid UTF-8 boundaries silently.
- Do not expose secure-field text or original private range metadata.
- Keep data-format and presentation crates Sans I/O.
- Prefer owned type methods or named contexts over scattered conversion helper
  functions.

## Non-Goals

- Implementing native TSF/AppKit/Wayland/Android/iOS/Web adapters.
- Redesigning TextField layout or rendering.
- Supporting rich-text document editing beyond plain TextField/TextArea ranges.
