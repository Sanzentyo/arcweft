# Request: seq-06.11d.5.1 native Style trace contract

Date: 2026-07-14

## Sequence position and independence

This first design-only cut after the native-only Style resolver defines the
portable explainability boundary for later Agent/LSP work. It is a completely
new, independently throwable request whose result must not be appended to an
older Style or CSS request.

It does not authorize production implementation; unrelated native Style work
may continue in parallel.

## Goal

Specify one typed, deterministic, bounded, and redactable contract that can
explain why a native Style property won, lost, inherited, or failed to apply to
one concrete runtime View node. The result must be suitable for in-process
debugging and for projection into a future wire protocol without making wire
concerns part of the resolver.

Close the gap between internal trace and stable tooling with exact Rust APIs,
wire schema, source maps, budgets, redaction, caching, and diagnostics. An
implementation agent must not invent any of them.

## Fixed native-only substrate

The following substrate is already implemented and is not a design question:

- `.arcw` has one native typed Style language. CSS source, syntax selectors,
  raw CSS bodies, external stylesheets, and Takumi are absent.
- Syntax lowers through native HIR and `CheckedViewStyleCatalog` into a
  sheet-owned `ViewStyleProgram`.
- Static View producers carry ordered `ViewStyleApplicationTarget` values.
  Runtime materializes complete `ViewStyleApplication` values once mount,
  scope, order, depth, and View-boundary facts are known.
- `arcweft-view::style::ViewStyleResolver` is the only cascade owner.
  `arcweft-bundle` and player crates only project its typed result.
- `ComputedViewStyle` retains typed values and winning provenance. Resolver
  inputs include node facts, visible ancestry, applications, parent computed
  Style, presentation environment, revisions, and trace mode.
- The winner tuple is scope depth, application order, selector predicate
  specificity, selector element specificity, rule source order, then
  declaration order. Later tuple values win.
- Inheritance copies only properties marked inheritable. Token lookup is
  sheet-owned. Inline token use requires one unambiguous owner. Nested-View
  traversal is permitted only by explicit boundary facts.
- Current internal trace modes are `Off`, `Winners`, and `Full`. Current events
  report winners, accepted/rejected contributions, rule rejection, and patch
  rejection. Full tracing bypasses the computed cache; winners can be rebuilt
  from cached computed provenance.
- Resolver work and cache limits already exist. The default maximums are 4,096
  applications, 65,536 rules, 262,144 contributions, 65,536 inventoried
  tokens, 262,144 selector steps, token depth 64, and 1,024 cache entries.
- Style sheets and patches retain source identities/ranges. The bundle carries
  canonical `SourceRangeRef` inventories; source content and path hydration
  remain adapter concerns.

Do not redesign this substrate unless the design identifies a concrete,
reproducible defect that makes the requested contract impossible.

## Questions the trace must answer

For a requested node and property, the contract must answer when evidence is
available:

1. What typed value is effective and what invalidation class it belongs to.
2. Whether the value is inherited, supplied by a named sheet, or supplied by
   an inline patch.
3. Which application, rule, selector, declaration, and source range produced
   the winner, and which competing contributions lost by what priority.
4. Why a rule or patch did not contribute, including selector facts, boundary
   blocking, environment/container facts, applicability, and budget.
5. How tokens and append/replace operations produced the typed final value
   without a second cascade.
6. Whether result/evidence came from cache, was reconstructed or collected,
   and what mode, filter, budget, source-map, or redaction omitted.

## Required typed API decisions

Provide exact Rust definitions and ownership for all public or crate-boundary
types. At minimum decide:

- a typed trace query identifying node, optional property set, evidence level,
  inclusion flags, trace budget, and redaction ceiling;
- a result envelope carrying computed revision, program/application/fact
  revisions, cache disposition, completion state, ordered evidence, and
  structured diagnostics;
- stable typed identities for node, sheet, patch, application, rule,
  declaration, selector step, token, source range, and property;
- an event algebra for winner, inheritance, token expansion, assignment,
  contribution/rejection, and omitted or truncated evidence;
- a typed source-location projection that distinguishes available, withheld,
  unavailable, stale, and malformed mappings;
- errors for invalid query/identity/range/reference, stale revision,
  authorization/redaction refusal, and each budget class.

State which types remain internal to `arcweft-view`, which transport-neutral
DTO crate owns portable records, and which adapter hydrates source locations.
Lower-level crates must remain Sans I/O and must not depend on Agent, LSP, CLI,
filesystem, renderer, or platform crates.

Do not expose a free-standing field-by-field conversion helper as the shared
boundary. Use an inherent conversion, `TryFrom`, or a named trace projection
context according to whether source maps, policy, and allocation are needed.

## Required wire-schema decisions

Specify one canonical serialized form for the portable trace DTO. Include:

- the schema identifier and exact JSON field/enum representation;
- required versus optional fields and unknown-field behavior;
- integer widths, range conventions, typed value representation, and ordering;
- how opaque IDs are encoded without asking clients to parse display strings;
- completion, truncation, omission, and redaction markers;
- diagnostic code, severity, labels, related evidence, and source location;
- at least one complete winner example and one rejected/truncated example.

Decide whether the schema is a complete response or a page/resource payload.
If paging is selected, define a typed cursor bound to the query, node,
revisions, redaction ceiling, and evidence ordering. A cursor must be validated
as untrusted input and must not be a serialized internal pointer or cache key.

The format is unreleased. Choose the best single initial shape; do not define a
legacy reader, alias, deprecated field, dual version, or migration shim.

## Budgets, ordering, and completion

Define independent limits for requested properties, emitted events, source-map
lookups, hydrated source bytes/snippets, token-chain evidence, ancestor facts,
serialized bytes, and pages/cursors. State defaults and hard maxima.

Evidence order must be deterministic across runs and backends. Specify the
order for multiple properties, applications, rules, declarations, token steps,
and diagnostics. Budget exhaustion must return a typed partial/completion
state; it must not silently look like a complete explanation or change the
computed result.

Trace budgets are observability budgets. They must not weaken or raise the
existing resolver correctness budgets, and tracing must never change which
property wins.

## Source maps and redaction

Define how typed Style source references map through merged bundles and loaded
source maps to source identity and half-open byte ranges. Cover missing source
content, absent maps, stale document revisions, invalid UTF-8 boundaries,
tampered range ownership, and generated Style with no authored range.

Classify every potentially sensitive field: typed values, token values,
resource identifiers, node/part names, module/source identities, filesystem
paths, source snippets, environment facts, and diagnostics. Define redaction
before serialization and before cache insertion. A lower-privilege response
must not reveal hidden data through hashes, lengths, ordering, diagnostic text,
cursor contents, or cache-hit behavior.

The core trace may retain typed values needed for correctness, but portable
projection must be policy-driven. Redaction must preserve typed reasons such as
`withheld` without inserting a fake value into the computed Style.

## Cache contract

Specify cache identity and lifecycle for computed results and any projected
trace pages. The key must account for node/fact/application/environment/source
revisions, query filters, trace mode, source-map revision, and redaction
ceiling where relevant. Define invalidation, deterministic eviction, stale
cursor rejection, and whether redacted results may share underlying computed
data without sharing projected evidence.

Preserve current semantics: full evidence cannot be fabricated from a cached
computed winner, and requesting full trace may bypass the computed cache.
`Off` must remain allocation-free for trace evidence in normal runtime use.

## Diagnostics contract

Separate resolver failure, trace-query failure, evidence omission, and
source-map/redaction status. Provide stable native-Style diagnostic codes and
tight typed labels where a source range exists. Do not create CSS-removal
diagnostics: deleted CSS spellings continue through ordinary `syntax.parse`
recovery and never enter this trace contract.

State which failures make the query fail, which return a valid partial result,
and which are per-event status. Messages are presentation; clients must route
on typed codes and fields.

## Constraints and non-goals

- No CSS/Takumi parser, carrier, adapter, diagnostic, cascade, or compatibility
  path may be introduced.
- Do not add a second resolver, recompute winners in tooling, or project typed
  values through property-name strings.
- Do not change verified cascade, inheritance, token, boundary, or application
  rules without defect evidence.
- Do not persist ordinary runtime traces in AWFB products. The design may
  define an external debug artifact only if ownership, privacy, and budgets are
  explicit.
- Do not make display labels, source paths, vector ordinals, or JSON spelling
  into semantic identity.
- Do not add compatibility aliases, dual readers, deprecated fields, source
  gates, or tests that grep implementation text.
- Mutation, live Style editing, renderer inspection, pixel capture, and a
  general execution trace are outside this request.

## Implementation order to specify

1. Freeze the typed query/result/event/source/redaction/error model and crate
   dependency direction.
2. Add behavior tests at the existing resolver boundary before transport work.
3. Implement one policy-aware projection from internal evidence to the
   portable DTO.
4. Implement canonical encode/decode and untrusted-input validation.
5. Add source-map hydration behind an adapter-owned context.
6. Add bounded paging/caching only after deterministic complete results pass.
7. Integrate no Agent or LSP surface in this cut; hand the DTO contract to the
   next independent requests.

## Required test matrix

- Positive: named sheet, patch, inheritance, token chain, append/replace, state,
  environment, and boundary explanations match `ComputedViewStyle`.
- Negative: unknown identities, ambiguous token owner, blocked boundary,
  unavailable facts, stale revisions, and bad source maps have typed outcomes.
- Tamper: invalid enums/IDs/owners/ranges/cursors, duplicate events, trailing
  data, and unknown fields are rejected without panic or disclosure.
- Budget: each limit has exact/one-over tests; deterministic truncation never
  changes the winner.
- Redaction: every ceiling covers values, paths, snippets, diagnostics,
  cursors, hashes, lengths, and cache reuse.
- Cache: hit/miss, invalidation, FIFO eviction, winner reconstruction, full
  bypass, stale page, and privilege isolation are deterministic.
- Backend: equal snapshots yield byte-equivalent native/web/headless traces;
  projection failures are not cascade outcomes.
- Round-trip: typed DTO to canonical wire to typed DTO is stable, including
  partial and redacted responses.

## Expected design output and acceptance

Produce a new standalone design document or package containing:

- normative Rust type definitions and a crate/dependency diagram;
- the complete wire schema with valid, partial, redacted, and invalid examples;
- ordering, identity, source-map, budget, paging, cache, redaction, and
  diagnostic tables plus the complete required test plan;
- explicit non-goals and any unsupported cases.

The request is complete only when every required decision has one final answer,
the examples agree with the Rust and wire types, untrusted input and privacy
behavior are testable, and an implementation agent can proceed without reading
another request or redesigning the existing native resolver.
