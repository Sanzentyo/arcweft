## Candidate Root Cause

The strongest candidate is a contract mismatch between renderer glyph layout and
editor/IME geometry:

- `arcweft-render-wgpu` uses glyphon layout for runtime text controls.
- `crates/arcweft-render-wgpu/src/geometry/text_controls.rs` maps display glyph
  ranges back to source byte ranges through `source_range_for_display_range`.
- `crates/arcweft-render-wgpu/src/text_editor_geometry.rs`
  `TextEditorGeometryPump::layout_from_laid_out_text` currently converts
  `LaidOutText.glyphs` directly into `TextEditorGlyphGeometry`.
- `crates/arcweft-presentation/src/text_editor.rs`
  `TextEditorLayout::from_renderer_parts_for_text` requires the resulting
  ranges to be monotonically ordered and non-overlapping.

That editor contract is reasonable for caret, hit-test, selection, and IME
rectangles, but renderer glyphs are not necessarily one-to-one with editable
text ranges. Mixed-script and fallback-heavy candidates such as `( ﾟДﾟ)` can
produce multiple glyphs for the same source byte range. Passing those raw glyphs
through as editor geometry causes `OverlappingGlyphRange`.

This is probably not the same root cause as the earlier white native composition
window issue. The earlier issue concerned native IME UI suppression. This issue
is after Arcweft has accepted IME input and is preparing renderer/editor
geometry for the focused text control.

## Review Questions

Please review these points before implementation:

1. Is the contract correct that `TextEditorLayout` should receive editor
   cluster/character geometry, not raw renderer glyph geometry?
2. For identical non-empty ranges such as `18..22` and `18..22`, is it correct
   to merge them into one editor cluster geometry by unioning their bounds?
3. Should partial overlaps, such as `18..22` and `20..25`, be rejected as a
   mapping bug, normalized into cluster geometry, or handled by a separate
   shaping-cluster model?
4. How should collapsed ranges (`x..x`) used as caret anchors for empty text,
   soft wraps, and newline anchors interact with non-empty glyph ranges?
5. Should normalization happen in
   `TextEditorGeometryPump::layout_from_laid_out_text`, or earlier in
   `geometry/text_controls.rs` while building `LaidOutText` for text controls?
6. Should `TextEditorGlyphGeometry` be renamed or split to make the contract
   explicit, for example `TextEditorClusterGeometry` versus renderer glyphs?
7. Should a layout geometry error ever tear down the native player, or should
   the frame degrade to a monospaced/previous-geometry fallback while emitting a
   diagnostic?
8. Why does the trace snapshot show `composition: null` around `set_composition`
   updates? Is that expected because the current bridge only records committed
   control state, or does it indicate a second bug in preedit snapshot plumbing?

## Proposed Repair Shape To Review

Preferred repair direction:

1. Keep `TextEditorLayout` strict. Editor layout should remain a validated,
   non-overlapping geometry model for editing operations.
2. Add a renderer-to-editor normalization step at the renderer boundary.
3. Sort renderer glyphs by `(range.start, range.end, visual position)`.
4. Merge identical non-empty ranges into one editor geometry by unioning their
   bounds.
5. Preserve collapsed caret anchors only when they represent distinct caret
   stops, and prevent them from causing false overlap with non-empty glyphs.
6. Treat partial overlaps as a separate review decision. Do not silently union
   them until the reviewer confirms the intended shaping-cluster semantics.
7. Add trace/debug output, at least behind a development-only path, that can dump
   text control id, display text, source text, renderer glyph ranges, normalized
   editor ranges, and any dropped/merged ranges.
8. Add regression tests for Japanese IME-style mixed script conversion,
   especially `( ﾟДﾟ)`.

## Suggested Tests

The review should specify exact tests, but the likely minimum set is:

- Unit test in `arcweft-render-wgpu` where two laid-out glyphs have the same
  source range and are normalized into one editor geometry.
- Unit test where `( ﾟДﾟ)`-like mixed-script/fallback glyph ranges do not produce
  `OverlappingGlyphRange`.
- Unit test that collapsed caret anchors do not invalidate otherwise valid
  non-overlapping geometry.
- Negative or diagnostic test for partial overlap if the design chooses to
  reject it.
- Native/manual validation command using `samples/modern-feedback-view` and
  `--text-input-trace-out`, with MS IME Japanese conversion from `kaomoji` to
  `( ﾟДﾟ)`.

## Constraints

- Do not fix this by disabling native IME or hiding the candidate path.
- Do not solve this by accepting arbitrary overlapping editor geometry without
  defining hit-test, caret, selection, and IME rectangle behavior.
- Keep `arcweft-presentation` renderer-agnostic. Renderer-specific glyphon
  behavior should not leak into presentation contracts.
- Local real-machine traces under `target/` are evidence, not checked-in golden
  fixtures.
- The final implementation should preserve native/web/observe geometry parity
  expectations where applicable.
