## Problem

The current Web IME sample accepts simple `EditContext` updates, but the
candidate window can appear at the viewport upper-left, a native/browser caret
can appear separately from Arcweft's teal caret, and normal text-field editing
operations do not work. The sample currently renders a fixed caret after the
composition span and does not maintain a real selection model.

## Request

Produce a final zip package with concrete design, implementation overlay,
tests, fixtures, validation notes, and apply instructions for a production
Web `EditContext` text-field path that owns candidate geometry, visible caret
policy, selection, pointer hit-testing, keyboard movement, deletion, and
shortcut commands.

## Required Decisions

1. Whether this package supersedes seq06.4a.1 or layers on top of it.
2. The Web player-owned editor state object that owns text, composition,
   selection, revision, caret geometry, and character bounds.
3. How the visible caret policy works:
   - Arcweft-rendered TextField has one visible Arcweft caret.
   - Browser/native caret is hidden when the platform permits it.
   - If native caret cannot be hidden, it must be synchronized or the package
     must document an exact browser limitation and visual fallback.
4. How EditContext text/selection is updated after Arcweft applies edits.
5. How caret and character rectangles are computed from rendered text layout and
   sent to EditContext so IME candidates appear near the edited range.
6. How pointer hit-testing maps screen coordinates to byte/UTF-16 offsets.
7. How keyboard movement maps arrow, word, line, home/end, delete, backspace,
   and shift-selection to `TextEditCommand`.
8. How clipboard shortcuts are handled without leaking secure text.
9. How composition ranges, target-converted segments, and selected composition
   ranges are painted.
10. How unsupported browsers report typed unsupported state without hidden
    textarea or contenteditable fallback.

## Required Implementation

- Move the sample away from manual `modelText` ownership. It may display status,
  but the Web player/editor bridge must own text and selection state.
- Replace the static `.caret` sample behavior with a caret rendered from the
  editor selection/caret snapshot.
- Add selection rendering for collapsed and ranged selections, including IME
  preedit selection.
- Pump geometry updates from rendered TextField layout to Web `EditContext`.
- Apply selection-only `textupdate` events and programmatic selection changes.
- Implement pointer click, drag selection, keyboard movement, deletion,
  selected-text replacement, select-all, copy/cut/paste where platform policy
  allows.
- Ensure shortcut suppression while IME composition is active follows
  `TextInputDispatchState::shortcuts_allowed`.
- Add source gates proving no hidden textarea/contenteditable fallback and no
  user-authored IME glue is required.
- Update `web/ime-sample-*` tests to assert geometry/caret/selection behavior,
  not only ready/unsupported status.
- Add documentation under `docs/implementation/`.

## Acceptance Criteria

- Candidate windows anchor to the current caret or composition range, not the
  viewport origin.
- Only one visible caret is shown in the Arcweft text field.
- Arcweft caret and selection remain synchronized with EditContext selection.
- Arrow keys, mouse clicks, drag selection, delete/backspace, selected-text
  replacement, and select-all work in the Web sample.
- IME composition updates render preedit text and composition selection without
  corrupting committed text.
- The sample uses player-owned Arcweft glue; app authors do not write custom
  IME event conversion JS.
- Secure fields do not expose text, selection-derived anchors, clipboard text,
  or candidate geometry beyond the redacted policy.
- Unsupported browsers report typed unsupported state and install no hidden
  fallback.

## Tests To Specify And Run

- Browser smoke with an EditContext-capable browser:
  - type Japanese preedit and commit;
  - assert candidate geometry API receives non-origin caret bounds;
  - assert one visible caret in screenshot/DOM state;
  - move caret left/right and by word where supported;
  - drag or click to reposition selection;
  - select text and replace/delete it;
  - run select-all and clipboard policy checks.
- Unsupported browser smoke proving no hidden fallback.
- Source gates for forbidden `textarea`, `contenteditable`, and sample-owned
  `new EditContext` glue outside the player boundary.
- Focused Rust tests for adapter selection-only updates and geometry commands.
- JS/wasm tests for player-owned setup.
- `cargo fmt --all -- --check`.
- Focused `cargo check`/`cargo test`/`cargo clippy` for changed crates.
- `npm`/Playwright Web tests for changed browser glue.
- Structural audit if crate boundaries or public contracts change.

## Constraints

- Do not redesign the seq06.3 common text-input contract unless the package
  includes an evidence-backed contract defect note.
- Do not use hidden textarea/contenteditable fallback.
- Do not leave user-authored glue JS as the owner of IME state.
- Do not make DOM/native object identity part of Sans I/O data.
- Do not rely on manual visual inspection as the only evidence for candidate
  placement or caret behavior.

## Non-Goals

- Windows, macOS, Wayland, Android, or iOS native implementation.
- Replacing the renderer or Takumi lowering.
- Rich document editing beyond current TextField/TextArea/SecureField scope.
