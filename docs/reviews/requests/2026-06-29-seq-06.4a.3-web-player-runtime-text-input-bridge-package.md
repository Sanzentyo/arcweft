# Request 06.4a.3: Web Player Runtime Text Input Bridge Package

> **Superseded (2026-07-13):** Arcweft Style is now native-only. The CSS authoring and Takumi product-path premises in this request were removed; see [Native-only typed Style path](../../implementation/native-only-style-path-2026-07-13.md). Do not use this request to reintroduce or reimplement CSS/Takumi Style behavior.

## Sequence Position

This follows the applied Web and shared text-input substrate:

- seq06.3 platform text-input contract integration.
- seq06.4a Web `EditContext` adapter.
- seq06.4a.1 player-owned Web `EditContext` glue.
- seq06.4a.2 Web caret, geometry, selection, and command behavior.
- seq06.4g shared cross-platform editing behavior.
- seq06.4i renderer-backed text-editor geometry.
- seq06.4j native player platform text-input bridge.

This request is the Web counterpart to seq06.4j. It must not redesign the
existing Web `EditContext` adapter or JavaScript glue unless implementation
evidence shows a concrete flaw. The missing layer is the bridge between the
normal Web player runtime loop, focused Arcweft text controls, renderer-backed
geometry, and the existing player-owned `EditContext` glue.

## Problem

The Web path already has meaningful pieces:

- `arcweft-player-web::edit_context` owns typed `EditContext` event
  normalization through `TextInputDispatchState`.
- `arcweft-player-web::web_text_input` exposes wasm value-shaped entry points.
- `web/player-editcontext.js` owns the browser `EditContext` object, event
  listeners, geometry calls, caret/selection mirror behavior, and command
  conversion.
- `web/player.js` installs player-owned text input by default through
  `setupArcweftWebTextInput`.

However, the final runtime/player integration is incomplete. The wasm
activation path still has a sample-style `sample_snapshot()` path, and the
normal Web player loop in `arcweft-player-web/src/app.rs` still routes keyboard
input through ordinary `InputController::keyboard` instead of syncing a real
focused renderer text target with `EditContext` and routing platform edits back
through `InputController::text_input`.

The desired acceptance surface is not a standalone IME demo and not
user-authored EditContext glue. It is the normal Web player:

```text
web/index.html?bundle=...
startArcweftWebPlayer(...)
```

running an Arcweft bundle with actual TextField/TextArea/SecureField controls.

## Request

Produce a zip package with design, implementation overlay, tests, browser
fixtures, validation notes, and apply instructions for a Web-player runtime text
input bridge.

The package must make the normal Web player own the active text-input session
end to end:

```text
focused Arcweft text control
  -> PreparedTextInputTarget snapshot + geometry
  -> wasm/Web player bridge
  -> player-owned EditContext JS glue
  -> PlatformTextInputEvent/TextInput batch
  -> InputController::text_input / shared editor behavior
```

## Required Decisions

1. The Web-player owner type/module for the active text-input bridge. Prefer a
   typed bridge owned by `arcweft-player-web` over scattered calls from
   `app.rs`, `web_text_input.rs`, and JavaScript.
2. Whether the bridge reuses the existing `WEB_TEXT_INPUT_SESSIONS` map or
   replaces it with a runtime-player-owned session keyed by focused target.
3. How `sample_snapshot()` is removed or demoted so activation uses real
   renderer/runtime snapshots from focused Arcweft controls.
4. How the Web player discovers focused text controls from
   `PreparedFrame::focused_text_input_target()` or an equivalent
   renderer-backed hook.
5. How snapshot, selection, composition, secure redaction, revision, and
   geometry updates flow from the Web player to `web/player-editcontext.js`
   without requiring users to write custom glue.
6. How `EditContext` textupdate/composition/command callbacks re-enter the
   active Web player session and become `InputController::text_input` outcomes.
7. How keyboard shortcut suppression mirrors native/player behavior through
   `keyboard_with_ime` or the existing shared composition-aware routing.
8. How pointer focus, pointer selection, keyboard traversal, blur, canvas
   focus, page visibility, resize, scroll, and redraw refresh update the active
   `EditContext` geometry.
9. How unsupported browsers report typed unsupported state while preserving the
   no-hidden-textarea/no-contenteditable fallback rule.
10. How browser validation captures evidence for candidate-window placement,
    Arcweft caret synchronization, selection, deletion, replacement, and secure
    field redaction.

## Required Implementation

- A Web-player text-input bridge module or owner type with a clear public
  boundary inside `arcweft-player-web`.
- Integration into the real Web player loop in `app.rs`, including redraw,
  prepared frame sync, focus changes, pointer events, keyboard events, and
  platform edit pumping.
- Replacement of `sample_snapshot()` acceptance behavior with real
  focused-control snapshots. If a small helper remains for tests, it must be
  test-only or clearly fixture-only and not used by normal player activation.
- A wasm export/API shape that lets `web/player-editcontext.js` call into the
  active player session rather than creating an independent sample session.
- JavaScript glue updates only where needed to consume runtime snapshot and
  geometry updates from the player. App authors should still only call
  `startArcweftWebPlayer` or `setupArcweftWebTextInput`; they must not write
  their own IME event conversion logic.
- Routing of `TextInput` batches back into `InputController::text_input` and
  shared editor behavior.
- Secure field handling that redacts text, selection-derived geometry,
  character bounds, clipboard data, trace/evidence, replay, and Agent-observable
  values according to the existing seq06 contract.
- Web fixture scene(s) with visible TextField, TextArea, SecureField, multiple
  fonts/styles where current seq06 CSS lowering supports them, stable ids, and
  deterministic evidence hooks.
- Source gates proving that hidden `textarea`, `contenteditable`, sample-owned
  `new EditContext`, and user-authored IME glue do not return.
- Documentation under `docs/implementation/` that states what browser-real IME
  validation was and was not performed.

## Acceptance Criteria

- Normal `startArcweftWebPlayer` / `web/index.html?bundle=...` startup owns the
  active text-input session for real Arcweft text controls.
- `sample_snapshot()` is not used by the normal player activation path.
- Candidate windows anchor to renderer-backed caret/composition geometry from
  the focused Arcweft control, not to the viewport origin or an independent DOM
  mirror.
- Arcweft-rendered caret and selection stay synchronized with `EditContext`
  selection and composition.
- Textupdate, composition, command, deletion, replacement, pointer selection,
  keyboard movement, and focus loss enter the shared `TextInput` path and update
  Arcweft editor state.
- The sample and app pages remain thin consumers; they do not instantiate
  `EditContext`, own model text, or convert IME events manually.
- Unsupported browsers report typed unsupported state and install no hidden DOM
  editing fallback.
- Secure fields redact text and geometry according to the existing contract.
- Native seq06.4j and Web seq06.4a.3 share the same conceptual player bridge
  shape where practical, while keeping browser objects inside Web/JS boundaries.

## Tests To Specify And Run

- Rust unit/integration tests for the Web-player bridge lifecycle:
  activation, snapshot update, geometry update, textupdate dispatch, command
  dispatch, blur/deactivation, stale session rejection, and secure redaction.
- Player-scene/input tests proving Web platform edits enter
  `InputController::text_input`.
- Renderer geometry tests proving focused text targets expose caret, selection,
  composition, and character bounds needed by `EditContext`.
- Source gates for no hidden textarea/contenteditable fallback and no
  sample-owned `new EditContext`.
- JS tests for `web/player-editcontext.js` proving runtime snapshot/geometry
  updates can be consumed without app-authored event conversion glue.
- Browser smoke with an EditContext-capable browser:
  - type Japanese preedit and commit;
  - verify candidate geometry is non-origin and near the Arcweft caret;
  - move the caret with arrows and pointer clicks;
  - select text, replace it, delete it, and blur focus;
  - exercise TextArea multiline behavior;
  - verify SecureField redaction.
- Unsupported-browser smoke proving typed unsupported state and no fallback.
- `cargo fmt --all -- --check`.
- Focused `cargo check`/`cargo test`/`cargo clippy` for touched crates.
- `cargo check -p arcweft-player-web --target wasm32-unknown-unknown` in an
  environment with the required wasm C toolchain, or a documented blocker if
  `clang`/toolchain support is unavailable.
- wasm-bindgen glue regeneration and browser smoke commands.
- Structural audit if crate boundaries, public contracts, or responsibility
  modules materially change.

## Constraints

- Do not redesign the seq06.3 common text-input contract unless the package
  includes an evidence-backed defect note.
- Do not leave `sample_snapshot()` or a sample-only session as the normal player
  acceptance path.
- Do not require user-authored pages to handle EditContext events manually.
- Do not add hidden textarea/contenteditable fallback.
- Do not put DOM object identity, `EditContext` objects, or browser event
  objects into Sans I/O crates, replay data, or portable capture schemas.
- Do not mark real browser IME acceptance complete without browser evidence.
- Do not use CPU-rasterized UI or Takumi bitmap fallback to solve caret or
  candidate geometry.

## Non-Goals

- Windows TSF, macOS AppKit, Wayland, Android, or iOS native backend work.
- Takumi/wgpu CSS compositing effects; use seq06.9a-06.9c for that.
- Full rich-document editing beyond current TextField/TextArea/SecureField
  scope.
- Replacing the existing WebGPU player renderer.

## Parallelization Guidance

This request can be designed and implemented in parallel with seq06.9a-06.9c
because those cuts target CSS compositing, not text-input session ownership.

It should not be implemented blindly in parallel with another change that
modifies `PreparedFrame::focused_text_input_target()` or renderer-backed
text-control geometry. If seq06.4i follow-up geometry work is still moving,
coordinate on the exact `PreparedTextInputTarget` shape first, then let this
package own the Web player/session/glue integration.

Recommended throwing order:

1. Throw this request by itself if the immediate goal is fixing Web IME
   usability.
2. Throw seq06.9a separately for Takumi/compositing substrate.
3. Let seq06.9b and seq06.9c design in parallel after 06.9a's contract is
   stable enough.
