# Seq-03.8 Request: Windowed Live Patch Ingress Closure Audit Package

## Sequence Position

This follows seq03.5, seq03.6, and seq03.7. The existing seq03.8 request is:

- `docs/reviews/requests/2026-06-28-seq-03.8-windowed-live-patch-ingress-adapter-package.md`

This request does not replace that request by assumption. It asks for a
current-main audit that determines whether seq03.8 is still outstanding, already
implemented by later work, or needs one or more narrower follow-up packages.

## Problem

Seq03.7 added windowed live-patch smoke fixtures and fixture regeneration. The
repo may still lack the adapter-side ingress path that feeds typed live-patch
events from a local watch/sidecar/dev adapter into the running windowed native
owner. Before starting seq04/seq05/seq06-dependent work that assumes seq03 is
closed, we need a source-evidence audit rather than a guess.

## Request

Produce a final zip package containing a seq03.8 closure audit for current
Arcweft `main`.

The audit must classify every acceptance item from the existing seq03.8 request
as one of:

- `implemented_and_validated`;
- `implemented_but_not_validated`;
- `missing`;
- `obsolete_or_subsumed`;
- `underspecified_requires_request_split`.

If anything is missing or underspecified, the package must include
throw-ready follow-up request markdown. If seq03.8 is genuinely complete, the
package must include the implementation-note text that should be added to close
seq03.

- `crates/arcweft-runtime-driver` patch/session APIs.

## Required Audit Questions

1. Does current `main` expose a typed adapter-owned ingress API for
   `WindowedPatchEvent` or equivalent local patch events?
2. Can `arcw run --watch` or an equivalent dev adapter enqueue a local patch
   into an already running windowed owner without mutating runtime state outside
   the event-loop owner?
3. Is there a clear frame-boundary rule that applies queued patches only at the
   safe windowed mutation point?
4. Are malformed local patch messages, wrong-base patches, disconnected event
   loops, and closed players reported through typed retained errors?
5. Are FIFO/backpressure/coalescing semantics implemented and tested?
6. Do seq03.7 smoke fixtures actually exercise external ingress, or only direct
   owner/session calls?
7. Does the ingress path consume seq02.5 patch schema 2 compatibility instead
   of locally reclassifying artifact changes?
8. Is any transport/filesystem/socket/watch logic kept out of
   `arcweft-runtime-driver`?
9. Are there deterministic tests or platform-gated validation commands that can
   prove the ingress path?
10. If seq03.8 is not complete, should the remaining work stay one package or
    split into watch transport, event-loop proxy, retained reports, and CLI
    integration?

## Acceptance Criteria

- Every seq03.8 requirement has a concrete file/function/test evidence citation
  or a concrete gap.
- The audit distinguishes direct fixture calls from a true external ingress
  adapter.
- The audit identifies whether seq03 can be treated as closed on current
  `main`.
- Missing work is converted into independently throwable request markdown with
  sequence-preserving numbering.
- The package does not redesign seq03 generation semantics unless it finds a
  concrete current-main flaw.

## Validation To Run Or Specify

- `cargo +nightly -Zscript tools/regenerate-windowed-live-patch-fixtures.rs --check`.
- Focused tests for any existing windowed live-patch owner/session APIs.
- Focused `cargo check` for `arcweft-player-native`,
  `arcweft-runtime-driver`, and any CLI/watch adapter crate involved.
- `git diff --check` for generated request or note overlays.

## Non-Goals

- Implementing release/trust/signature policy.
- Adding network/HTTP/watch responsibilities to `arcweft-runtime-driver`.
- Replacing seq03.7 smoke fixtures.
- Broad native player refactors unrelated to live-patch ingress closure.

## Parallelization Guidance

This audit can run in parallel with seq04/seq05/seq06 design work because it is
evidence-gathering first. Do not apply any production seq03.8 implementation
result until the audit says whether one package is still enough or narrower
follow-up requests are needed.
