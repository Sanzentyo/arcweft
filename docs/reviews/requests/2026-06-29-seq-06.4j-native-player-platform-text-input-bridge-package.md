# Request 06.4j: Native Player Platform Text Input Bridge Package

## Sequence Position

This follows the applied seq06 text-input substrate:

- seq06.3 platform text-input contract integration.
- seq06.4a Web EditContext adapter.
- seq06.4b/06.4b.2 Windows TSF adapter and real IME object boundary.
- seq06.4c/06.4c.2 macOS `NSTextInputClient` adapter work.
- seq06.4g shared cross-platform editing behavior.
- seq06.4i renderer-backed text-editor geometry.

This request supersedes treating a platform-specific sample binary as the final
acceptance surface. Backend diagnostic binaries may remain useful, but Arcweft's
acceptance path must be the real native player running a DSL-backed scene.

## Problem

Arcweft now has platform text-input contracts, shared editor behavior, renderer
geometry, and platform-specific adapter pieces. The missing layer is the native
player bridge that connects those pieces without hard-wiring one platform stack
directly into the scene event loop.

The current Windows TSF sample binary is not sufficient as final validation: it
can open a native window but does not render an Arcweft scene, does not exercise
the normal `arcw run --runner native` path, and can fail in ways that only prove
the sample harness lacks a real focused player text target. Directly wiring TSF
into the player would also create a Windows-only special case instead of the
cross-platform text-input boundary Arcweft needs.

## Request

Produce a zip package with design, implementation overlay, tests, source gates,
fixtures, and validation notes for a cross-platform native-player platform text
input bridge.

The bridge must be the single native-player integration point for platform text
input. Windows TSF, macOS AppKit, Wayland text-input-v3, Android
`InputConnection`, and iOS `UITextInput` should be backend implementations or
future backend implementations behind that layer, not separate direct player
integrations.

The package must include a DSL-backed native text-input sample that can be run
through the normal Arcweft player path.

## Required Decisions

1. The owner type and module boundary for the native-player text-input bridge.
   Prefer a typed owner with platform-specific backend variants or cfg-backed
   construction over scattered direct calls from the scene loop. Use dynamic
   dispatch only if the design proves it is needed for the platform boundary.
2. How native player focus, pointer selection, keyboard focus traversal, window
   activation, window deactivation, and destroyed text controls map to one
   platform text-input session lifecycle.
3. How the player discovers focused text controls from Arcweft scene/runtime
   state, not from sample-only objects.
4. How renderer-backed geometry from seq06.4i is supplied to the platform
   backend for caret, selection, composition, and candidate-window placement.
5. How platform edits drain into the existing Arcweft
   `PlatformTextInputEvent`/batch path and then into `InputController::text_input`
   or the responsible runtime-host entry point.
6. How keyboard shortcuts and navigation use the shared
   `keyboard_with_ime`/composition-aware routing, so platform composition does
   not fight normal player shortcuts.
7. How trace capture is owned by the player run path, including redaction,
   serials, backend identity, capability evidence, geometry evidence, focus
   changes, composition updates, commits, deletion, selection movement, and
   secure-field behavior.
8. The exact CLI/API shape for running a DSL-backed native IME sample. The
   package may choose the final spelling, but it must not require users to call
   a platform-specific sample binary for acceptance.
9. What remains platform-specific in Windows TSF/AppKit/etc. backend modules,
   and what must be shared in the bridge.
10. How unsupported or unavailable backends report capabilities without adding
    compatibility shims, fake IME success, hidden DOM fallbacks, or silent
    degraded semantics.

## Required Implementation

- A native-player text-input bridge module with a clear public boundary and
  narrow platform cfg points.
- Integration into the real native scene/window owner, including lifecycle,
  focus, keyboard, pointer selection, redraw, and platform event pumping.
- A backend adapter interface or owned enum boundary that Windows TSF and macOS
  AppKit can implement without changing player-level call sites.
- Windows TSF backend wiring through the new bridge where available. If a
  platform cannot be fully validated in the package environment, leave the
  implementation behind the proper target cfg and document exact validation
  steps rather than faking success.
- A DSL-backed native sample scene with visible `TextField`, `TextArea`, and
  `SecureField` controls, multiple fonts/styles where supported by current
  seq06 CSS lowering, and deterministic labels suitable for fixture capture.
- A normal player/CLI command path for the sample, for example:

  ```bash
  cargo run -p arcweft-cli -- run --runner native <sample.arcw> \
    --text-input-trace-out fixtures/windows-tsf-real-ime/microsoft-japanese-ime-hiragana.real.json
  ```

  The package may refine the exact command if the existing CLI shape requires a
  different spelling, but the final path must be player/DSL based.

- Trace writing through the same player path, not through platform-specific
  harness-only state.
- Source gates proving that platform object identities, COM/AppKit/native ranges,
  and backend handles do not leak into Sans I/O crates or replay/capture data.
- Documentation that demotes `windows-tsf-ime-sample` and equivalent binaries to
  diagnostic harnesses only, or removes/renames them if the final bridge makes
  them unnecessary.

## Acceptance Criteria

- The final acceptance surface is a normal native Arcweft player run of a
  DSL-backed scene, not a platform-specific sample binary.
- The native player shows visible Arcweft text controls and can focus them by
  pointer and keyboard traversal.
- Platform IME candidate/composition UI is anchored to the Arcweft caret or
  composition range provided by renderer-backed geometry, not to the terminal or
  a hidden harness field.
- Platform text edits mutate Arcweft shared editor state through the existing
  batch/serial path.
- Arrow keys, mouse selection, deletion, replacement, shortcuts, and focus loss
  are routed through shared cross-platform editor behavior.
- Secure fields redact text, native ranges, object identity, geometry, capture,
  replay, and diagnostics according to the existing seq06 contract.
- Windows TSF and macOS AppKit backends can be attached through the same bridge
  boundary. Backend-specific validation gaps are documented with exact commands
  and expected evidence.
- Non-target platforms still compile through source gates or unavailable
  capability reports.

## Tests To Specify And Run

- Focused native-player bridge unit tests or integration tests for focus
  lifecycle, stale focused-control rejection, and trace capture.
- Player-scene/input tests proving platform text edits enter the shared
  `TextInput` path.
- Renderer geometry tests proving caret/selection/composition bounds flow into
  backend requests.
- Source gates for no TSF/AppKit/native identity leakage into Sans I/O crates.
- Non-Windows and non-macOS compile/source gates where feasible.
- Windows real Microsoft Japanese IME trace capture through the player/DSL path.
- macOS real Japanese IME trace capture through the same player/DSL path when
  the AppKit backend is available.
- `cargo fmt --all -- --check`.
- Focused `cargo check`/`cargo test`/`cargo clippy` for touched crates.
- Structural audit, because this adds or materially changes a cross-crate
  player/platform boundary.

## Constraints

- Do not redesign seq06.3 text-input contracts, seq06.4g editor behavior, or
  seq06.4i geometry ownership unless current implementation evidence shows a
  concrete flaw.
- Do not add Windows-only TSF calls directly into the player event loop as the
  long-term architecture.
- Do not treat a blank native window, hidden platform widget, terminal-anchored
  candidate UI, or backend-only trace as acceptance.
- Do not add compatibility shims, silent fallback editing paths, or platform
  probing that changes product/runtime semantics.

## Non-Goals

- Completing every platform backend in this one package. The bridge is the
  shared integration surface; backend completion can remain platform-specific
  follow-up work.
- Redesigning UI/CSS styling beyond what is needed for the DSL-backed sample.
- Replacing renderer-backed text geometry.
- Implementing browser/Web EditContext; the web path has a different host
  boundary even though it should share text-input contracts and fixtures.

## Parallelization Guidance

This request should be designed before new platform-specific closure packages
claim final acceptance. Once the bridge API is frozen, Windows TSF, macOS
AppKit, Wayland, Android, and iOS backends can proceed in parallel against that
API.

If multiple designers are available, use this split:

1. One designer owns seq06.4j and defines the player bridge, DSL sample, trace
   API, and source gates.
2. Windows TSF and macOS AppKit designers consume the seq06.4j API and produce
   backend closure packages without redefining player lifecycle or trace shape.
3. Wayland/Android/iOS designers can draft backend packages in parallel, but
   must mark player acceptance as dependent on seq06.4j rather than inventing
   platform-specific acceptance harnesses.
