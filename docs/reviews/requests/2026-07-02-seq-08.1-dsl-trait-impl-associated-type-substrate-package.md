# Request: seq-08.1 DSL trait / impl / associated type substrate package

## Sequence Position

Seq08 follows the language/runtime work that made ranges first-class runtime
values and moved runtime iteration to a Rust-style `Iterator` contract inside
`arcweft-core`. That runtime substrate is not enough for user-authored Arcweft
iteration or generic abstractions. The next language slice should make the DSL's
own `trait` / `impl` / associated type model real before adding standard
library traits such as `Iterator`.

Use `trait`, not `protocol`, as the Arcweft surface keyword. Existing language
documentation and parser structures already use Rust-like `trait`, `impl`,
`where`, and associated type terminology. `protocol` should remain available for
wire/host/Agent protocol concepts, not for the DSL type system.

This request should be designed before seq08.2 Iterator/IntoIterator production
integration. Seq08.2 may be drafted in parallel only if it treats the seq08.1
trait substrate as a dependency and does not invent a separate conformance model.

Known current evidence:

- Syntax has structured `TraitItem` and `ImplItem` concepts, including
  associated type member parsing and function signatures.
- `docs/01-language/traits-seq-ranges.md` describes Rust-like `trait` /
  `impl` / `where`, supertraits, associated types, and GAT-like associated type
  constructors.
- Semantic analysis has ordinary type shapes and function signatures, but no
  complete trait catalog, impl coherence model, associated type projection
  resolution, trait-bound solver, or witness/conformance representation.
- Runtime range iteration is currently a Rust implementation detail in
  `arcweft-core`; the DSL cannot define its own iterable type by implementing a
  DSL trait.
- The existing docs mention `Seq` / `IntoSeq` as the surface model for `for`.
  This may be stale relative to the desired Rust-like `Iterator` direction and
  must be explicitly reconciled, not silently ignored.

## Problem

Arcweft has syntax and design notes for traits, but the language does not yet
have a production semantic substrate for:

- trait declarations;
- impl declarations;
- associated type declarations and assignments;
- `Self::Assoc` and `T::Assoc` projection;
- trait bounds in generic parameter lists and `where` clauses;
- method requirements and method resolution through bounds;
- impl coherence / overlap diagnostics;
- a runtime-plan or compile-time witness representation that later features can
  reuse.

Without this substrate, implementing `Iterator` directly would push special-case
logic into `for`, range, sequence, or runtime-plan lowering. That would conflict
with Arcweft's no compatibility shim / no one-off parser-compiler branch policy.

## Goal

Design and implement the first production trait substrate for the Arcweft DSL.

The package should move toward the final public contract, not the smallest
compatibility patch. It should make `trait` / `impl` / associated type behavior
available as a typed compiler feature that later slices can use for
`Iterator`, `IntoIterator`, `TryLike`, `Mappable`, capacity traits, and
verified standard library abstractions.

## Required Decisions

1. Surface syntax:
   - Confirm `trait`, `impl`, `where`, `Self`, `Self::Assoc`, and `T::Assoc`
     spelling.
   - Decide whether `pub trait` / `pub impl` visibility is supported in the
     first cut or parsed but semantically constrained.
   - Decide whether associated type constructors such as `type Mapped<B>` are
     implemented now or specified as a later GAT-like slice with structured
     diagnostics in this cut.
2. Trait item model:
   - Required associated types.
   - Associated type defaults, if any.
   - Required function signatures.
   - Default method bodies, if any.
   - Supertraits and their inherited requirements.
3. Impl item model:
   - Inherent impl vs trait impl.
   - Associated type assignments.
   - Method definitions and signature compatibility.
   - Generic impls and where clauses.
   - Whether partial impls are rejected immediately.
4. Bounds and projection:
   - How generic parameter bounds are represented.
   - How `where T: Trait` and `Trait<Assoc = Type>` constraints are represented.
   - How `Self::Assoc` and `T::Assoc` resolve.
   - How ambiguous or missing associated types are diagnosed.
5. Coherence:
   - One impl per trait/type pair.
   - Overlapping generic impl detection.
   - Orphan/module rules appropriate for Arcweft packages.
   - Treatment of standard prelude/core blanket impls.
6. Witness/conformance representation:
   - Define a typed compiler/sema representation for "type implements trait".
   - Decide whether runtime-plan needs an explicit witness id now or whether
     static dispatch can preserve enough evidence for seq08.2.
   - Do not use stringly trait labels as the reusable internal contract.
7. Method resolution:
   - Direct method lookup vs trait-bound method lookup.
   - Ambiguity diagnostics.
   - Whether fully qualified syntax is required or deferred.
8. Diagnostics:
   - Structured diagnostics for missing associated type assignments, missing
     required methods, signature mismatch, duplicate impls, overlap, unknown
     trait, unknown associated type, unsatisfied bounds, and ambiguous method
     resolution.
   - These diagnostics should align with seq07 typed diagnostic direction where
     current dependency boundaries permit.
9. Documentation reconciliation:
   - Update `docs/01-language/traits-seq-ranges.md` to distinguish implemented
     seq08.1 substrate from future standard traits.
   - Explicitly state whether the old `IntoSeq` wording is retained, replaced,
     or marked future/deprecated by the next Iterator request.

## Required Implementation Scope

- Preserve or complete structured parser/CST/AST handling for `trait` and
  `impl` items without line-based parsing regressions.
- Add HIR or semantic declarations for trait definitions, impl definitions,
  associated type requirements, associated type assignments, function
  requirements, and where predicates.
- Build a typed trait/impl catalog in semantic analysis.
- Validate impl completeness and method/associated-type compatibility.
- Resolve associated type projections in expression/type checking.
- Enforce at least a conservative coherence model.
- Add typed diagnostics for the required failure cases.
- Add focused tests for parser, HIR/sema, project-level checking, and
  diagnostics.
- Add an implementation note under `docs/implementation/`.
- Do not implement `Iterator` / `IntoIterator` production `for` lowering in this
  request unless the trait substrate is already complete and the package clearly
  keeps that work as a separate final section. Iterator behavior belongs to
  seq08.2.

## Non-Goals

- Do not add a `protocol` keyword for DSL type abstraction.
- Do not implement dynamic trait objects unless the package proves they are
  required for the first substrate.
- Do not add compatibility aliases, parser branches for removed syntax, or
  stringly fallback method resolution.
- Do not hard-code `Iterator`, `IntoIterator`, `TryLike`, or `Mappable` as
  compiler magic in this request.
- Do not redesign unrelated parser/language surfaces unless current evidence
  shows a concrete blocker.
