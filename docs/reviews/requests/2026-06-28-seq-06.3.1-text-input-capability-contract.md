# Request 06.3.1: Text Input Capability Contract

## Sequence Position

This is a split-out contract design request from seq06.3. It should be resolved
before platform-specific adapter implementation for Web EditContext, Windows
TSF, macOS `NSTextInputClient`, Wayland text-input-v3, Android
`InputConnection`, and iOS `UITextInput`.

This request may run in parallel with seq06.3.2, seq06.3.3, and seq06.3.4. It
must not redesign the existing `TextInput`, `PlatformTextInputEvent`, focus
generation, or secure redaction model unless current implementation evidence
shows a concrete flaw.

## Why This Split Is Needed

`TextInputCapabilities::for_platform_adapter` currently treats all explicit
platform adapters as if they support the same feature set. That is acceptable as
a placeholder, but production adapters need a truthful capability contract so
the runtime, UI, tests, and diagnostics can distinguish fully supported,
partially supported, unsupported, privacy-redacted, and platform-disabled IME
features.

Without this design, platform adapter work can accidentally encode false
assumptions about reconversion, surrounding text, character bounds,
programmatic commit/cancel, delete-surrounding behavior, or composition segment
metadata.

## Required Research

Review the concrete capability surfaces of:

- Web EditContext:
  - MDN `EditContext`: https://developer.mozilla.org/en-US/docs/Web/API/EditContext
  - W3C EditContext draft: https://w3c.github.io/edit-context/
- Windows TSF:
  - Microsoft Text Services Framework: https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework
- macOS AppKit:
  - Apple `NSTextInputClient`: https://developer.apple.com/documentation/appkit/nstextinputclient
- Wayland text-input-v3:
  - wayland-protocols XML: https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/unstable/text-input/text-input-unstable-v3.xml
- Android:
  - Android `InputConnection`: https://developer.android.com/reference/android/view/inputmethod/InputConnection
- iOS:
  - Apple `UITextInput`: https://developer.apple.com/documentation/uikit/uitextinput

The research must identify which features are native, emulated by adapter
state, unsupported, security-gated, compositor/browser-version dependent, or
host-toolkit dependent.

## Required Decisions

1. Whether `TextInputCapabilitySupport` needs more states than
   `Supported` / `Unsupported`, such as `Limited`, `SecureRedacted`,
   `VersionDependent`, or `HostDependent`.
2. Whether capability support should include diagnostic reasons, stable codes,
   or source API names for user-facing reports.
3. How capabilities are computed for secure fields, browser capability
   detection, Wayland compositor support, and mobile soft-keyboard modes.
4. Whether capabilities belong only to adapter kind or also to an activated
   session snapshot, OS version, browser feature detection result, compositor
   protocol object, or text field options.
5. Which capabilities are required for minimal Japanese IME correctness, and
   which are optional enhancements.
6. How unsupported capabilities should affect behavior: fail activation,
   degrade UI affordances, omit host commands, or emit structured diagnostics.
7. How this contract prevents hidden textarea fallback on Web while still
   producing actionable unsupported-browser diagnostics.

## Required Output

Produce an implementation-ready design markdown that contains:

- a capability truth table for all six adapter families;
- exact proposed Rust data model changes, if any;
- session-level capability computation rules;
- secure-field capability override rules;
- diagnostics and error wording for unsupported required capabilities;
- a migration plan from the current all-supported placeholder;
- an ownership map showing which crate computes, stores, and consumes each
  capability;
- non-goals and deferred platform-specific implementation notes.

If code changes are proposed, include the exact files to edit and the expected
public API after the change.

## Implementation Order To Specify

1. Update the capability model in `arcweft-presentation` only if required.
2. Update `arcweft-runtime-host` capability gates and secure overrides.
3. Add focused unit tests for capability computation and Web unsupported mode.
4. Add source-level guards preventing silent fallback paths.
5. Update platform adapter requests to depend on the new matrix.

## Tests To Specify

- Web without EditContext reports unsupported without hidden textarea fallback.
- Secure fields redact surrounding text and reconversion capabilities.
- Each adapter kind returns a truthful default matrix.
- Session options can narrow capability support without mutating adapter-wide
  defaults.
- Unsupported required capabilities produce structured diagnostics.
- Capability serialization or debug output is stable enough for fixture review.

## Constraints

- Do not introduce OS handles into Sans I/O crates.
- Do not make `arcweft-presentation` depend on native adapter crates.
- Do not hide unsupported Web IME behind compatibility fallback.
- Do not claim capability support before the platform-specific request proves
  the API can provide it.
- Keep the model typed; avoid stringly capability names.

## Non-Goals

- Implementing the platform adapters.
- Redesigning `TextInputOperation` payload shapes except where capability
  modeling exposes a proven contract bug.
- Adding browser, TSF, AppKit, Wayland, Android, or iOS runtime code.
