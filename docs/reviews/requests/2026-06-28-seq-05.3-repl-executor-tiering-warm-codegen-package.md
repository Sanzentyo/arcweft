# Seq-05.3 Request: REPL Executor Tiering, Warm, And Codegen Package

## Sequence Position

This follows seq05.1 and should consume seq05.2 command hooks for `:warm` and `:codegen`.

Design can start in parallel with seq05.2, but implementation should wait until the REPL session API and command dispatch hooks are stable.

## Boundary Decision From Seq05.0

Seq05.3 owns concrete `:warm` and `:codegen` behavior. Seq05.2 only reserves typed command variants/hooks. Seq05.1 provides executable snapshots and invalidation tokens. Seq05.3 must not redesign the REPL state machine or make product players depend on compiler/REPL/JIT/AOT tooling.

## Request

Design and implement the VM-first executor tiering policy for Agent REPL runtime tiers, including background `:warm` and `:codegen` requests.

Return the final work as a zip package with design, Rust implementation overlay, tests, validation notes, and apply instructions.

- Accepted seq05.0 dispatch package.
- Seq05.1 REPL session/cell transaction API.
- Seq05.1 executable snapshot and tier invalidation API.
- Seq05.2 command dispatch hooks for `:warm` and `:codegen`, if available.
- `docs/reviews/requests/2026-06-24-seq-05-agent-repl-runtime-tiers.md`.
- `crates/arcweft-agent-runner/src/runner.rs`.

- Current runtime-driver and bytecode VM execution paths.

## Required Decisions

1. How `AgentControllerExecutorFactory` selects bytecode VM vs tiered executor in REPL/dev mode.
2. Which REPL policy enables tiering; product policy must remain VM-first.
3. What `:warm` means:
   - compile current committed cells;
   - compile selected cell/generation;
   - compile base project plus overlay;
   - no-op when unsupported.
4. What `:codegen` reports:
   - enabled backends;
   - warmed generations;
   - warmed cells/regions;
   - pending jobs;
   - failures;
   - invalidated artifacts;
   - fallback-to-VM state.
5. How background work is scheduled without blocking immediate cell response.
6. How codegen artifacts are invalidated by cell commit, undo, reset, base project hash change, capability/effect policy change, or generation change.
7. How effect/capability policy applies before background codegen.
8. How tiered execution preserves deterministic observation and host-call dispatch.
9. How failure falls back to VM without poisoning the REPL session.
10. Which parts remain design-only or status-only if full-script lowering or a backend is not implemented yet.
11. How status-only/no-op behavior is represented deterministically when runtime-codegen has policy/contracts but no executable backend.

## Required Implementation

- Add typed executor tier policy for REPL/dev mode.
- Add stable status/result types for warm/codegen requests.
- Add non-blocking background request plumbing where concrete backend hooks exist.
- Add `AgentControllerExecutorFactory` selection without changing product player behavior.
- Add VM fallback behavior for unsupported or failed warm/codegen requests.
- Add command handlers for `:warm` and `:codegen` through seq05.2 hooks, or include a narrow hook patch if seq05.2 has not landed.
- Add tests proving immediate VM execution remains available before and after warm/codegen attempts.
- Add implementation documentation under `docs/implementation/`.

## Required Status Surface

Seq05.3 should expose typed status equivalent to:

```rust
pub struct ReplTierPolicy;

pub struct ReplCodegenStatus;
```

Status must be deterministic even when a backend is unavailable:

```text
requested: true
started_background_job: false
backend_status: unsupported
fallback: bytecode_vm
reason: full_script_backend_not_available
```

## Acceptance Criteria

- Product execution remains bytecode-VM-first.
- REPL/dev policy can request tiered executor behavior without changing source syntax.
- `:warm` does not block immediate cell execution.
- `:codegen` reports deterministic status and failure evidence.
- Failed or unsupported codegen falls back to VM without poisoning session state.
- Host-call dispatch and Agent observation stay deterministic.
- Product players do not depend on codegen/JIT/AOT crates.
- Warm/codegen invalidation follows seq05.1 commit/undo/reset/generation/base change tokens.

## Non-Goals

- Do not add source-level JIT/AOT syntax.
- Do not require persistent cache.
- Do not make product players depend on compiler, REPL, codegen, JIT, or AOT crates.
- Do not implement a speculative full scheduler or background fiber policy.
- Do not replace the bytecode VM as the immediate execution path.
- Do not implement full-script Cranelift executable memory, native object emission, Wasm AOT helpers, OSR, or deoptimization unless another accepted request already supplies that implementation-ready backend design.

## Parallelization Guidance

Design can run in parallel with seq05.2. Implementation should follow seq05.1 and preferably seq05.2 so that command hooks are stable. If implemented before seq05.2, return a narrow hook patch and document the expected seq05.2 integration point.
