# Seq-05.3 Request: REPL Executor Tiering, Warm, And Codegen Package

## Sequence Position

This follows seq05.1 and should consume seq05.2 command hooks for `:warm` and
`:codegen`.

Design can start in parallel with seq05.2, but implementation should wait until
the REPL session API and command dispatch hooks are stable.

## Request

Design and implement the VM-first executor tiering policy for Agent REPL
runtime tiers, including background `:warm` and `:codegen` requests.

Return the final work as a zip package with design, Rust implementation overlay,
tests, validation notes, and apply instructions.

## Required Inputs

- Current Arcweft `main`.
- Seq05.1 REPL session/cell transaction API.
- Seq05.2 command dispatch hooks, if available.
- `docs/reviews/requests/2026-06-24-seq-05-agent-repl-runtime-tiers.md`.
- `crates/arcweft-agent-runner/src/runner.rs`.
- `crates/arcweft-runtime-codegen/src/lib.rs`.
- Current `AgentControllerExecutorFactory` behavior.
- Current runtime-driver and bytecode VM execution paths.

## Required Decisions

1. How `AgentControllerExecutorFactory` selects bytecode VM vs tiered executor.
2. Which REPL policy enables tiering; product policy must remain VM-first.
3. What `:warm` means:
   - compile current committed cells;
   - compile selected cell/generation;
   - compile base project plus overlay;
   - no-op when unsupported.
4. What `:codegen` reports:
   - enabled backends;
   - warmed generations;
   - pending jobs;
   - failures;
   - fallback-to-VM state.
5. How background work is scheduled without blocking immediate cell response.
6. How codegen artifacts are invalidated by cell undo/reset or generation
   changes.
7. How effect/capability policy applies before background codegen.
8. How tiered execution preserves deterministic observation and host-call
   dispatch.
9. How failure falls back to VM without poisoning the REPL session.
10. Which parts remain design-only if full-script lowering or a backend is not
    implemented yet.

## Required Implementation

- Add typed executor tier policy for REPL/dev mode.
- Add stable status/result types for warm/codegen requests.
- Add non-blocking background request plumbing where concrete backend hooks
  exist.
- Add `AgentControllerExecutorFactory` selection without changing product
  player behavior.
- Add VM fallback behavior for unsupported or failed warm/codegen requests.
- Add command hooks for `:warm` and `:codegen`, or integrate with seq05.2 if it
  has already landed.
- Add tests proving immediate VM execution remains available before and after
  warm/codegen attempts.
- Add implementation documentation under `docs/implementation/`.

## Acceptance Criteria

- Product execution remains bytecode-VM-first.
- REPL/dev policy can request tiered executor behavior without changing source
  syntax.
- `:warm` does not block immediate cell execution.
- `:codegen` reports deterministic status and failure evidence.
- Failed or unsupported codegen falls back to VM without poisoning session
  state.
- Host-call dispatch and Agent observation stay deterministic.
- Product players do not depend on codegen/JIT/AOT crates.

## Tests To Specify And Run

```bash
cargo fmt --all -- --check
cargo test -p arcweft-agent-runner repl_tiering --all-features
cargo test -p arcweft-runtime-codegen --all-features
cargo check -p arcweft-agent-runner -p arcweft-runtime-codegen -p arcweft-runtime-driver --all-targets --all-features
cargo clippy -p arcweft-agent-runner -p arcweft-runtime-codegen -p arcweft-runtime-driver --all-targets --all-features -- -D warnings
cargo +nightly -Zscript tools/structure-audit.rs --root .
git diff --check
```

If no concrete backend can run in the package environment, `VALIDATION.md` must
record which tests are design/status-only and which backend validation remains
blocked.

## Non-Goals

- Do not add source-level JIT/AOT syntax.
- Do not require persistent cache.
- Do not make product players depend on compiler or codegen crates.
- Do not implement a speculative full scheduler or background fiber policy.
- Do not replace the bytecode VM as the immediate execution path.

## Parallelization Guidance

Design can run in parallel with seq05.2. Implementation should follow seq05.1
and preferably seq05.2 so that command hooks are stable. If implemented before
seq05.2, return a narrow hook patch and document the expected seq05.2 integration
point.
