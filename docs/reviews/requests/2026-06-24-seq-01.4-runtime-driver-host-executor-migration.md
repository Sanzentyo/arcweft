# Request 01.4: Runtime Driver And Host Executor Migration

## Sequence Position

Submit this after Requests 01.1 through 01.3 have designed lowering, compact VM
execution, parity testing, and baseline compiled-region lowering.

## Request

Please design migration of `runtime-driver`, `runtime-host`, native player, and
related executor construction to the AWBC compact execution boundary.

This request should not change the product bytecode format by itself. Product
payload migration belongs in Request 01.5 after runtime selection is stable.

## Why This Needs A Separate Design Cut

The executable-runtime-core overlay defines the execution substrate but does not
describe how existing runtime/player crates should be rewired from structured
`BytecodeProgram` execution to compact AWBC execution.

The remaining design needs concrete crate-by-crate boundaries so the migration
does not introduce a third compatibility executor or leak compiler-only
dependencies into players.

## Required Design Decisions

Please provide concrete answers for:

1. Which crates currently construct or select structured bytecode executors?
2. What new runtime execution facade should those crates call instead?
3. Which crate owns executor selection between structured, compact VM, and
   compiled regions during migration?
4. How are host services, dialogue observations, choice input, await/await-many
   tasks, sources, streams, effects, traps, and saves exposed through the compact
   boundary?
5. How should existing CLI/native-player/dev flags select structured vs compact
   execution while parity gates are still open?
6. What dependencies must be removed from product players, and what dependency
   direction must be preserved?
7. What telemetry or diagnostics should report executor selection and fallback?
8. What temporary migration code is allowed, how is it named, and what deletion
   gates remove it?
9. How should save/resume/checkpoint state pass between runtime-host services
   and `FiberState`?
10. What smoke tests prove the migrated runtime boundary preserves current
    behavior?

## Required Implementation Order In The Design

Please propose small cuts in this order or justify a better order:

1. Inventory current structured executor construction and dependencies.
2. Introduce a narrow execution facade over compact AWBC/fiber exits.
3. Add explicit dev/test executor selection.
4. Wire runtime-driver and runtime-host to the facade.
5. Wire native player smoke paths.
6. Add structured/compact parity smoke coverage at the runtime boundary.
7. Remove obsolete executor construction once gates pass.

## Tests To Specify

The design should include tests for:

- executor selection policy;
- host-call/effect/source/task exits;
- dialogue/choice observations;
- trap/source-map reporting;
- save/resume checkpoint behavior;
- native player or CLI smoke commands under compact selection;
- dependency checks preventing compiler crates from entering product players.

## Constraints

- Keep product players free of syntax, HIR, sema, compiler, verifier, CLI, and
  LSP dependencies.
- Do not make structured execution a silent fallback in product code.
- Keep transition flags explicit and deletion-gated.
- Preserve deterministic runtime behavior.

## Expected Output

Please produce one design document with:

- current executor inventory;
- target crate/module architecture;
- facade types and exits;
- migration flags and deletion gates;
- host/runtime boundary behavior;
- implementation cuts;
- focused tests;
- explicit non-goals.
