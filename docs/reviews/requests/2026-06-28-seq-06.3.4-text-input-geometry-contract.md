# Request 06.3.4: Text Input Geometry and Candidate Anchor Contract

## Sequence Position

This is a split-out contract design request from seq06.3. It should be resolved
before platform-specific adapters wire candidate-window, caret, and character
geometry for Web EditContext, Windows TSF, macOS `NSTextInputClient`, Wayland
text-input-v3, Android `InputConnection`, and iOS `UITextInput`.

This request may run in parallel with seq06.3.1, seq06.3.2, and seq06.3.3. It
must preserve the existing text-local, viewport, and screen-space direction of
`TextInputGeometrySnapshot` unless evidence shows a concrete flaw.

## Why This Split Is Needed

The current contract includes text-local to viewport to screen transforms and
character bounds, but platform APIs differ in how they request caret rectangles,
first rectangles, candidate anchors, character bounds, surface-relative
coordinates, screen coordinates, and vertical writing behavior. The design must
define exactly which coordinate spaces Arcweft owns, which platform adapters
consume, and what to do when geometry is stale, clipped, transformed, scrolled,
or unavailable.

Without this design, candidate windows can appear in the wrong position,
especially under scrolling, HiDPI scaling, transformed UI, vertical text, and
multi-window native hosts.

## Required Research

Review geometry APIs and coordinate-space requirements for:

- Web EditContext:
  - MDN `EditContext`: https://developer.mozilla.org/en-US/docs/Web/API/EditContext
  - W3C EditContext draft: https://w3c.github.io/edit-context/
- Windows TSF:
  - Microsoft Text Services Framework: https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework
- macOS AppKit:
  - Apple `NSTextInputClient`: https://developer.apple.com/documentation/appkit/nstextinputclient
- Wayland text-input-v3:
  - wayland-protocols XML: https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/unstable/text-input/text-input-unstable-v3.xml
- Android:
  - Android `InputConnection`: https://developer.android.com/reference/android/view/inputmethod/InputConnection
- iOS:
  - Apple `UITextInput`: https://developer.apple.com/documentation/uikit/uitextinput

The research must identify what rectangle each platform expects, the coordinate
space used by that rectangle, and how the platform observes subsequent geometry
updates.

## Required Decisions

1. Which rectangles are canonical: control rect, caret rect, candidate anchor,
   first character rect, character bounds, selected range bounds, or visible
   clipped bounds.
2. Which coordinate spaces are stored in Arcweft and which are computed by
   native adapters: text-local, viewport, window, surface, screen, device pixel,
   logical pixel, or platform view coordinates.
3. How HiDPI scale, transformed UI, scrolling, clipping, and multi-window
   movement affect geometry snapshots.
4. How vertical writing modes map candidate anchors and character bounds.
5. How stale geometry revisions are detected and whether platform callbacks can
   request a fresh snapshot.
6. How secure fields expose geometry without exposing text or character-bound
   metadata that leaks value length.
7. Whether `TextInputGeometrySnapshot` needs additional fields, revision checks,
   or capability flags.
8. How geometry updates are batched with text-input host commands and platform
   session activation.

## Required Output

Produce an implementation-ready design markdown that contains:

- a platform-by-platform geometry requirement matrix;
- canonical coordinate-space definitions;
- candidate anchor and character-bound rules;
- HiDPI, scrolling, clipping, transform, and vertical-writing behavior;
- stale-geometry and revision handling rules;
- secure-field geometry redaction rules;
- proposed Rust data model changes, if any;
- implementation order and visual/protocol tests.

If code changes are proposed, include the exact files to edit and the expected
public API after the change.

## Implementation Order To Specify

1. Finalize coordinate-space definitions and required rectangles.
2. Update `TextInputGeometrySnapshot` only if the current shape is insufficient.
3. Add runtime-host or View tests for transform, scroll, and revision behavior.
4. Add fixture expectations for each platform adapter.
5. Update platform-specific request documents to consume the finalized geometry
   contract.

## Tests To Specify

- Candidate anchor follows the caret after scroll.
- Candidate anchor follows transformed TextField geometry.
- HiDPI scale maps logical viewport coordinates to platform coordinates
  deterministically.
- Vertical writing chooses the expected candidate anchor edge.
- Secure fields do not expose character-bound lengths when redaction forbids
  value metadata.
- Stale geometry updates are rejected or refreshed according to the design.
- Platform fixture traces include geometry update ordering.

## Constraints

- Do not put native window/view handles in Sans I/O types.
- Do not make geometry depend on wall-clock time.
- Do not leak secure-field text length through character bounds.
- Keep rendering and platform coordinate conversion separated by crate
  boundaries.
- Do not add platform fallback behavior that conflicts with the capability
  contract.

## Non-Goals

- Implementing native platform adapters.
- Redesigning the full layout engine.
- Adding rich-text selection geometry beyond TextField/TextArea needs.
