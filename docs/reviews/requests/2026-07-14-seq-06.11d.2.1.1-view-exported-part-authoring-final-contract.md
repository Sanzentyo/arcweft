## Problem and background

A caller-applied Style sheet may cross one nested-View boundary only to the
callee root and to a part that the callee explicitly exports. Private child
ancestry must remain invisible. The product codec and runtime can represent
and enforce that boundary, but `.arcw` has no final contract for declaring the
export.

View nodes already have implementation-local part identity. Making every local
part public would expose private structure and turn an incidental label into a
stable API. The contract must instead define export ownership, target, public
name, repeated occurrences, and preservation through tooling and runtime.

## Confirmed substrate that must be preserved

The following is implemented substrate, not an invitation to redesign:

- Arcweft Style has one native typed source path. There is no CSS Style variant,
  Takumi adapter, raw stylesheet payload, CSS discriminator, or CSS runtime.
- Native Style source lowers through explicit syntax AST, native HIR,
  `CheckedViewStyleCatalog`, compiler lowering, a sheet-owned
  `ViewStyleProgram`, runtime applications, and the single resolver in
  `arcweft-view`.
- `ViewPartName` is the checked selector-side part name. Selector nodes retain
  element/part/state structure and exact source ranges before product lowering.
- The in-memory `arcweft-view::ViewProgram` has local `ViewPartId` values and a
  program-owned `ViewPartExport { id, public_name }` inventory. Ownership is
  implicit in the containing program, and this runtime-oriented type does not
  carry a definition source range.
- The canonical bundle currently has
  `ViewExportedPart { view, part_id, public_name }`. Its codec rejects malformed
  identities, unknown owners and targets, and duplicate owner-local/public
  mappings. These fields are currently serialized strings, and the record has
  no exported-part definition provenance.
- Normal `.arcw` View lowering currently emits an empty exported-part inventory.
  Existing non-empty records are constructed by lower-level builders, fixtures,
  or decoded products; there is no source authoring path to preserve.
- The runtime already distinguishes implementation-local part facts from
  exported public part facts for each mounted occurrence.
- The resolver already enforces the security boundary: a caller scope may
  address the direct child root or one explicitly exported part across exactly
  one View boundary; structural selectors do not gain access to the exported
  node's private ancestors or descendants.
- Ordered Style applications, selector priority, inheritance, token ownership,
  resolver work limits, trace records, and bounded cache behavior are complete.
- Existing node-local `.part(...)` behavior is private implementation identity.
  It must not silently become public merely because this authoring feature is
  added.

A change to any item above is allowed only when the design identifies a
specific, reproducible defect that prevents the exported-part authoring
contract. Document that defect and keep the correction narrowly scoped.

## Required decisions

The final design must make every decision below. Do not leave alternatives for
the implementation agent.

1. Define one canonical `.arcw` spelling for declaring an exported part. State
   whether the declaration is attached to the target node, collected in the
   owning `view` header/body, or split between those locations. Include complete
   valid and malformed examples and exact formatter output.
2. Define the relationship between a private `.part(...)` label and a public
   export. Specify whether the export references an existing local part or
   creates both identities at once, and prohibit an equivalent second spelling.
3. Define the source, AST, HIR, checked-sema, compiler, View-program, bundle,
   and runtime shapes. Show the exact typed identity tuple for owning View,
   local target, public name, definition range, and any module visibility.
   State explicitly whether the existing in-memory and bundle records are
   replaced, narrowed, or augmented; do not assume they already preserve
   source provenance or fully typed serialized identities.
4. Define the owner and uniqueness namespaces. Cover duplicate public names in
   one View, duplicate exports of one local target, the same public name in two
   Views, overloaded/repeated local targets, and multi-module product merge.
5. Define name resolution and visibility. State which module may declare an
   export, whether private Views may expose parts to their legal callers, and
   whether a caller can qualify or otherwise bypass the callee's public table.
6. Define the one canonical selector spelling used by a caller for an exported
   part. Explain how the same spelling resolves to a private part inside the
   owning View without confusing the two namespaces, or choose a distinct typed
   syntax if that ambiguity cannot be made safe.
7. Define static-to-runtime occurrence semantics for `if`, `match`, `Repeat`,
   and nested `CallView`. An export may have zero, one, or many mounted
   occurrences; specify stable occurrence identity without exposing instruction
   ordinals or source order as public IDs.
8. Define nested re-export semantics. Choose explicit re-export at every
   boundary, direct-only export with no re-export in the first cut, or another
   closed rule. Accidental transitivity is forbidden.
9. Define how caller Style application, inheritance, selector ancestry, and
   trace provenance behave at the boundary. Preserve the rule that an exported
   part is a narrow capability and does not reveal private structure.
10. Define the semantic consistency checks between the exported-part inventory
    and the actual View instruction/part inventory, including conditional and
    unreachable targets, wrong-owner targets, and stale references after merge.
11. Define source maps and diagnostics with tight ranges for malformed syntax,
    invalid/missing/duplicate identities, wrong ownership or visibility, and
    unsupported re-export shapes.
12. Define formatter, LSP completion, hover, go-to-definition, find-references,
    rename, symbol, and semantic-token behavior. Rename must state whether local
    and public names are one operation or two distinct identities.
13. Define canonical codec validation and deterministic ordering. Decide where
    exported-part definition provenance lives in the product/source-map model,
    then state how a tampered owner, target, public name, source range, or
    duplicate record fails; decoding must not consult `.arcw` source.
14. Define edit/hot-reload behavior. State which View and Style scopes are
    invalidated when an export declaration or public name changes and how stale
    mounted occurrences are removed.

## Constraints

- Keep the system native-only. Do not add CSS syntax, CSS selectors, a Takumi
  dependency, browser CSS behavior, raw source payloads, or a CSS-shaped escape
  hatch under another name.
- Do not redesign seq-06.11d.1 through d.3, the sheet-owned
  `ViewStyleProgram`, or the single computed resolver without a concrete defect.
- Keep implementation-local part identity private by default. Public exposure
  must be explicit and owned by the callee View.
- Do not make an exported part an unowned string. Typed ownership must survive
  compiler merge and runtime mounting.
- Do not allow selector traversal across more than the one validated boundary
  capability already supported by the resolver.
- The language and product are unreleased internal contracts. Move directly to
  the chosen final model; do not add compatibility aliases, dual parsers,
  deprecated modifiers, migration readers, version bumps for abandoned shapes,
  or wrapper APIs preserving a provisional form.
- Do not add source gates. Test public parser, semantic, codec, runtime, and
  tooling behavior instead of searching repository files for spellings or paths.
- Keep syntax parsing in `arcweft-lang-syntax`, HIR in `arcweft-lang-hir`,
  semantic ownership/name checks in `arcweft-lang-sema`, product lowering in the
  compiler/tooling layer, data codecs Sans I/O, and mounted boundary facts in
  the runtime layer.
- Preserve deterministic serialization, bounded decode/resolution work, source
  provenance, and current crate dependency direction.

## Non-goals

- General public access to a callee's private View tree.
- CSS pseudo-elements, shadow-DOM compatibility, browser `part`/`exportparts`
  emulation, or DOM class semantics.
- A general component ABI, arbitrary reflection, dynamic string lookup, or
  runtime mutation of the public export table.
- Redesigning Style property/value types, cascade priority, tokens, rendering,
  or the View evaluator.
- Preserving any unpublished provisional exported-part authoring spelling.

## Required implementation order

1. Produce a decision table for private local labels, direct exports, caller
   selectors, repeated occurrences, nested calls, and re-exports.
2. Freeze one source grammar and formatter form, then specify AST and recovery
   ranges for every accepted and malformed family.
3. Specify HIR and checked ownership records plus semantic resolution and
   diagnostic codes.
4. Specify the compiler projection into the existing canonical View/export and
   Style products, including multi-module ID rewriting and source maps.
5. Specify deterministic codec validation and tamper failures.
6. Connect the checked inventory to the existing direct-boundary runtime facts;
   change the resolver only if a documented defect prevents the chosen contract.
7. Specify LSP/formatter behavior and edit invalidation.
8. Implement and validate positive, negative, round-trip, nested-runtime, and
   tooling tests before documenting the syntax as supported.

## Required test specification

### Parser, formatter, HIR, and diagnostics

- Canonical declarations parse with exact node/name/target ranges and lower
  without retaining raw source as semantic data.
- Missing targets or names, invalid identifiers, duplicate clauses, misplaced
  declarations, and deliberately unsupported alternate spellings recover with
  ordinary structured parser diagnostics.
- Formatter output is unique and idempotent; formatting malformed input keeps
  recoverable surrounding View structure.
- HIR retains typed owner/local/public identities and provenance with no string
  reparse.

### Semantic analysis and compiler lowering

- A private local part remains private until explicitly exported.
- Missing, duplicate, wrong-owner, invisible, and unsupported re-export cases
  produce stable structured diagnostics with exact ranges.
- Two Views may expose the same public name without collision; one View may not
  create ambiguous public or local mappings.
- Multi-module lowering and product merge rewrite typed references correctly
  and never resolve by suffix or source-text matching.
- Branch and repeat targets follow the selected static-to-runtime occurrence
  rule deterministically.

### Codec and tamper resistance

- Canonical encode/decode round-trips preserve owner, local target, public name,
  ordering, and source provenance.
- Malformed IDs, unknown View owners, missing local targets, duplicate records,
  invalid ranges, and product cross-section mismatches fail at the typed codec
  boundary within configured budgets.
- Decoding succeeds without source files and has no compatibility reader.

### Runtime and resolver behavior

- A caller-applied sheet reaches a direct child root and its explicit exported
  part, but not a private sibling, ancestor, or descendant.
- A private `.part(...)` with the same text as a public name is not exposed by
  coincidence.
- Repeated and conditional exported occurrences receive stable mounted facts;
  removal of an occurrence clears its cache/invalidation state.
- Nested calls follow the selected re-export policy and never become implicitly
  transitive.
- Selector trace identifies the public export and boundary decision without
  leaking a private path as public API.

### LSP and edit behavior

- Completion offers only legal declaration and selector names in the current
  owner/callee context.
- Definition, references, and rename follow the selected two-identity or
  one-identity rule exactly across modules.
- A declaration edit invalidates only affected View/export/style inventories
  and produces no stale diagnostic or mounted export.

No test may pass or fail by scanning source files for symbol spellings, snippets,
or file placement.

## Acceptance criteria

The design is implementation-ready only when all required decisions have one
answer, examples and type shapes agree, parser through runtime ownership is
traceable, malformed/tampered cases have typed failures, and an implementation
agent can complete the feature without consulting another request or guessing.
It must preserve the native-only d.1-d.3 architecture and direct-boundary
privacy model, introduce no compatibility or source gate, and leave no alternate
export spelling as an unresolved option.
