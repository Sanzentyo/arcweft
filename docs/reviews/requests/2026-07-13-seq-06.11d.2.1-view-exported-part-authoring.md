# Request: seq-06.11d.2.1 View exported-part authoring

Date: 2026-07-13

## Sequence position

This design request branches from seq-06.11d.2 after the d.1 typed Style
syntax/HIR/sema catalog. D.2 already requires typed exported-part resource
identity, codec validation, and nested-View runtime boundary semantics. Resolve
this request before claiming end-to-end `.arcw` authoring support for exported
parts. It must not delay implementation of those resource/runtime contracts.

## Why this split is needed

The Style package says that a sheet applied at a `CallView` boundary may style
the child root and explicitly exported parts, while structural selectors must
not enter private child internals. It does not define how a View author creates
that export.

The current `.part(name)` modifier identifies a node, but the package does not
say whether that act is private labeling or public export; whether an explicit
declaration is also required; how the owning View is recorded; how visibility,
duplicates, repeats, or nested re-exports behave; or how an external selector
names the export. Guessing any of these in parser or lowering would freeze a
public language contract from an incidental product record.

## Existing substrate to preserve

- D.1 owns typed `ViewPartName`, selector sequences, source ranges, checked
  Style sheets, and canonical element/state/property metadata.
- The native-only Style path owns typed sheet/patch identities, source ranges,
  ordered applications on node producers, compiler-owned resource lowering,
  and the nested-View scope barrier.
- D.2 runtime semantics permit call-boundary style to reach only the child root
  and validated exports; private descendants remain structurally invisible.
- Existing `.part(name)` parsing and element part identity must not be silently
  reinterpreted as public API without an explicit decision here.

Do not redesign that verified substrate unless a concrete implementation defect
is demonstrated.

## Required decisions

1. Specify the canonical `.arcw` syntax for declaring an exported part. Decide
   whether export is attached to the target node, declared in the owning View,
   or both, and show complete examples including formatter output.
2. Define the relationship between a local `.part(name)` marker and a public
   export. State whether all, some, or none of those markers are exported by
   default; avoid two equivalent spellings.
3. Define the identity tuple carried through AST, HIR, sema, compiler, bundle,
   and runtime: owning View ID, local target/part ID, public export name, source
   range, and any visibility/module identity.
4. Define the uniqueness namespace and diagnostics for duplicate export names,
   duplicate local targets, missing targets, invalid names, and exports from
   private or unavailable Views.
5. Define selector spelling and name resolution at the call boundary. Specify
   whether `.part`, `Element.part`, or a qualified form names an exported part,
   and how the callee's module/private namespace is hidden.
6. Define repeated and conditional target behavior. Clarify whether one static
   export may identify multiple runtime occurrences and how stable occurrence
   identity is represented without making source-order ordinals public IDs.
7. Define nested View re-export. State whether exports are transitive, require
   an explicit re-export at each boundary, or cannot be re-exported in the
   first contract.
8. Define inheritance and structural matching at the boundary precisely. The
   decision must preserve the rule that private descendants are not exposed by
   ancestry merely because the call root receives a sheet.
9. Define semantic diagnostics, formatter/LSP behavior, source ranges, and
   compiler lowering for every accepted and malformed syntax family.
10. Define the canonical product validation needed to prove the owning View,
    target part, and public name agree with the View program inventory.

## Implementation order

1. Write the source examples and a visibility/ownership table for private
   labels, direct exports, call-boundary selectors, and nested re-exports.
2. Finalize one AST/HIR/sema shape with exact ranges and diagnostics; reject
   alternate provisional spellings through normal parser recovery.
3. Extend the d.2 canonical exported-part record and compiler lowering only as
   required by the chosen authoring contract.
4. Implement parser, HIR lowering, semantic name/visibility checks, formatter,
   and LSP projection.
5. Connect the checked export inventory to the already-defined d.2
   resource/runtime boundary.
6. Add positive, malformed, visibility, codec, and nested-runtime tests before
   treating the syntax as supported.

## Tests to specify

- The canonical declaration marks exactly one intended node as an export and
  preserves its source range through HIR and compiler lowering.
- A private `.part(name)` remains unreachable from a caller's sheet.
- A direct exported part is matchable when a sheet is applied to that
  `CallView`, while a sibling private node is not.
- Duplicate public names, missing local targets, invalid names, and an export
  owned by the wrong View produce structured diagnostics with tight ranges.
- Two Views may export the same public part name without identity collision.
- Repeated/conditional occurrences follow the chosen static-to-runtime
  identity rule deterministically.
- Nested re-export follows the chosen explicit policy and never becomes
  accidentally transitive.
- Selector spelling resolves against only the callee's public export inventory
  and cannot name module-private internals.
- Multi-module compiler lowering and product merge preserve the owning View and
  rewrite references without string matching.
- Encode/decode round-trips retain ownership and source provenance; tampered
  owner/target references fail decode.
- Formatter output is canonical, malformed alternatives recover structurally,
  and no source-text gate is used as correctness evidence.

## Constraints

- Do not add compatibility aliases, dual parsers, deprecated modifiers, or a
  second public export spelling for this unreleased language surface.
- Do not model exported parts as unowned strings. Use the d.2 typed View and
  part identity boundaries and checked compiler context.
- Do not reopen `.arcw` source in CLI, bundle, runtime, or tooling to infer an
  export that sema/compiler did not retain.
- Do not let selectors cross arbitrary nested-View ancestry. Export is a
  narrow capability, not a switch that makes the child tree public.
- Do not redesign d.1 property/value/selector ownership, d.2 sheet scope, or
  the existing View evaluator unless implementation evidence identifies a
  concrete flaw.
- Do not reopen a CSS authoring, product, bundle, or runtime path while adding
  exported-part authoring. Style trace/explainability remains an independent
  sequence cut.
- Test observable parser, semantic, codec, and runtime behavior; do not add a
  source gate that searches implementation files for spellings or locations.

## Expected output

- A normative `.arcw` syntax and formatter form with private/exported/re-export
  examples.
- A visibility, ownership, and runtime-occurrence table covering direct,
  repeated, conditional, and nested View parts.
- Exact AST/HIR/sema/compiler/resource records and dependency direction.
- Structured diagnostic and source-range contracts.
- Parser, HIR, sema, compiler, codec, formatter/LSP, and nested-runtime test
  matrices sufficient for an implementation agent to proceed without guessing.
- An implementation note that records any deliberately unsupported re-export
  or occurrence case as an explicit non-goal rather than silently accepting it.
