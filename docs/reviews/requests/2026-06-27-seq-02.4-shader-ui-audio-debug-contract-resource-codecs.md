# Seq-02.4 Shader, UI, Audio, Debug, and Contract Resource Codecs

## Sequence Position

This request follows seq-02.3 and depends on the seq-02.1 common wire codec. It
collects the specialized resource families that have adapter-facing or tooling
contracts but are not required to unblock the first content/presentation/entity
migration.

If a family proves too large for one implementation package, split it further
without weakening the common wire contract.

## Why This Split Is Needed

Shader, UI, audio, debug, and contract resources have different consumers and
failure modes from core runtime/content catalogs. They may involve platform
capability requirements, inspection/debug views, presentation adapters, and
runtime host requests. They should not be silently folded into earlier codec
work without explicit schemas and tests.

## Required Decisions

1. Define canonical compact schemas for shader resources, including shader
   identity, stage, target profile, source/binary digest, specialization
   constants, uniforms, and adapter requirements linkage.
2. Define canonical compact schemas for UI resources, including widgets,
   layout/style references, input bindings, accessibility ids, and presentation
   state references.
3. Define canonical compact schemas for audio resources and audio graph
   descriptors, including buses, voices, effect resources, envelopes, runtime
   audio command references, and adapter capability requirements.
4. Define canonical compact schemas for locale/text resources, including
   locale ids, fallback chains, text-resource indexes, plural or variant
   tables if present, and source anchors.
5. Define canonical compact schemas for debug symbols and contracts, including
   public inspection names, stable ids, source spans, verifier contracts,
   adapter contracts, and product visibility.
6. Define how each family participates in patch compatibility fingerprints.
7. Define decoder budgets and adapter-boundary error handling per family.
8. Define which fields are product-runtime truth and which are inspection-only.
9. Define whether any family remains explicitly future work and what evidence
   must unblock it.

## Implementation Order To Specify

1. Classify each specialized family as implementation-ready, future,
   inspection-only, or dependent on another design.
2. Implement the smallest implementation-ready codec family first, using the
   seq-02.1 common wire primitives.
3. Add deterministic fixtures and malformed/budget tests.
4. Wire product AWFB encode/decode and inspection export for the migrated
   family.
5. Add patch compatibility fingerprints for the migrated family.
6. Repeat family-by-family; split follow-up requests where a family needs more
   design.

## Tests To Specify

- deterministic bytes for each implemented family;
- schema-version and unknown-field behavior;
- adapter requirement reference validation;
- malformed shader/UI/audio/debug/contract payload diagnostics;
- budget failures for large graphs, tables, strings, and source spans;
- patch classification for resource-only, adapter-affecting, and
  restart-required changes;
- runtime/presentation smoke where a migrated family affects observable
  product behavior;
- source gates proving no product JSON fallback for migrated families.

## Constraints

- Keep codecs Sans I/O and deterministic.
- Do not compile shaders, initialize UI platforms, open audio devices, or fetch
  resources inside `arcweft-bundle`.
- Do not parse string operation names or platform names as compatibility
  shims; use typed registries and ids.
- Do not redesign seq-01 AWBC audio payload work unless this request finds a
  concrete schema conflict.
- Keep inspection/debug data from becoming product-runtime executable truth
  unless explicitly designed.

## Non-Goals

- Replacing the common resource wire codec from seq-02.1.
- Reopening runtime-types, entrypoints, adapter requirements, content,
  presentation, or entity schemas unless a cross-reference bug is found.
- Patch v2 container, AWFR archive, external payload carrier, or signing-policy
  redesign.

## Expected Output

Produce a design or implementation package with:

- per-family readiness classification;
- canonical schemas for implementation-ready families;
- explicit future-work boundaries for blocked families;
- patch fingerprint rules;
- implementation order and test matrix;
- deletion gates for typed JSON product payloads.
