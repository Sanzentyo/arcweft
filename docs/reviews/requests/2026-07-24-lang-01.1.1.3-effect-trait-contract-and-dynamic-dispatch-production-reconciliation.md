## Why reconciliation is required

The parent contract gives the semantic direction but does not close the
production boundary:

1. `TraitMethodRequirement` and `TraitMethodImpl` retain typed signatures and
   bodies but no authoritative semantic effect row, exact effect-clause span,
   or join to the shared callable/effect facts.
2. The parent says an omitted bodyless-trait method row is closed empty and an
   awaiting impl must be rejected, but it does not select the diagnostic owner,
   code, primary range, related ranges, or shortest-trace projection when no
   authored row exists.
3. The parent requires dynamic trait-object dispatch in E017, while the
   maintained language design explicitly defers dynamic trait objects and the
   current syntax/HIR/sema has no such value type or dispatch owner. Static
   witness method dispatch exists, but it is not equivalent evidence.
4. Current effect diagnostics expose legacy `AWF-EFX-*` categories, while the
   parent names `sema.effect.closed_row_missing` for E022/E023 without defining
   the exact typed diagnostic migration, source binding, or LSP projection.
5. Method resolution has typed trait identities, but the contract does not say
   whether trait requirements, impl methods, method values, static witnesses,
   imports, and any future dynamic dispatch join through `TraitCallableId`, a
   project declaration ID, a catalog record, or another sole owner.

Implementing these choices locally would guess a public language surface,
semantic identity, diagnostic contract, or duplicate effect authority.

## Required decisions

### 1. Sole trait-method effect owner

- Select the exact typed owner and identity for a trait requirement's authored
  effect contract, an impl method's inferred effect row, and the conformance
  relation between them.
- Give the exact fields, constructors, visibility, source spans, and
  publication order through trait catalog construction, body checking,
  callable resolution, project indexing, and tooling.
- Reuse the existing callable/effect registries where their identity is
  sufficient. Do not introduce a parallel trait-only string ID, copied effect
  set, or second body inference pass.
- State how inherited requirements, imports/reexports, aliases, method values,
  and static witness calls preserve one identity and one row.

### 2. Omitted and explicit effect-row semantics

- Confirm the exact representation of an omitted bodyless-trait method row as
  closed empty, without treating an absent span as an open/unknown row.
- Define how explicit closed and existing typed open rows are represented and
  substituted; do not invent a second effect-row grammar.
- Define the exact subset check for impl inference, including multiple effects,
  inherited requirements, generic substitutions, currying, and
  `control.suspend`.
- Define behavior for a body-bearing inherent method separately from a
  bodyless trait requirement.

### 3. Typed diagnostics and source ownership

- Select the exact diagnostic enum variants and stable codes for E015, E016,
  E022, and E023.
- For each case, specify the primary source span, related requirement/impl/call
  spans, effect payload, and deterministic shortest call trace. In particular,
  state what owns the primary range when the trait requirement omitted its
  effect clause.
- Reconcile the named `sema.effect.closed_row_missing` contract with the
  existing effect-diagnostic family. Directly replace obsolete generic or
  legacy categories where appropriate; do not leave dual diagnostics or a
  compatibility mapping.
- Specify CLI and LSP rendering from the same typed diagnostic without source
  reparsing or spelling-specific branches.

### 4. E017 dynamic-dispatch precedence

- Reconcile E017 with the maintained design that defers dynamic trait objects.
- Select exactly one final disposition:
  - define a complete implementation-ready dynamic trait-object
    syntax/type/HIR/witness/runtime/tooling contract and its dependency order;
    or
  - explicitly supersede E017 for Lang-01.1.1, classify it as a future
    language feature, and provide a correctly scoped replacement row for the
    currently supported static witness dispatch.
- Do not silently count static witness dispatch as dynamic-trait-object
  evidence, and do not add a placeholder `dyn` parser branch, erased string
  type, compatibility node, or non-executable HIR variant.

### 5. Publication and deletion order

- Give one compile-clean, deletion-driven order that adds the final typed owner,
  migrates every consumer, then deletes old copied rows, string identities,
  generic diagnostics, and duplicate inference branches in the same public
  authority switch.
- Identify the exact current consumers to migrate and the behavior/API tests
  that prove the old path is gone. Do not prescribe a source-text gate.
- Keep this semantic cut independent from the Stream wire/opcode correction
  and the Proof syntax/HIR public switch unless an exact dependency is
  demonstrated.

## Tests to specify

The returned matrix must include at least:

- A023 and E014: an awaiting impl accepted only when the bodyless requirement
  explicitly permits `control.suspend`;
- E015: an omitted requirement row is closed empty and rejects the awaiting
  impl with exact typed diagnostic and ranges;
- E016: an explicit non-suspending requirement rejects a suspending impl with
  the shortest deterministic trace;
- inherited and generic requirements, two same-named traits, method aliases,
  curried method groups, method values, and static witness dispatch;
- E022 direct Await and E023 transitive callee propagation with exact primary
  and related spans;
- explicit open-row substitution without losing other effects;
- missing, ambiguous, private, stale, and rollback trait/callable identities;
- the selected E017 disposition, with positive runtime/tooling evidence if
  dynamic trait objects are selected or explicit non-applicability and current
  grammar rejection if they remain deferred; and
- focused sema, compiler, LSP, workspace, Clippy, structural, and applicable
  Tier 2 gates.

Removal evidence must use typed APIs, compile-fail visibility, behavior,
diagnostic, or structured dependency evidence. It must not scan repository
source text for spellings.

- Do not introduce compatibility aliases, shims, dual readers, source gates,
