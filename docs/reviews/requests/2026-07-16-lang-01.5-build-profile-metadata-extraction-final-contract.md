# Request: Build and profile metadata extraction final contract

## Sequence position

This is Lang-01.5, split from the 2026-07-16 top-level declaration reduction.
It is independent of callable, live-source, and typed-resource surface design.

## Why this split is needed

Several current source declarations primarily select packaging, profiles, or
concrete adapters rather than executable language behavior:

- `dialogue defaults` combines style/default data with launch-profile choice;
- `content` identifies package/build roots;
- hand-authored concrete `extern ... mod ... from ...` mirrors adapter ABI
  metadata;
- concrete Activity Rust/WASM/process origin is a build selection even when
  the abstract Activity identity remains author-visible.

Moving them blindly to TOML would replace typed source scaffolds with stringly
configuration. The destination manifest and source-owned pieces must therefore
be designed together.

## Required decisions

1. Split each current declaration into source-owned typed data, build/profile
   selection, generated adapter metadata, and runtime identity.
2. Define the typed manifest schema for content roots, dialogue profile
   selection, concrete extern modules, and concrete Activity implementations.
3. Decide which dialogue typography/default data becomes a typed style or
   View resource and which selection belongs to the launch profile.
4. Define module/package IDs, version/ABI hashes, visibility, dependency demand,
   and diagnostics without source re-parsing.
5. Define generated Rust/WASM/process adapter metadata import and prohibit
   hand-maintained duplicate symbol declarations where generation is
   authoritative.
6. Preserve abstract `extern capability` and abstract Activity interfaces as
   security/runtime boundaries where required.
7. Define project-index, CLI, LSP, build-cache, and Agent inspection behavior
   for manifest-owned data.
8. Provide a direct source/manifest migration; do not support both locations.

## Implementation order to specify

1. Typed manifest schemas and identity/hash rules.
2. Source-vs-manifest ownership table.
3. Compiler/project-loader/index integration.
4. Dialogue style/View and Activity/adapter mappings.
5. Tooling, diagnostics, and generated metadata support.
6. Delete old declaration grammars, AST/HIR variants, and obsolete examples.

## Tests to specify

- Content demand and launch-profile selection are deterministic and typed.
- Missing, duplicate, ambiguous, and wrong-family references have structured
  diagnostics.
- Generated adapter metadata ABI mismatches and tampering are rejected.
- Abstract capability/Activity identities remain stable while concrete
  implementation selection changes by profile.
- Project index, CLI, LSP, build cache, and Agent inspection agree on the same
  manifest-owned identity.
- Old source declarations have no compatibility AST/CST/HIR nodes after
  migration.

## Constraints

- No stringly manifest replacement, dual ownership, compatibility reader,
  source gate, or migration-only syntax.
- Keep data-format crates Sans I/O and project loading in adapters.
- Do not redesign verified style, View, capability, or Activity substrate
  unless evidence demonstrates a concrete defect.

## Expected output

- A source-vs-manifest ownership matrix.
- Final typed schemas and canonical examples.
- Compiler/project-loader/tooling/runtime integration contracts.
- A direct migration/deletion order and positive/negative/tamper tests.
