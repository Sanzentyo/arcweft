# Request: AW-AH-009.3 character nominal signature-help contract

Date: 2026-07-14

## Readiness result and task kind

This is a **final-design or evidence-backed non-goal task**, not an
implementation task. The repository already has character-aware call arguments,
but the LSP signature path is Rust-adapter-only. It therefore cannot be closed
merely because no character-specific signature implementation exists, and it
cannot be implemented by guessing a synthetic constructor or word-based hint.

The task is gated on the accepted AW-AH-009.1 final contract. If that artifact
is not attached, the assignee may collect surface evidence but must not finalize
typed query, alias display, cache, diagnostic, or revision APIs.

## Sequence position and reason for the split

This request follows the AW-AH-009 structural identity core and should consume
the finalized AW-AH-009.1 environment contract. It is independently throwable.

The original AW-AH-009 request requires signature-help inputs to use typed
identity. The re-upload neither identifies a character-specific signature
surface nor changes the current LSP implementation, which only delegates Rust
adapter function metadata. Implementing guessed hints would invent a new
language/tooling contract. A final design must either identify the real
character-aware call surfaces or close the item with explicit evidence that no
such signature surface exists.

This request must not redesign `CharacterNominalType`, source spelling,
completion, or hover.

## Required inputs and repository evidence

Attach both this request and
`arcweft-aw-ah-009.1-character-nominal-registration-alias-diagnostics-final-contract.zip`.
The original AW-AH-009 delivery is not otherwise required. Inspect the current
checkout and the implementation note at
[`2026-07-14-aw-ah-009-character-nominal-type-identity.md`](../../implementation/2026-07-14-aw-ah-009-character-nominal-type-identity.md).

The final decision must reconcile at least these current seams:

- `arcweft-lang-sema::checker::presentation::check_character_look_arg`
  supplies a structural character look expectation for a presentation call.
- documented dialogue and character-stage surfaces contain named `look=`
  arguments and character calls; they are real candidates that an explicit
  non-goal must classify rather than ignore.
- `TypeCheckEnv` and the project index already retain typed callable
  signatures, but no position-aware native signature-help query consumes them.
- `arcweft-lsp::features::signature::signature_help` extracts one word and
  delegates only to `rust_adapter_signature_help`; the adapter helper selects a
  Rust export by name and currently reports active parameter zero.

These facts prove a resolver gap, not the correct final scope. The assignee must
inventory all call syntaxes before choosing implementation or non-goal.

## Fixed substrate

- Expected character look/part/variant types are structural `TypeKind` values.
- `TypeCheckEnv` owns registered callable signatures and enum inventories; the
  project index owns source-declared callable signatures.
- LSP completion and hover can display inherent source labels without parsing
  them.
- Current signature help consumes only Rust adapter metadata selected by a word.

## Required decisions

1. Inventory every current Arcweft syntax surface where signature help should
   expose a character nominal type, including presentation calls, named
   arguments, constructors, methods, and callable values.
2. If no surface is applicable, state the evidence and exact non-goal; do not
   add a placeholder or synthetic character constructor. The evidence must
   explicitly classify the existing character/dialogue `look=` call surfaces
   and explain why ordinary native callable signatures do or do not own them.
3. Otherwise define the typed query from document position through HIR/sema
   callable selection, active argument, expected `TypeKind`, and profile epoch.
4. Define labels, parameter documentation, active parameter/signature, overload
   ordering, ambiguity, incomplete source recovery, and diagnostic behavior.
5. Define how same-spelling members across characters/parts remain scoped and
   how aliases affect display without affecting identity.
6. Define cache/revision identity and hard budgets for candidates, parameters,
   nested calls, and recovery work.
7. Decide the relationship between native semantic signatures and existing
   Rust adapter signature metadata without adding two competing resolvers.

## Implementation order to specify

1. Prove and freeze the applicable language surfaces.
2. Add one sema-backed signature query with typed expected arguments.
3. Adapt Rust metadata through the same result shape if both sources remain.
4. Connect LSP position/recovery and deterministic presentation.
5. Remove any word-only fallback that can select the wrong nominal owner.

## Required tests

- Each applicable call surface returns the correct active parameter and typed
  character owner/part.
- Same local member names across characters and parts do not collide.
- Canonical, compact, qualified, and aliased source spellings select one
  identity while preserving the documented display spelling.
- Nested calls, named/reordered arguments, incomplete syntax, overloads, stale
  profile facts, exact candidate limit, and one-over limit are deterministic.
- Rust adapter and native semantic signatures follow one precedence rule.
- If the design concludes no applicable surface exists, include compile/search
  inventory evidence in the design review, but do not turn source spelling into
  an automated source gate.

### Mandatory negative and recovery matrix

If signature help is applicable, the final contract must define exact outcomes
for unknown callee, ambiguous overload, unknown character owner/part, stale
profile epoch, cursor outside an argument list, missing close delimiter, nested
calls, spread arguments, duplicate named arguments, reordered named arguments,
and exact/one-over candidate, parameter, and nesting limits. It must also define
the precedence result when both native and Rust-adapter metadata can name the
same callable.

If signature help is a non-goal, the evidence matrix must enumerate every
current native call-expression family, identify its existing semantic owner,
and show why none can expose a character nominal parameter. A mere source grep
or absence of an implementation is insufficient. In either outcome, no
automated test may search checked-in source spellings.

## Constraints and non-goals

- No synthetic `CharacterLook<...>` parser, stringly signature key, or
  compatibility shim.
- No new callable syntax merely to justify signature help.
- No broad signature-help redesign outside the proven shared resolver seam.

## Acceptance and next handoff

An implementation outcome is complete only when one position-aware sema query
owns native and adapted signatures, active argument recovery is deterministic,
and all budgets/errors are final. A non-goal outcome is complete only when the

acceptance, throw a separate implementation task only for the implementation
outcome, attaching this archive and the AW-AH-009.1 final contract. Do not create
a placeholder implementation for a non-goal outcome.
