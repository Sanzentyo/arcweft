# Request: AW-AH-009.3 character nominal signature-help contract

Date: 2026-07-14

## Sequence position and reason for the split

This request follows the AW-AH-009 structural identity core and should consume
the finalized AW-AH-009.1 environment contract. It is independently throwable.

The original AW-AH-009 request requires signature-help inputs to use typed
identity. The re-upload neither identifies a character-specific signature
surface nor changes the current LSP implementation, which only delegates Rust
adapter function metadata. Implementing guessed hints would invent a new
language/tooling contract. A final design must either identify the real
character-aware call surfaces or close the item with explicit evidence that no
such signature surface exists.

This request must not redesign `CharacterNominalType`, source spelling,
completion, or hover.

## Fixed substrate

- Expected character look/part/variant types are structural `TypeKind` values.
- `SemanticEnvironment` owns callable signatures and enum inventories.
- LSP completion and hover can display inherent source labels without parsing
  them.
- Current signature help consumes only Rust adapter metadata selected by a word.

## Required decisions

1. Inventory every current Arcweft syntax surface where signature help should
   expose a character nominal type, including presentation calls, named
   arguments, constructors, methods, and callable values.
2. If no surface is applicable, state the evidence and exact non-goal; do not
   add a placeholder or synthetic character constructor.
3. Otherwise define the typed query from document position through HIR/sema
   callable selection, active argument, expected `TypeKind`, and profile epoch.
4. Define labels, parameter documentation, active parameter/signature, overload
   ordering, ambiguity, incomplete source recovery, and diagnostic behavior.
5. Define how same-spelling members across characters/parts remain scoped and
   how aliases affect display without affecting identity.
6. Define cache/revision identity and hard budgets for candidates, parameters,
   nested calls, and recovery work.
7. Decide the relationship between native semantic signatures and existing
   Rust adapter signature metadata without adding two competing resolvers.

## Implementation order to specify

1. Prove and freeze the applicable language surfaces.
2. Add one sema-backed signature query with typed expected arguments.
3. Adapt Rust metadata through the same result shape if both sources remain.
4. Connect LSP position/recovery and deterministic presentation.
5. Remove any word-only fallback that can select the wrong nominal owner.

## Required tests

- Each applicable call surface returns the correct active parameter and typed
  character owner/part.
- Same local member names across characters and parts do not collide.
- Canonical, compact, qualified, and aliased source spellings select one
  identity while preserving the documented display spelling.
- Nested calls, named/reordered arguments, incomplete syntax, overloads, stale
  profile facts, exact candidate limit, and one-over limit are deterministic.
- Rust adapter and native semantic signatures follow one precedence rule.
- If the design concludes no applicable surface exists, include compile/search
  inventory evidence in the design review, but do not turn source spelling into
  an automated source gate.

## Constraints and non-goals

- No synthetic `CharacterLook<...>` parser, stringly signature key, or
  compatibility shim.
- No new callable syntax merely to justify signature help.
- No broad signature-help redesign outside the proven shared resolver seam.

## Expected output

Produce a standalone final design or evidence-backed explicit non-goal with
exact APIs, ownership, active-argument algorithm, cache keys, limits/errors,
implementation order, and complete tests.
