# Request 01.2: Compact VM And Parity Harness

## Sequence Position

Submit this after Request 01.1 has designed `RuntimePlan` to AWBC lowering.
Design the compact VM and the structured/compact parity harness together; they
depend on the same observable semantics and fixtures.

## Request

Please design the first compact AWBC VM executor and its differential parity
harness against the current structured VM behavior.

The design should use the AWBC schema, verifier, fiber state, safe points, and
compiled-region fallback ABI already introduced by Request 01. It should not
redesign the bytecode format.

## Why These Should Be Designed Together

The executable-runtime-core overlay defines opcode shapes and broad VM rules,
but it does not implement compact VM dispatch, pattern/expression execution, or
the differential structured/compact fixture harness.

VM semantics and parity normalization must be designed as one cut because the
VM's externally observable behavior is defined by the same events the harness
must compare.

## Required Design Decisions

Please provide concrete answers for:

1. What module layout should `arcweft-core::awbc::vm` use?
2. What is the public executor API for stepping AWBC with `FiberState`,
   execution budget, host-call placeholders, and observation collection?
3. What runtime value representation does the compact VM use at execution time,
   and how does it relate to AWBC constants and current structured runtime
   values?
4. What is the exact semantics of every non-terminator opcode?
5. What is the exact semantics of every terminator opcode, including
   suspension, trap, return, dynamic goto, host call, dialogue, choice, await,
   await-many, budget yield, and unreachable?
6. How does pattern matching/binding execute, including partial failures,
   register initialization, scope rollback, and source-map diagnostics?
7. How are helpers, intrinsics, host calls, effects, sources, streams, and line
   tasks represented at the VM boundary before product migration is complete?
8. How is budget charged, and which operations create safe points?
9. How should VM traps map to structured diagnostics and source anchors?
10. What observations should the differential harness compare, normalize, or
    deliberately ignore?
11. How are nondeterministic host/task/source inputs scripted for replayable
    parity tests?
12. How should failed parity cases be minimized and reported?

## Required Implementation Order In The Design

Please propose small cuts in this order or justify a better order:

1. Add VM value/register helpers and budget accounting.
2. Implement non-terminator expression/pattern instructions.
3. Implement local control-flow terminators and trap/return.
4. Implement dialogue/choice/source/await/host boundary terminators as explicit
   suspension exits.
5. Add replayable observation recording for structured and compact executors.
6. Add differential parity fixtures for flow, dialogue, choice, await,
   await-many, goto, match, loop, source, trap, and budget behavior.
7. Put compact execution behind explicit test/dev selection only.

## Tests To Specify

The design should include tests for:

- per-opcode execution;
- register init and scope rollback;
- branch/match/loop behavior;
- source-map trap reports;
- safe-point suspend/resume;
- budget-yield determinism;
- replayed host/task/source inputs;
- structured vs compact normalized observation parity.

## Constraints

- Keep `arcweft-core` Sans I/O.
- Keep host I/O out of the VM; host interactions must be represented as typed
  exits or scripted test inputs.
- Do not silently fall back to the structured VM inside compact VM tests.
- Do not make compact execution the product default until migration gates pass.

## Expected Output

Please produce one design document with:

- VM module/API design;
- per-opcode semantics;
- value, register, scope, budget, and trap behavior;
- host/source/task boundary contracts;
- parity observation schema;
- fixture/replay design;
- implementation cuts;
- focused tests;
- explicit non-goals.
