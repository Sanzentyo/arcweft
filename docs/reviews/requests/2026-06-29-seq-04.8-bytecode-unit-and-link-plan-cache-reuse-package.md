# Seq-04.8 Request: Bytecode Unit and Link-Plan Cache Reuse Package

## Sequence Position

This follows seq04.1 through seq04.7 and consumes the executable runtime/AWBC
identity work from seq01 plus the resource/artifact identity work from seq02.
Seq04.5 deferred bytecode-unit and link-plan reuse because AWBC/codegen
identities and link descriptors were not stable enough to trust.

Seq04.8 is the first request allowed to implement persistent bytecode-unit or
link-plan reuse, and only after proving the necessary identities are stable.

Do not redesign seq01 AWBC/runtime IR, seq02 product artifact schemas, or
seq04.1-04.7 cache substrate unless current implementation evidence shows a
concrete flaw.

## Request

Design and implement persistent cache support for bytecode units and link-plan
reuse.

Return the final work as a zip package with design, Rust implementation
overlay, tests, implementation notes, validation notes, and apply instructions.

## Required Inputs

- Current Arcweft `main`.
- The seq04.7 package result, or the current repository state after applying
  seq04.7.
- Seq01 AWBC/runtime IR implementation notes.
- Seq02 product artifact and patch/signing implementation notes.
- Current `arcweft-bytecode` / AWBC encode/decode owners.
- Current compiler lowering from runtime-plan units to bytecode.
- Current product AWFB/AWBC bundle build path.
- Current cache explain and `BuildSnapshot` evidence models.

## Required Decisions

1. What is a bytecode unit in current Arcweft and which stable identity owns it:
   runtime-plan unit, entrypoint, compiled region, generation region, or another
   unit.
2. Which bytecode inputs are part of the persistent query key:
   runtime-plan unit digest, AWBC schema version, verifier policy, codegen
   policy, target profile, feature set, compiler identity, and dependency
   digests.
3. What exact bytes are persisted: canonical AWBC unit bytes, bytecode facts,
   verifier transcript, relocation/import table, or a combination.
4. What makes a link-plan descriptor stable: ordered unit identities,
   entrypoint table, resource section identities, adapter requirements, patch
   compatibility fingerprints, and product build options.
5. How reused bytecode units are verified before linking.
6. How link-plan reuse preserves AWFB/AWBC content roots and signing/publish
   boundaries.
7. How bytecode/link soft misses are reported through `BuildSnapshot` and
   `arcw cache explain`.
8. Which parts remain conservative if codegen/link identities are still not
   stable.

## Required Implementation

Implement only the ready subset.

The expected ready implementation includes:

- bytecode-unit `.awbo` schema or explicit bytecode gate object;
- link-plan `.awbo` schema or explicit link-plan gate object;
- typed query/artifact ownership on Arcweft enums;
- adapter-owned read/write-through and soft-miss evidence;
- compiler/build integration that reuses validated bytecode/link records only
  after re-verifying identity;
- cache explain output for bytecode/link query families;
- tests proving reused and rebuilt builds produce identical product bytes where
  reuse is implemented.

If either bytecode-unit or link-plan identity remains insufficient, implement
typed conservative evidence for that family and return a narrow follow-up
request. Do not implement compatibility shims, probe-based fallback, or
stringly bytecode cache acceptance.

## Acceptance Criteria

- Bytecode reuse, if implemented, is based on canonical bytecode unit identity
  and verifier/codegen policy, not on filename or timestamp reuse.
- Link-plan reuse, if implemented, is based on stable ordered unit and resource
  identities, not on the old whole-build artifact path.
- Reused bytecode/link records produce identical AWFB/AWBC product bytes to a
  source rebuild for covered fixtures.
- Stale/corrupt/mismatched bytecode or link records are typed soft misses.
- Cache explain can inspect bytecode and link-plan hit/miss evidence.
- Signing, release publish, release verification, and remote publication remain
  outside this seq04 cache slice.
- Product players remain free of compiler/persistent-cache dependencies.

## Tests To Specify And Run

```bash
cargo fmt --all -- --check
cargo test -p arcweft-project persistent_object --all-features
cargo test -p arcweft-project-loader persistent_query --all-features
cargo test -p arcweft-compiler persistent_query --all-features
cargo test -p arcweft-bundle --all-features
cargo test -p arcweft-cli cache --all-features
cargo check -p arcweft-project -p arcweft-project-loader -p arcweft-compiler -p arcweft-bundle -p arcweft-cli --all-targets --all-features
cargo clippy -p arcweft-project -p arcweft-project-loader -p arcweft-compiler -p arcweft-bundle -p arcweft-cli --all-targets --all-features -- -D warnings
cargo +nightly -Zscript tools/structure-audit.rs --root .
git diff --check
```

Focused tests must cover:

- deterministic bytecode/link object bytes;
- bytecode hit after repeated build;
- link-plan hit after repeated build;
- source/runtime-plan/codegen/verifier/options mismatch soft misses;
- malformed bytecode/link object rejection;
- cache explain bytecode/link evidence;
- identical AWFB/AWBC bytes for reused and rebuilt covered fixtures.

## Non-Goals

- No JIT/AOT machine-code cache.
- No runtime hot-swap ingress changes.
- No release signing, publish, remote upload, or trust verifier changes.
- No product JSON fallback or codec probing.
- No old AWBC compatibility shim.

## Parallelization Guidance

Seq04.8 should be designed after seq04.6 and seq04.7 are at least drafted, but
implementation must wait for seq04.7's runtime-plan unit identity. If a package
author finds bytecode and link-plan identities separable, they may return two
smaller follow-up requests, but the first implementation must still preserve a
single coherent product-byte equivalence validation story.
