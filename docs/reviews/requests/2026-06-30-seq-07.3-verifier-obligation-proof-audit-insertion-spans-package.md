# Seq-07.3 Request: Verifier Obligation Proof/Audit Insertion Spans

## Sequence Position

Seq07.3 follows seq07.2 verifier action diagnostics.

Seq07.2 added typed diagnostic suggestions, verifier `ToolAction` source-edit
payloads, host-command payloads, CLI rendering, and LSP code-action conversion.
It intentionally left proof/audit source edits gated on exact spans.

This request closes that gap by threading safe proof/audit insertion locations
from verifier obligations into typed verifier actions. Do not redesign the
project-wide diagnostic model from seq07.1 or the action carrier from seq07.2
unless current implementation evidence shows a concrete contract flaw.

## Problem

Verifier obligations can now expose typed repair actions, but proof/audit source
edits are only useful when the verifier can point at a safe insertion span. In
the current model, missing or imprecise spans force repair guidance to remain a
host command or evidence-only action.

For source-edit actions to be practical, the verifier must know where a proof
stub or unsafe audit stub can be inserted without corrupting surrounding Arcweft
source. This must be derived from typed syntax/HIR/source anchors rather than
from rendered CLI text or string search.

## Goal

Design and implement safe insertion-span propagation for verifier obligations so
`GenerateProofStub` and `GenerateUnsafeAudit` can emit typed `SourceEdit`
suggestions when the source location is exact and safe.

When exact insertion is not provably safe, the action must remain a typed host
command or evidence-only repair plan. Do not emit speculative source edits.

## Required Decisions

1. Which verifier obligation kinds can own proof insertion spans.
2. Which verifier obligation kinds can own unsafe-audit insertion spans.
3. Which AST/HIR/source structures are authoritative for finding safe insertion
   points.
4. How insertion spans are represented:
   - empty insertion range at a stable source offset;
   - replacement range for an existing placeholder;
   - enclosing declaration/item anchor plus insertion policy.
5. How indentation, surrounding newlines, attributes, and item boundaries are
   preserved in generated edits.
6. Whether proof/audit stubs are generated in verifier, compiler tooling, or a
   dedicated action-lowering context.
7. Which applicability is assigned:
   - `HasPlaceholders` for human-authored proof bodies or audit justifications;
   - `MaybeIncorrect` when the target is exact but content may require semantic
     edits;
   - never `MachineApplicable` unless the generated edit is complete and safe
     without human proof/audit text.
8. How LSP code actions and CLI suggestions expose the same edit without
   duplicating formatter logic.
9. How failures are represented when an obligation has no safe insertion span.

## Required Implementation Scope

- Add typed source insertion information to the verifier obligation model or to
  a named obligation action-lowering context.
- Thread source anchors/ranges from syntax/HIR lowering into verifier
  obligations where the dependency direction allows it.
- Convert exact proof/audit insertion spans into seq07.2 `SourceEdit`
  suggestions.
- Keep host-command actions for obligations whose insertion point is unknown,
  ambiguous, generated, macro-like, or outside the editable source file.
- Add fixtures where the CLI prints a proof/audit source-edit suggestion with a
  stable code label and patch preview.
- Add LSP/code-action tests proving the same typed source edit becomes a
  workspace edit.
- Add negative tests proving no source edit is emitted for ambiguous or
  missing-span obligations.
- Keep verifier/data crates Sans I/O. File reads, editor application, and
  source mutation belong to CLI/LSP/tooling adapters.
- Do not parse CLI output or rendered diagnostic text to recover edits.
- Do not add compatibility shims that silently accept old action shapes.

## Suggested Implementation Order

1. Inventory current verifier obligation constructors and identify where source
   anchors are lost.
2. Define a typed insertion target such as `VerifierInsertionTarget`,
   `ProofInsertionTarget`, or an equivalent owned boundary type.
3. Thread exact declaration/item/source spans into obligations during lowering
   or verification.
4. Add a small source-edit builder that owns newline/indent/stub formatting
   rules for proof and audit insertion.
5. Update `GenerateProofStub` and `GenerateUnsafeAudit` action construction to
   include source edits only when the insertion target is exact.
6. Route unchanged host-command fallback through the existing seq07.2 action
   path when no safe source edit exists.
7. Add CLI, verifier, and LSP tests.
8. Record validation and remaining edge cases in `docs/implementation/`.

## Acceptance Criteria

- Verifier obligations carry exact proof/audit insertion information when the
  source structure makes insertion safe.
- `GenerateProofStub` emits a typed `SourceEdit` only for exact safe insertion
  targets.
- `GenerateUnsafeAudit` emits a typed `SourceEdit` only for exact safe insertion
  targets.
- Generated edits preserve indentation, surrounding newlines, and source item
  boundaries.
- CLI diagnostic output shows actionable proof/audit patch previews through the
  shared diagnostic renderer.
- LSP code actions expose the same edits as workspace edits from typed action
  data.
- Ambiguous or missing-span obligations do not emit source edits and instead
  remain typed host-command/evidence repair plans.
- Product player crates do not depend on verifier edit, CLI, LSP, MCP, or debug
  inspection adapters.

## Non-Goals

- Do not redesign proof semantics, solver policy, unsafe-audit semantics, or
  verifier obligation meaning.
- Do not implement a full source formatter.
- Do not make generated proof bodies or safety justifications
  machine-applicable unless they are genuinely complete.
- Do not add one-shot migration tooling for old diagnostics.
- Do not parse terminal output to create edits.
