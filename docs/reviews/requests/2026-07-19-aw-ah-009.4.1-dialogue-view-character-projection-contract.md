## Accepted direction

Dialogue presentation remains a persistent authored View mount. Dialogue
progression, reveal, paging, stage, and advance remain runtime-driver
responsibilities; this request does not move the dialogue state machine into
View evaluation.

The author-facing View projection becomes:

```arcw
pub view MainDialogue(dialogue: DialogueView) {
    Panel {
        Text(dialogue.character.display_name)
        RichText(dialogue.content)
    }
}
```

Required typed fields:

```text
dialogue.character.id
dialogue.character.display_name
dialogue.content
dialogue.stage
dialogue.reveal
dialogue.primary_action
```

Delete the flat speaker projection:

```text
dialogue.speaker
speaker_label
DialogueTextProjection::Speaker
BundleViewTextValue::DialogueSpeaker
```

Its conceptual replacements are:

```text
character_display_name
DialogueTextProjection::CharacterDisplayName
BundleViewTextValue::CharacterDisplayName
```

Do not keep flat aliases, dual readers, deprecated fields, or compatibility
projection nodes.

The word `speaker` in a voice/TTS provider is a different external-provider
concept. Rename that API to either `voice_speaker` or `tts_speaker`; do not
conflate it with character identity.

## Current implementation problem

The current shared dialogue display path is already converged:

```text
dialogue runtime
  -> DialogueViewInput
  -> persistent View mount
  -> ResolvedTextDocument
  -> TextLayout
  -> PreparedTextBatch
  -> ViewPrimitive::Text
  -> ViewCompositor
  -> SharedRenderer
```

However, character presentation data is still flattened:

- `LineDisplaySpec` / `LineDisplayFrame` carry an optional
  `speaker_label: String`;
- standard and authored Views read `dialogue.speaker`;
- View bundle/runtime text projection has `DialogueSpeaker`;
- Agent observation, accessibility, capture, tests, schemas, and examples use
  the same flat label;
- the line display carrier does not make `CharacterId` and localized display
  name one typed character object;
- voice-provider documentation separately uses `speaker`, creating ambiguous
  terminology.

A field rename alone is insufficient because the accepted View catalog,
runtime carrier, save/restore, localization, Agent/MCP, accessibility, and
publication boundaries must agree on one identity and display-name source.

## Established substrate to preserve

- AW-AH-009.4 supplies the final `CharacterDialogue` identity/config and wire
  decision.
- `arcweft-character` owns validated `CharacterId` and character manifest
  metadata.
- Dialogue View ownership is already a required `ViewId` validated against the
  accepted View catalog and `ViewParameterRole::Dialogue`.
- Dialogue occurrences use persistent mount/entry/stage/revision identity.
- Text layout/render/capture consumes one `PreparedTextBatch`; no dialogue-only
  renderer may return.
- Native/Web/headless/capture/Agent all consume the same prepared scene.
- Save is blocked while a transient dialogue View owner cannot be restored.
- Locale resolution and localization catalogs are existing lower-level
  substrate; this request must state how they supply display names rather than
  inventing a second string table.

## Design objective

Define one typed `DialogueCharacterViewValue` (exact name open) containing
stable character identity and the resolved display name used for a particular
dialogue occurrence. Carry it from checked runtime-plan/display data through
View evaluation, save/restore, Agent/MCP, accessibility, and capture metadata
without string re-inference or a flat speaker compatibility path.

## Required decisions

### 1. Exact typed carrier and ownership

Define exact shapes for:

```text
DialogueCharacterViewValue
DialogueViewValue / DialogueViewInput integration
LineDisplaySpec and LineDisplayFrame character fields
View instruction/text projection variants
bundle/runtime wire records
```

The carrier must contain a validated `CharacterId`. Decide whether it also
contains:

- resolved display-name text;
- display-name localization key;
- source locale and effective locale;
- character manifest generation/revision;
- source provenance;
- optional presentation-specific name override.

State which crate owns each field and ensure lower crates remain Sans I/O.

### 2. Display-name and locale policy

Specify the normative resolution order for:

- character manifest display name;
- localized character name;
- line/config-specific override, if allowed;
- fallback locale;
- missing translation;
- empty display name;
- narrator or intentionally hidden name;
- hot locale change while a dialogue occurrence is retained.

Choose whether the View receives only a resolved immutable display name or a
typed localization reference that View evaluation resolves. Define
determinism, invalidation, save/restore, and replay implications.

Do not use `speaker_label` as an untyped fallback after resolution fails.

### 3. View parameter and projection contract

Define the exact nested type available for
`ViewParameterRole::Dialogue`:

```text
dialogue.character.id
dialogue.character.display_name
dialogue.content
dialogue.stage
dialogue.reveal
dialogue.primary_action
```

Decide:

- value types and nullability;
- whether `id` is a `Ref<Character>`, `CharacterId`, or View-safe nominal
  projection;
- the final standard View part/source IDs for character name and content;
- which values are layout-affecting versus paint-only;
- dependency/invalidation classes;
- behavior when character metadata changes during View-program replacement;
- whether custom Views may omit character-name rendering.

No projection may expose both nested and flat speaker fields.

### 4. Runtime-plan, bundle, and accepted runtime

Define how accepted HIR from AW-AH-009.4 supplies the character projection to:

- line display catalog;
- dialogue presentation operations;
- retained `DialogueEntryState`;
- `DialogueViewInput`;
- accepted View parameter binding;
- standard View generation;
- content-only hot swap and View-program replacement.

Wrong or missing character identity must be rejected before mount allocation or
state mutation. Define duplicate, unknown, stale, and wrong-role behavior.
Preserve atomic evaluation/replacement/restore.

### 5. Save, replay, patch, and hot reload

Inventory whether save/replay stores:

- `CharacterId` only and re-resolves the name;
- `CharacterId` plus the resolved display name/locale;
- a versioned character projection record.

Specify behavior for:

- character rename/public-ID change;
- locale change;
- manifest display-name change;
- deleted character;
- stale character generation;
- bundle patch while dialogue is retained;
- replay across an equivalent bundle.

Use one canonical typed record if persisted. Reject tampered wrong-family IDs,
unknown characters, invalid locale data, duplicates, oversized strings, stale
generations, and noncanonical encoding. Do not add a `speaker_label` dual
reader.

### 6. Agent, MCP, accessibility, hit test, and capture

Define one downstream semantic projection:

- observed dialogue object character ID and display name;
- accessibility name/label;
- text object ownership;
- hit-test object refs;
- Color/ObjectId/Mask capture descriptors;
- privacy/content-policy publication;
- trace/debug data.

State whether character display-name text is treated as authored text,
localized personal data, or ordinary presentation metadata for policy
purposes. All backends must derive it from the same prepared View text item and
semantic owner. Do not create a second speaker-text list or geometry path.

### 7. Tooling and schemas

Define updates for:

- View parameter type checking and completion;
- hover, go-to-definition, rename, and signature help;
- standard View manifest/schema;
- bundle schema and generated docs;
- formatter examples;
- Agent/MCP protocol schema;
- accessibility/debug documentation.

Tooling should offer nested `dialogue.character.*` fields from typed View
parameter metadata. It must not special-case the string `dialogue.speaker`.

### 8. Voice-provider terminology

Choose one external-provider field name:

```text
voice_speaker
```

or:

```text
tts_speaker
```

Define its type, ownership, provider mapping, diagnostics, and documentation.
It must not use `CharacterId` unless the provider contract explicitly maps a
character to a provider voice. Remove the ambiguous provider field `speaker`
directly; no alias is needed for unreleased formats.

## Ownership constraints

- `arcweft-character` owns `CharacterId` and character manifest identity.
- Runtime-plan owns checked character-to-display projection construction.
- `arcweft-render-text` may carry typed, serializable display input but does
  not perform filesystem/locale I/O.
- Runtime-driver owns retained dialogue state and atomic updates.
- View/bundle crates own typed parameter/instruction records.
- Player scene and shared renderer consume one prepared text path.
- Agent/MCP/accessibility consume semantic output from that same path.
- Voice/TTS adapter terminology remains outside dialogue character identity.

Do not introduce a higher-layer dependency into `arcweft-core`,
`arcweft-character`, or data-format crates.

## Non-goals

- Do not redesign `CharacterDialogue` config/content semantics settled by
  AW-AH-009.4.
- Do not move dialogue progression/reveal/advance into View.
- Do not make every text producer a View mount.
- Do not redesign the shared text shaper, layout engine, renderer, or capture
  architecture.
- Do not restore CSS/Takumi style paths.
- Do not add flat speaker aliases, compatibility readers, migration shims, or
  source gates.
- Do not preserve `speaker_label` because current tests or samples contain it;
  migrate those consumers to the final typed projection.

## Implementation order to specify

1. Import the settled AW-AH-009.4 character/value/wire model.
2. Freeze display-name/locale resolution and the exact nested View carrier.
3. Freeze standard View part/source IDs and voice-provider terminology.
4. Add typed line/display/bundle/View records with validation and limits.
5. Switch runtime-plan, retained dialogue state, accepted View binding,
   replacement, and restore atomically.
6. Switch standard/custom View text projection and shared prepared-text owner.
7. Switch Agent/MCP/accessibility/hit-test/capture and schemas.
8. Switch LSP/tooling/docs/examples.
9. Delete `speaker_label`, `dialogue.speaker`, old projection variants,
   provider `speaker`, readers, aliases, and old tests.
10. Run focused validation, normal workspace tests, Tier 2 MCP/Agent/native
    auxiliary/visual tests, Native/Web parity where affected, and structural
    audit.

## Required tests

- A typed `CharacterId` and resolved display name reach a standard dialogue
  View.
- A custom View reads `dialogue.character.id` and
  `dialogue.character.display_name`.
- Wrong-family, unknown, missing, duplicate, malformed, oversized, and stale
  character values fail before mount/state mutation.
- Locale fallback and hot locale change follow the normative policy.
- Hidden/narrator/empty-name behavior is explicit and tested.
- Save/restore/replay/hot reload preserve or deliberately re-resolve character
  display data according to the selected model.
- View-program replacement cannot delete/retype required dialogue character
  fields without typed rejection and atomic rollback.
- Native, Web, headless, capture, accessibility, and Agent/MCP observe the
  same character-name prepared text and semantic owner.
- ObjectId/Mask/capture refs do not create a second geometry or label store.
- Content-policy publication preserves the selected public identity policy.
- LSP completion/hover/definition/rename use nested typed fields.
- The chosen `voice_speaker` or `tts_speaker` name reaches provider adapters
  and malformed mappings are rejected.
- Compile/API tests prove flat speaker fields and old projection variants are
  absent.
- Final parser/runtime tests contain no compatibility alias or dedicated
  removed-field path.

Use typed API, behavior, codec, tamper, parity, and compile-fail tests. Do not
test deletion by scanning repository source.

## Acceptance criteria

The contract is implementation-ready only when character identity and display
name form one typed nested dialogue View value; locale and persistence behavior
are deterministic; standard/custom View fields are fixed; Agent, accessibility,
and capture use the same prepared text owner; voice-provider terminology is
unambiguous; and every flat speaker field/variant/reader can be deleted without
a compatibility path.
