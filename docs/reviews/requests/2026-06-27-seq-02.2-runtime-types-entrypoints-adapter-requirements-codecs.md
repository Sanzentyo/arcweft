# Seq-02.2 Runtime Types, Entrypoints, and Adapter Requirements Codecs

## Sequence Position

This request follows seq-02.1. It is the first concrete section-family codec
implementation request because runtime types, entrypoints, and adapter
requirements are the smallest resource families that directly shape product
runtime compatibility.

Do not begin this request until seq-02.1 has frozen the common resource wire
codec, budget model, and migration matrix.

## Why This Split Is Needed

Seq-02 needs compact product resource section codecs, but runtime compatibility
cannot wait for every content, presentation, shader, UI, or debug resource
family. Runtime types, entrypoints, and adapter requirements are the core
contract used by product loaders, runtime-driver, players, patch
classification, and release policy.

This request designs and implements only those core runtime-facing section
codecs. It must not broaden into all resource families.

## Required Decisions

1. Define canonical compact schemas for runtime type declarations, public
   runtime type ids, value kinds, function/interface fingerprints, and type
   compatibility labels.
2. Define canonical compact schemas for entrypoints, including public id,
   exported name, AWBC function binding, initial state requirements, source
   anchor, and product visibility.
3. Define canonical compact schemas for adapter requirements, including
   required capabilities, optional capabilities, version ranges, feature flags,
   launch constraints, and platform-specific requirement references.
4. Define how these sections reference AWBC functions and resource sections
   without cyclic validation.
5. Define schema versions and unknown-field behavior for each section.
6. Define decoder budgets for runtime type count, entrypoint count, adapter
   requirement count, string bytes, and cross-reference count.
7. Define patch compatibility fingerprints for each section and map changes to
   `content-only`, `code-compatible`, `code-generational`, or
   `restart-required`.
8. Define inspection/export views for these sections.
9. Decide whether old typed JSON payloads are deleted immediately after parity
   tests pass or left behind only as fixture source inputs.

## Implementation Order To Specify

1. Add compact schema types and codecs using the seq-02.1 common wire
   primitives.
2. Add JSON-to-compact parity fixtures from current typed resource values.
3. Wire product AWFB encoding to emit the compact sections.
4. Wire product AWFB decoding to require the compact sections for migrated
   product artifacts.
5. Add patch compatibility fingerprint derivation for migrated sections.
6. Update runtime-driver and player loading paths to consume the typed compact
   decode output.
7. Delete or source-gate typed JSON product fallback for these section
   families.

## Tests To Specify

- deterministic compact bytes for each section family;
- decode budget failures for each family;
- unknown required/optional field behavior;
- malformed cross-reference diagnostics;
- JSON-to-compact parity for existing fixtures;
- product AWFB built from source decodes with compact runtime sections;
- patch classification for type-compatible, entrypoint-only, and adapter
  requirement changes;
- runtime-driver/player smoke for a product bundle using compact runtime
  sections;
- source gates proving no product JSON fallback remains for migrated families.

## Constraints

- Keep `arcweft-bundle` as a Sans I/O data and codec crate.
- Keep compiler-only lowering and source diagnostics outside
  `arcweft-bundle`.
- Do not add a generic "resource JSON" escape hatch.
- Do not hard-code one-off runtime type names or adapter names when a typed
  registry or schema rule is required.
- Preserve current product AWBC execution and artifact identity behavior.

## Non-Goals

- Content, presentation, shader, UI, entity, audio, debug, or contract codecs.
- Patch v2 file-format redesign beyond compatibility fingerprints for these
  migrated section families.
- AWFR archive or signing-policy redesign.

## Expected Output

Return a design or implementation package with:

- canonical schemas for runtime types, entrypoints, and adapter requirements;
- ownership and dependency map;
- patch compatibility fingerprint rules;
- implementation cuts;
- focused fixture/test list;
- deletion gates for typed JSON product payloads.
