# Seq-05.1 Request: REPL Session, Overlay, Cell Transaction, And Immediate VM Execution Package

## Sequence Position

This is the first implementation package accepted by seq05.0. It follows the original seq05 Agent REPL runtime tiers request and consumes current seq01 executable runtime core and seq03 generation runtime semantics.

It must not depend on seq04 persistent query cache, seq03.7 windowed smoke fixtures, seq03.8 ingress adapters, or seq06 presentation/text-input work.

## Boundary Decision From Seq05.0

Seq05.1 owns the REPL transaction substrate:

- base project snapshot;
- REPL overlay module model;
- committed cell representation;
- transactional parse/HIR/sema/effect/verifier pipeline;
- rollback invariants for pre-commit failures;
- generation/binding evidence and invalidation;
- immediate committed-cell execution through the bytecode VM path;
- state mutation primitives for later commands such as list/undo/reset.

Prefer a new tooling-layer crate:

```text
crates/arcweft-agent-repl/
```

Do not put compiler-dependent REPL transaction ownership directly into `arcweft-agent-runner` or `arcweft-cli` unless current implementation evidence proves a cleaner boundary. `arcweft-agent-runner` should remain the controller execution and host-call dispatch boundary. `arcweft-cli` should become an adapter over stable REPL APIs.

## Request

Design and implement the REPL session/overlay data model and transactional cell commit model for Agent REPL runtime tiers.

Return the final work as a zip package with design, Rust implementation overlay, tests, fixtures if needed, validation notes, and apply instructions.

## Required Decisions

1. Confirm the owning crate/module for the REPL substrate. The expected answer is `arcweft-agent-repl` unless a better boundary is justified.
2. How a base project snapshot and overlay module are represented.
3. How cells are represented:
   - item cells;
   - statement cells;
   - expression cells;
   - command-only inputs, which must be rejected or delegated to seq05.2.
4. What transaction phases exist:
   - classify/parse;
   - HIR lowering;
   - semantic/effect checks;
   - verifier gate;
   - commit record construction;
   - immediate bytecode VM execution;
   - evidence publication.
5. What state is visible before commit and what state is rolled back after parse, lower, semantic/effect, or verifier failure.
6. How post-commit VM execution failures are recorded, especially when host effects may already have been observed.
7. How committed cells produce AWBC/runtime IR regions or entries without changing product source syntax.
8. How generation-aware bindings are recorded at commit time.
9. How project-bound bindings are invalidated when base project hash or active generation changes.
10. How host capability/effect policy rejects a cell before commit.
11. What minimal public API seq05.2 should use for listing cells, undo/reset, capability/generation inspection, and cell evaluation without reaching into internals.
12. What executable snapshot/invalidation API seq05.3 should use for tiering without redesigning the REPL state machine.

## Required Implementation

- Add a REPL session/overlay module data model.
- Add a typed cell input representation and transaction result model.
- Add transaction phases for the first safe cell families.
- Add rollback behavior for parse, lower, semantic/effect, and verifier failures.
- Add committed-cell immediate execution through the existing bytecode VM path, using the default Agent controller executor path.
- Add deterministic generation/binding evidence for committed cells.
- Add undo/reset state mutation primitives, but not user-visible command dispatch.
- Add narrow public APIs for later command and tiering packages.
- Add implementation documentation under `docs/implementation/`.

## Public API Requirements For Seq05.2

Seq05.1 must expose typed APIs equivalent to:

```rust
pub struct ReplSession;
pub struct ReplBaseSnapshot;
pub struct ReplCellId;
pub struct ReplCellRecord;
pub struct ReplCellList;
pub struct ReplEvaluateOutcome;
pub struct ReplUndoOutcome;
pub struct ReplResetOutcome;
pub struct ReplGenerationEvidence;
pub struct ReplBindingEvidence;
pub enum ReplTransactionError;
```

Required method families:

```rust
impl ReplSession {
    pub fn evaluate_cell(... ) -> Result<ReplEvaluateOutcome, ReplTransactionError>;
    pub fn cells(&self, filter: ReplCellFilter) -> ReplCellList;
    pub fn undo_latest_cell(&mut self, options: ReplUndoOptions) -> Result<ReplUndoOutcome, ReplTransactionError>;
    pub fn reset_to_base(&mut self, options: ReplResetOptions) -> ReplResetOutcome;
    pub fn generation_evidence(&self) -> ReplGenerationEvidence;
    pub fn binding_evidence(&self) -> ReplBindingEvidence;
    pub fn capabilities(&self) -> ReplCapabilityReport;
}
```

Seq05.2 must be able to implement commands entirely through these APIs.

## Public API Requirements For Seq05.3

Seq05.1 must expose an executable/tiering projection equivalent to:

```rust
pub struct ReplExecutableSnapshot;
pub struct ReplTierInvalidationToken;
pub enum ReplTierInvalidationReason;
```

Required method families:

```rust
impl ReplSession {
    pub fn executable_snapshot(&self) -> ReplExecutableSnapshot;
    pub fn tier_invalidation_tokens_since(&self, cursor: ReplTierCursor) -> Vec<ReplTierInvalidationToken>;
    pub fn record_tier_status(&mut self, status: ReplTierStatusRecord);
    pub fn tier_status(&self) -> ReplTierStatusProjection;
}
```

No seq05.3 API should require direct access to overlay internals or compiler state.

## Acceptance Criteria

- A REPL session can hold a base project snapshot plus committed overlay cells.
- Failed parse/HIR/sema/effect/verifier transactions leave committed state unchanged.
- Successful cells commit deterministically and execute immediately through the bytecode VM.
- VM execution failure after commit is recorded with deterministic status and host-effect evidence.
- Effect/capability policy rejects unsafe cells before commit.
- Generation and binding evidence is recorded for committed cells.
- Public APIs allow seq05.2 to list cells, undo, reset, inspect capabilities/generations, and submit cells without peeking into internals.
- Public APIs allow seq05.3 to read executable snapshots and invalidation tokens without redesigning the REPL state machine.
- Product players do not gain compiler/REPL dependencies.
- No source-level JIT/AOT syntax is introduced.

## Non-Goals

- No user-visible REPL command parser beyond the minimal typed API required for seq05.2.
- No `:warm`, `:codegen`, JIT, or AOT implementation.
- No persistent cache requirement.
- No windowed/live-patch ingress.
- No product-player dependency on compiler or REPL crates.
- No source-level tiering syntax.
- No attempt to reverse arbitrary external host side effects for undo.

## Parallelization Guidance

This should be implemented before seq05.2 and seq05.3. Seq05.2 and seq05.3 design can start in parallel, but they must treat this package's public transaction/session/executable-snapshot APIs as input boundaries.
