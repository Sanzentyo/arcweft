# Seq-05.1 Request: REPL Overlay And Cell Transaction Package

## Sequence Position

This is the first implementation package proposed by seq05.0. It follows the
original seq05 Agent REPL runtime tiers request and consumes current seq01 and
seq03 runtime semantics.

It must not depend on seq04 persistent query cache, seq03.7 windowed smoke
fixtures, seq03.8 ingress adapters, or seq06 presentation/text-input work.

## Request

Design and implement the REPL overlay session and transactional cell commit
model for Agent REPL runtime tiers.

Return the final work as a zip package with design, Rust implementation overlay,
tests, fixtures if needed, validation notes, and apply instructions.

## Required Inputs

- Current Arcweft `main`.
- `docs/reviews/requests/2026-06-24-seq-05-agent-repl-runtime-tiers.md`.
- `docs/implementation/integrated-execution-2026-06-24.md`.
- `crates/arcweft-agent-runner/src/runner.rs`.
- Current parser/HIR/sema/lowering/verifier crate boundaries.
- Current AWBC/runtime-driver generation semantics from seq01 and seq03.
- `crates/arcweft-runtime-codegen/src/lib.rs` only as future tiering context,
  not as a required dependency for this cut.

## Required Decisions

1. Which crate owns the REPL session overlay data model.
2. How a base project snapshot and overlay module are represented.
3. How cells are represented:
   - item cells;
   - statement cells;
   - expression cells;
   - command-only inputs, which may be rejected or delegated to seq05.2.
4. What transaction phases exist:
   - parse;
   - HIR lowering;
   - semantic/effect checks;
   - verifier gate;
   - commit;
   - immediate VM execution.
5. What state is visible before commit and what state is rolled back after
   failure.
6. How committed cells produce AWBC/runtime IR regions or entries without
   changing product source syntax.
7. How generation-aware bindings are recorded at commit time.
8. How project-bound bindings are invalidated when base project hash or active
   generation changes.
9. How host capability/effect policy rejects a cell before commit.
10. What minimal public API seq05.2 should use for listing cells, undo/reset,
    and command execution without reaching into internals.

## Required Implementation

- Add a REPL session/overlay module data model.
- Add a typed cell input representation and transaction result model.
- Add transactional parse/HIR/sema/effect/verifier commit flow for the first
  safe cell families.
- Add rollback behavior for parse, lower, semantic/effect, and verifier
  failures.
- Add committed-cell immediate execution through the existing bytecode VM path.
- Add deterministic generation/binding evidence for committed cells.
- Add narrow public APIs for later command and tiering packages.
- Add implementation documentation under `docs/implementation/`.

## Acceptance Criteria

- A REPL session can hold a base project snapshot plus committed overlay cells.
- Failed parse/HIR/sema/effect/verifier transactions leave committed state
  unchanged.
- Successful cells commit deterministically and execute immediately through the
  bytecode VM.
- Effect/capability policy rejects unsafe cells before commit.
- Generation and binding evidence is recorded for committed cells.
- Product players do not gain compiler/REPL dependencies.
- No source-level JIT/AOT syntax is introduced.

If the final owner crate differs, update the commands and explain why in
`verification/VALIDATION.md`.

## Non-Goals

- No user-visible REPL command parser beyond what is needed to feed cell inputs.
- No `:warm`, `:codegen`, JIT, or AOT implementation.
- No persistent cache requirement.
- No windowed/live-patch ingress.
- No product-player dependency on compiler or REPL crates.

## Parallelization Guidance

This should be implemented before seq05.2 and seq05.3. Seq05.3 design can start
in parallel, but it must treat this package's public transaction/session API as
an input boundary.
